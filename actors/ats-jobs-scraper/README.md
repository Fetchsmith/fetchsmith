# ATS Jobs Scraper – Greenhouse, Ashby, Lever, Recruitee, Workable, SmartRecruiters, Workday, Teamtailor, Personio, Breezy, Rippling & BambooHR

Live job postings straight from any company's own career board on **Greenhouse, Ashby, Lever, Recruitee, Workable, SmartRecruiters, Workday, Teamtailor, Personio, Breezy, Rippling or BambooHR** — 12 ATS platforms in one call, normalized into one schema no matter which ATS the company uses.

In short: a hiring page scraper and applicant tracking system API in one call — no browser, no login, just the postings each company's own ATS already exposes publicly.

## What it does
- Fetches each company's public job-board API directly (no browser, no login) for **Greenhouse**, **Ashby**, **Lever**, **Recruitee**, **Workable**, **SmartRecruiters**, **Workday**, **Teamtailor**, **Personio**, **Breezy**, **Rippling** and **BambooHR** — 12 ATS platforms combined reaching well over 10,000 career sites, including many large employers no other field in this list reaches.
- **Don't know which ATS a company uses?** Leave `ats` off (or set it to `"auto"`) and give just the slug — the Actor checks all 11 non-Workday platforms for you and uses whichever one is real. See [Don't know which ATS a company uses?](#dont-know-which-ats-a-company-uses-use-ats-auto).
- Normalizes every posting into one shared schema (title, department, team, employment type, workplace type, remote flag, location, salary where the ATS exposes it, timestamps, apply URL, description).
- Client-side filters (title keyword + exclude, location keyword + exclude, remote-only, has-salary, posted-after date) are applied **before** charging, so you only pay for postings you actually want.
- Companies that have migrated off an ATS (very common for Lever) are skipped with a warning, not a failed run.
- Pay per result: you are charged only for job postings actually returned. **No start fee.**

## Use cases
- **Job-board aggregation** — pull live openings from every company you track across 12 different ATSes into one feed, instead of maintaining 12 separate scrapers.
- **Recruiting/sourcing intelligence** — spot when a target company opens a new role in a specific team or location, with `department`/`team`/`location` already normalized so you can filter without per-ATS cleanup.
- **Salary benchmarking** — `salaryMin`/`salaryMax`/`salaryCurrency`/`salaryInterval` give a normalized comparable across Ashby, Lever, Recruitee and Greenhouse postings that publish pay ranges, plus Workday postings whose free-text description names a pay figure under pay-transparency law.
- **Remote-work tracking** — `remoteOnly` plus the normalized `workplaceType`/`isRemote` fields build a remote-jobs feed across every ATS at once, not just the ones with a "remote" search filter.
- **Skill/tech-stack sourcing** — `descriptionKeyword` searches the full posting body, so you can pull every role at 50 companies that mentions `Kubernetes`, `Rust` or `visa sponsorship` — requirements that almost never appear in the job title.
- **Hiring-trend research** — `postedAfter`/`postedBefore` plus `publishedAt` let you track how fast a company (or a whole market segment) is opening new roles over time.
- **Job alerts / new-posting watch** — set `watchLabel` and a scheduled run returns *only* the roles that opened since the last run, not the same open-roles list every time. You are charged for new postings only (see [Watch mode](#watch-mode-only-new-postings-since-last-run)).

## Input
| Field | Type | Description |
|---|---|---|
| `companies` | array | `[{"ats": "auto\|greenhouse\|ashby\|lever\|recruitee\|workable\|smartrecruiters\|workday\|teamtailor\|personio\|breezy\|rippling\|bamboohr", "slug": "<company-slug>"}]`. The slug is the company identifier in their career-board URL, e.g. `jobs.ashbyhq.com/ramp` → `{"ats":"ashby","slug":"ramp"}`. **Omit `ats` or set it to `"auto"` to skip knowing which platform a company uses** — the Actor tries all 11 non-Workday platforms for that slug and keeps whichever one actually has a board. **Workday's slug is `"<host>/<site>"`** (see below) since a Workday board has no single short identifier, and it always needs an explicit `"ats":"workday"` — it cannot be auto-detected. |
| `titleKeyword` | string | Only keep postings whose title contains this text. |
| `titleExcludeKeyword` | string | Drop postings whose title contains this text, e.g. `"Senior"` to filter out senior roles. |
| `locationKeyword` | string | Only keep postings whose location/city/region/country contains this text. |
| `locationExcludeKeyword` | string | Drop postings whose location/city/region/country contains this text, e.g. a country you don't hire in. |
| `employmentTypeKeyword` | string | Only keep postings whose `employmentType` contains this text, matched case- and separator-insensitively (spaces/hyphens/underscores are ignored on both sides, so `"full-time"`, `"full time"` and `"fulltime"` all match Ashby's `"FullTime"`), e.g. `"full-time"` or `"part-time"` — works on every ATS that publishes the field **except Personio**, whose closed vocabulary (`permanent`/`intern`/`temporary`/`working_student`) contains neither word — use `"permanent"` there instead. Each ATS uses its own vocabulary beyond that (`"contract"` matches nothing on Workday, Recruitee or Personio), so check the employment-type table below first. Postings where the ATS never exposes this field are dropped when set — **on Greenhouse and Teamtailor boards that is every posting** (see Employment type below). |
| `departmentKeyword` | string | Only keep postings whose `department`, `team` or `departmentPath` contains this text, e.g. `"Engineering"`. Postings where the ATS never exposes a department are dropped when set. |
| `descriptionKeyword` | string | Only keep postings whose **description text** contains this text, e.g. `"Kubernetes"` or `"visa sponsorship"` — the requirements a job title never mentions. Matched against the plain text, not the HTML. |
| `descriptionExcludeKeyword` | string | Drop postings whose description text contains this text, e.g. `"security clearance"`. |
| `hasSalary` | boolean | Only keep postings that come back with a salary — an ATS compensation field (Ashby, Lever, Recruitee) or a pay-transparency range printed in the posting body (Greenhouse). Default `false`. |
| `minSalary` / `maxSalary` | integer | Only keep postings whose salary range overlaps this floor/ceiling, e.g. `minSalary:150000`. Compared against the number as posted — no currency conversion, no pay-interval normalization (check `salaryCurrency`/`salaryInterval` on the row, since ranges mix year/month/week/day/hour). Postings with no salary never match either. |
| `remoteOnly` | boolean | Only keep postings the ATS marks as remote. Default `false`. |
| `postedAfter` | string | `YYYY-MM-DD` (or full ISO datetime); only keep postings published on/after it. The named day is included. An unparseable date stops the run — see "Date bounds" below. |
| `postedBefore` | string | `YYYY-MM-DD` (or full ISO datetime); only keep postings published on/before it — the named day is included in full. Pair with `postedAfter` for a date window (e.g. everything a company opened in one quarter). |
| `includeDescriptions` | boolean | Include full HTML + plain-text description. Default `true`. The description filters still work with this off — the text is fetched, matched, then dropped from the rows. |
| `maxJobsPerCompany` | integer | Cap on how many postings that pass your filters are kept per company — filters are applied first, then this cap. Default `50` — kept low so a run with no input at all (e.g. an API caller omitting the field) stays fast and cheap; pass a higher value explicitly for bulk pulls (up to `5000`). |
| `maxResults` | integer | Cap total postings returned across all companies. Default `300` — same reasoning as above; pass a higher value explicitly for bulk pulls (up to `100000`). If it's reached partway through your `companies` list, the remaining companies are never even checked — the status message names them (see FAQ). |
| `watchLabel` | string | Optional. Name a saved job alert and return only postings not delivered under that label + filter set before. First run per label is a free baseline. See [Watch mode](#watch-mode-only-new-postings-since-last-run). |
| `watchEvents` | array | Optional. Restrict a watch to `new`, `salaryAdded` and/or `closed` postings (empty = `new` + `salaryAdded`; `closed` is opt-in only). Ignored unless `watchLabel` is set. See [Watch mode](#watch-mode-only-new-postings-since-last-run). |
| `webhookUrl` | string | Optional. POST a small JSON completion summary (postings pushed, companies scanned/errored, dataset ID, watch new/skipped counts) here when the run finishes — see FAQ. |
| `proxyConfiguration` | object | Apify Proxy config. Default: Apify Proxy on. |

### Don't know which ATS a company uses? Use `"ats": "auto"`
If you only have a guess at the slug (e.g. the company's own name, lowercased) and not the platform, pass `{"slug": "<slug>"}` with no `ats`, or `{"ats": "auto", "slug": "<slug>"}`. The Actor tries Greenhouse, Ashby, Lever, Recruitee, Workable, SmartRecruiters, Teamtailor, Personio, Breezy, Rippling and BambooHR for that exact slug in parallel and keeps whichever platform actually has a board there — `atsSource` on the returned rows shows what it found. If the same slug happens to be a real, populated board on more than one platform (rare, but generic slugs like `demo` can collide), it keeps the one with postings; if more than one has postings, it logs the ambiguity and picks by a fixed priority order. If no platform has that slug at all, the company is skipped and reported the same as a wrong explicit `ats` guess (see below) — nothing is charged for it. Auto-detect costs the same as specifying the platform directly: only the postings actually returned are charged. **Workday is never auto-detected** — its slug format is `"<host>/<site>"`, not a bare company name, so there's nothing to guess; always pass `"ats": "workday"` explicitly for it.

### Finding a company's slug
- **Greenhouse**: `boards.greenhouse.io/<slug>` or the `gh_jid`-style URL on their careers page.
- **Ashby**: `jobs.ashbyhq.com/<slug>`.
- **Lever**: `jobs.lever.co/<slug>`. Many well-known companies have migrated to a different ATS — if the slug 404s, they're no longer on Lever and the Actor skips them without failing. Unlike Greenhouse, Lever's API honors real pagination, so the Actor only pulls roughly 3x `maxJobsPerCompany` postings off the board (not the whole thing) — on a 4,000+-posting board (e.g. `jobgether`) that is the difference between a ~1 MB request and a 50 MB one for a typical `maxJobsPerCompany`. **No 2,000-posting ceiling here either** (cycle 3694, the same self-imposed cap cycle 3692 removed from Workday): raise `maxJobsPerCompany` toward its 5,000 maximum and the raw fetch scales with it, up to ~15,000.
- **Recruitee**: `<slug>.recruitee.com`.
- **Workable**: `apply.workable.com/<slug>`.
- **SmartRecruiters**: `jobs.smartrecruiters.com/<slug>` (identifier is case-sensitive, e.g. `BMWDealerCareers`). **No 2,000-posting ceiling** (cycle 3694, same fix as Workday/Lever above): verified live against `BoschGroup`, a 5,178-posting board that now pages to the end with 0 duplicate postings across any two pages. Repeated postings are still detected and dropped as a precaution — the same guard Workday needed for a tenant that clamped its own result set — so you are never billed twice for the same requisition even on a board that behaves like `nvidia.wd5` did.
- **Workday**: use `"<host>/<site>"` from the board's own URL, e.g. `okgov.wd1.myworkdayjobs.com/okgovjobs` → `{"ats":"workday","slug":"okgov.wd1.myworkdayjobs.com/okgovjobs"}`. The `wd<N>` host segment and the site name are both required and vary per company — copy them straight from the address bar on the company's own Workday career page (`https://<host>/<site>`). **Large-enterprise and government tenants page in full: there is no 2,000-posting ceiling** (cycle 3692 — a prior internal cap stopped a Workday scan at 2,000 raw postings regardless of `maxJobsPerCompany`; verified live against `pwc.wd3.myworkdayjobs.com/Global_Experienced_Careers`, a 3,652-posting board that now scans to the end with no cut-short warning). Two real Workday quirks this scan handles for you, both measured live: `total` is only meaningful on the first page (some tenants report `total: 0` on deeper pages), and some tenants cap their own result set and then serve the **same page again** for every deeper offset rather than an empty one (`nvidia.wd5` does this past offset 2,000) — repeated postings are detected and dropped, so you are never billed twice for the same requisition. Raise `maxJobsPerCompany` to go deep: the formula scans up to 3x your cap in raw postings before filtering, so a 5,000 cap reaches ~15,000 raw. The run's own time budget is the remaining bound, and if it stops the scan early the status message says so.
- **Teamtailor**: `<slug>.teamtailor.com`, e.g. `oatly.teamtailor.com` → `{"ats":"teamtailor","slug":"oatly"}`. The board is a JSON Feed with an embedded schema.org `JobPosting` per item, so location/date/organization come free — no per-job detail call.
- **Personio**: `<slug>.jobs.personio.de`, e.g. `ottonova.jobs.personio.de` → `{"ats":"personio","slug":"ottonova"}`. An empty board (no open roles) is a normal result, not an error.
- **Breezy**: `<slug>.breezy.hr`, e.g. `the-san-francisco-standard.breezy.hr` → `{"ats":"breezy","slug":"the-san-francisco-standard"}`. Breezy publishes structured `country`/`region`/`city` plus a real `is_remote` flag, and a free-text `salary` field is parsed into `salaryMin`/`salaryMax`/`salaryCurrency`/`salaryInterval` when the posting includes one.
- **Rippling**: `ats.rippling.com/<slug>/jobs`, e.g. `ats.rippling.com/findhelp/jobs` → `{"ats":"rippling","slug":"findhelp"}`. Rippling publishes structured `payRangeDetails` (currency/frequency/range per geo tier) on postings where the employer filled it in, so `salaryMin`/`salaryMax`/`salaryCurrency`/`salaryInterval` are filled wherever the board does — it is not in the salary-blind list below.

## Output
One row per job posting:
`company, atsSource, jobId, title, department, team, departmentPath, employmentType, workplaceType, isRemote, location, secondaryLocations, country, region, city, salaryMin, salaryMax, salaryCurrency, salaryInterval, publishedAt, updatedAt, jobUrl, applyUrl, descriptionHtml, descriptionText, scrapedAt`

`descriptionHtml` is the posting body as the ATS serves it, with one exception: inline base64 image payloads are dropped. Some Recruitee boards paste screenshots straight into the job description (one real posting measured 2,436,168 bytes, 99.6% of it a single PNG, against a 6,150-byte median) — the `<img>` tag is kept with the image type and byte count in place of the payload (`src="data-uri-stripped:image/png:2426348"`), so you still see that an image was there without paying storage for it. `descriptionText` is unaffected either way.

### Department and team (changed in 0.1.36)

A Greenhouse job carries exactly one department, and it is the **leaf** of the board's own org tree — on a large board that is an internal cost-centre node, not a department anyone would group by. Measured over **1,909 live postings across 5 boards**, **76% sit at depth ≥ 1** in the tree (up to depth 3 on Stripe: `Tech > Security (Planning Org) > Security (Planning Group) > 8611 Security Analytics`).

Since 0.1.36 this Actor also reads the board-level department endpoint — **one extra request per company, not per job** — rebuilds the chain, and reports:

| Field | Value |
| --- | --- |
| `department` | the **top-level** department (`"Tech"`) |
| `team` | the **leaf** the posting actually sits in (`"8611 Security Analytics"`), `null` when the job is already top-level |
| `departmentPath` | the whole chain root→leaf as an array, `null` on sources with no hierarchy |

The point is cross-company grouping: distinct `department` values on the same live boards collapse from **191 → 4** (Stripe), **44 → 13** (Databricks), **29 → 3** (Airbnb), **17 → 5** (Discord). `team` went from `null` on every Greenhouse row to filled on **76%**.

`departmentKeyword` now matches against `department`, `team` **and** `departmentPath` together, so a filter you wrote against a leaf name before 0.1.36 still matches — the filter got strictly wider, never narrower. If the departments endpoint is unavailable for a board, `department` falls back to the leaf name exactly as before and `team` is `null`. Ashby and Lever expose a real `team` field of their own and are unchanged; Recruitee, Workable, SmartRecruiters and Workday have no team concept and return `null`.

**Workday's board-listing API doesn't carry `department`, `employmentType` or an exact `publishedAt` date** — those only come back from a per-job detail call, which this Actor makes automatically for every kept posting when `includeDescriptions` is `true` (the default) **or when you set a filter that needs one of those fields** (`employmentTypeKeyword`, `departmentKeyword`, `postedAfter`, `postedBefore`, `descriptionKeyword`, `descriptionExcludeKeyword`) — so those filters work on Workday boards even with `includeDescriptions: false`. With descriptions off and none of those filters set, the detail call is skipped for a faster, cheaper-in-wall-clock run and those three fields come back `null` for Workday postings only (every other ATS is unaffected either way). `department` is populated from the posting's hiring organization name (e.g. `"131 DEPARTMENT OF CORRECTIONS"`), which is what Workday boards actually expose in place of a dedicated department field.

### Employment type
**Greenhouse boards never publish an employment type**, so `employmentType` is always `null` on Greenhouse rows and setting `employmentTypeKeyword` drops the entire board (measured: `airbnb`, 163 live postings → **0 rows**, while the same `"full"` filter returns rows on Ashby and Lever). The run logs a warning naming the company when this combination is used. This is an upstream gap, not a fetch this Actor can defer: Greenhouse's public job-board API has no such field. Filter Greenhouse companies on `titleKeyword` (`"intern"`, `"contract"`) or `descriptionKeyword` instead. Ashby (`FullTime`), Lever (`Regular Full Time (Salary)`), Recruitee, Workable and SmartRecruiters all expose it from the listing; Workday and Rippling both expose it only via the per-job detail call described above.

`employmentType` is raw, not a shared vocabulary — each ATS spells "full-time" with a different (or no) separator: Ashby `FullTime` (no separator), Lever `Full-time`/`Full-Time` (hyphen, casing varies by company), Workable `Full-time` (hyphen), Recruitee `fulltime_permanent`/`fulltime_fixed_term` (underscore, lowercase), SmartRecruiters a plain label like `Part-time`/`Intern`. **`employmentTypeKeyword` matching ignores spaces, hyphens and underscores on both sides**, so `"full-time"` (the most natural way to type it) matches all of the above — measured live on `ashby:ramp` (155 postings, all `FullTime`/`Intern`/`Temporary`): before this fix `"full-time"` returned **0 rows** while `"fulltime"` and `"full"` both returned the expected matches, since a bare `.toLowerCase()` never bridged the missing hyphen. If you need to distinguish a specific wording (e.g. permanent vs. fixed-term on Recruitee), filter on a longer, more specific substring instead (`"fixed_term"` or `"fixedterm"` both work).

**What each ATS actually puts in `employmentType`** (measured live 2026-10-10 — ~3,200 postings across 19 real boards; the "values seen" column is exactly what that sample contained, not a vendor-documented list). Separator style is already handled for you; *vocabulary* is not, so this is what you can filter on:

| ATS | Shape | Values seen live (sample) | `"full-time"` | `"contract"` |
|---|---|---|---|---|
| Ashby | closed, camelCase | `FullTime`, `Contract`, `Intern`, `Temporary` (1,112 postings, 3 boards) | ✅ | ✅ |
| SmartRecruiters | closed label | `Full-time`, `Part-time`, `Intern` (104 postings, 3 boards) | ✅ | not seen in sample |
| Workable | closed label | `Full-time` only (7 postings, 1 board — thin sample) | ✅ | not seen in sample |
| Recruitee | code, tenure baked in | `fulltime_permanent`, `fulltime_fixed_term`, `parttime_fixed_term` (13 postings, 1 board) | ✅ | ❌ — use `"fixed-term"` or `"permanent"` |
| Lever | **free text the employer types** | 18 distinct values on 8 boards (1,913 postings): `Full Time Employee`, `Full-time`, `Full Time/Part Time`, `Seasonal`, `Part Time`, `Permanent`, `Internship`, `International EOR`, `Remote`, `Short Term`, `Full Time Contractor`, … (2% `null`) | usually | rarely — varies by board |
| Workday | **closed, two values only** | `Full time`, `Part time` — nothing else | ✅ | ❌ never, on any board |
| Greenhouse | not published at all | always `null` | ❌ | ❌ |
| Breezy | closed label | `Full-Time`, `Contract`, `Temporary`, `Other` (9 postings, 2 boards) | ✅ | ✅ |
| Personio | closed, lowercase snake_case | `permanent`, `intern`, `temporary`, `working_student` (25 postings, 5 boards) | ❌ — use `"permanent"` | ❌ — use `"temporary"` |
| Teamtailor | schema.org field exists, never populated | always `null` (67 postings, 5 boards) | ❌ | ❌ |

| BambooHR | **not a dedicated field — read from `employmentStatusLabel`, which is sometimes a job-open/closed status instead** | `Full-Time`, `Full Time` on 2 of 3 tenants checked; `Active` (a status, not a type) on the third (63 postings, 3 boards — thin sample) | ✅ on tenants that publish a real type; ❌ on tenants whose value is a status word | not seen in sample |

Full write-up of this table, including why we normalise separators but deliberately do not normalise vocabulary: ["full-time" is not a filter](https://fetchsmith.com/blog/ats-employment-type-is-not-one-vocabulary).

Only the Workday row is a claim about the *whole* vocabulary rather than about a sample: Workday publishes its own `timeType` facet, so the full value set is directly readable (see below). For the other ATSes, treat the table as "these definitely exist and definitely match" — a board may use a value this sample never hit.

- **Personio's vocabulary doesn't contain the word "full" or "time" at all** — a permanent, full-time role is just `permanent`, so `employmentTypeKeyword: "full-time"` returns **0 rows** on every Personio board (measured: `ottonova`/`clark`/`orderbird`/`exporto`/`personio` own board, 25 postings, 20 `permanent`). Filter on `"permanent"` instead; `"contract"` also matches nothing — the closest Personio gets to contingent work is `temporary` or `working_student`.
- **Teamtailor's `employmentType` is a real schema.org field the Actor reads, but it was `null` on every one of 67 live postings sampled across 5 boards** (`oatly`, `career.teamtailor.com`, `schibsted`, `doconomy`, plus a confirmed-empty board at `vivino`) — treat it as unavailable on this ATS and filter on `titleKeyword`/`descriptionKeyword` instead, same advice as Greenhouse.

Two of these are worth planning around:

- **Lever's value is not a vocabulary.** It is whatever the employer typed into Lever's "commitment" field, so it carries things that aren't employment types at all (`Remote`, `International Office Entity`, `International EOR`) and splits the same concept four ways across boards (`Full-time` / `Full Time` / `Full Time Employee` / `Permanent`). Filter Lever on a short substring (`"full"`, `"intern"`) rather than an exact phrase, or use `titleKeyword` instead.
- **Workday publishes the contract/intern dimension, but not per posting.** Its `timeType` field — the only employment type on the job detail payload — is a closed `Full time`/`Part time` pair (verified against Workday's own `timeType` facet on three unrelated tenants: 443/81, 2674/2, 1521/14). The classification you probably want (`Regular`, `Temporary`, `Seasonal`, `Intern`, `Contractor`, `Fixed Term`, `Apprentice`) lives in a separate `workerSubType` facet that Workday exposes **only** as a board-level facet — it is absent from both the listing rows and the per-job detail payload, so there is no per-posting value for this Actor to return. Use `titleKeyword` (`"intern"`, `"contract"`) on Workday boards. The run logs a warning naming the board whenever `employmentTypeKeyword` can't match it.

### Location
See [the full write-up](https://fetchsmith.com/blog/ats-location-field-is-not-one-shape) for which platforms are structured vs free text and why `offices[]`/`addressRegion` are both traps, not shortcuts. `location` is always the board's own text. `city`, `region` and `country` are the normalised breakdown, and both `locationKeyword` and `locationExcludeKeyword` match against all four plus `secondaryLocations` — so `locationExcludeKeyword: "United States"` drops a Greenhouse posting whose text only reads `"San Francisco, CA"`, and `locationKeyword: "California"` keeps it. Measured on the 163 live `airbnb` postings: `locationKeyword: "California"` returns **15** rows, only **1** of which says "California" in the board's own text.

Ashby, Lever, Recruitee, SmartRecruiters, Workable and **Breezy** publish structured geography, so it is passed straight through. **Greenhouse publishes none** — it has a single hand-typed string per posting, and the same board mixes `"United States"`, `"San Francisco, CA"`, `"Bengaluru, India"`, `"Remote - Texas"` and `"Northeast - United States"`. This Actor normalises that string against a country/state/city vocabulary: measured over 1,914 live postings (`airbnb`, `databricks`, `figma`, `stripe`, `discord`, September 2026) it fills `country` on **95%**, `city` on **67%** and `region` on **50%**.

**Breezy's `city`/`region`/`country` come from real structured fields** (`location.city`/`location.state.name`/`location.country.name`), not text-parsed — measured on the 2 live boards found with postings (`the-san-francisco-standard`, `breezy.breezy.hr`'s own demo tenant, 9 postings): all 9 filled `country`, `region` and `city` with no `null`s. **Teamtailor's `city` comes from its embedded schema.org `jobLocation[].address.addressLocality`, also structured**, but `region` is deliberately left `null` — measured across 5 live boards (67 postings: `oatly`, `career.teamtailor.com`, `schibsted`, `doconomy`, plus confirmed-empty `vivino`), the underlying `addressRegion` field is missing on **49%** (33 of 67, e.g. every `schibsted`/`doconomy` posting) and, on the 51% where it is populated, it's either a continent name (`"North America"`, `"Oceania"`, `"Europe"`) or a repeat of the country itself (`"United States"`, `"Sweden"`, `"Germany"`) — never a real state/province, so shipping it as `region` would mislabel it either way. **Personio's only location field (`office`) is free text, same shape as Greenhouse**, and reuses the same `parseLocation` normaliser: across the same 25-posting, 5-board sample used for employment type above, `country` and `city` each filled on **76%** (19 of 25) and `region` on **0%** (none of these boards' office strings carry a state/province token for the normaliser to match). The misses are real German place names the normaliser's vocabulary doesn't cover — `"Singen am Hohentwiel"`, `"Konstanz"` and the field-sales label `"Außendienst Köln"` ("field sales Cologne," which doesn't match on the embedded city name either) all come back `null` rather than a guess, plus the literal placeholder `"Remote"`.

**Workday** publishes no geography in its list payload either — just one text field per posting, written differently by every tenant (`"US, CA, Santa Clara"`, `"France - Paris"`, `"Canada, Toronto"`). The same normaliser runs on it, so Workday rows now carry `city`/`region`/`country` instead of the nulls they returned before. Measured over 800 live postings (`nvidia`, `salesforce`, `adobe`, `okgov`, September 2026): from the list payload alone `country` fills on **35%**, `city` **22%** and `region` **14%**; when `includeDescriptions` is on, the per-job detail call adds Workday's one structured field and `country` reaches **100%** (its spelling `"United States of America"` is normalised to `"United States"` so it groups with every other source). The detail call also resolves multi-site postings the list shows only as `"3 Locations"`, which is where most of the extra `city`/`region` comes from. The practical effect on filtering: `locationKeyword: "United States"` matched **0** of those 800 Workday postings before and matches **89** now; `"California"` goes from **6** to **70**.

**Fixed in 0.1.39:** on county-government boards where the list text has no place name at all (`okgov`'s `"Muskogee County"`, `"Craig County"`, ...), `locationKeyword`/`locationExcludeKeyword` used to be checked before the per-job detail call that resolves `country`, silently dropping every one of those postings even though the resolved value would have matched. Measured live on `okgov`: `locationKeyword: "United States"` went from **0 of 10** to **10 of 10**, with `locationExcludeKeyword: "United States"` now correctly complementary (0 kept). Billing unchanged (1 `job` event per returned row).

**Re-measured after the fix (September 2026), and the "89 of 800" figure above is now a floor, not current:** a fresh live pull of `nvidia` (list text already parseable, unaffected by the bug) and the full visible `okgov` board (60 of 60 postings, not just the earlier 10-row sample) matched `locationKeyword: "United States"` on **101–102 of 120 postings (≈84%)**, run twice a minute apart (live boards drift slightly). The county-government board alone went from the old code's **0 of 60** to the fixed code's **60 of 60** — the earlier 10-row proof generalizes to the whole board, not just the sample.

Anything the vocabulary does not recognise stays `null` rather than being guessed, because a wrong country is worse than a missing one. In practice that means: multi-country zones (`"EMEA"`, `"APAC"`), placeholders (`"N/A"`, `"Remote"`), internal abbreviations some boards use for their own offices (`"SF"`, `"CHI"`, `"ATL"`), and the bare token `"Georgia"`, which is equally the US state and the country. Where a posting lists several places, the fields describe the **first** one and the rest stay in `secondaryLocations`. Greenhouse's `offices[]` array is deliberately **not** used to fill these fields: on some boards it contradicts the posting outright (a `databricks` posting located in `"Finland"` carries a `"Denmark"` office), so trusting it would invent wrong answers. The same restraint applies to Workday: its `"3 Locations"`/`"8 Locations"` placeholders, `"Statewide"`, county names (`"Tulsa County"`) and the street addresses some tenants put in the detail location (`"Stringtown - 13001 N Highway 69"`) all stay `null` rather than becoming a bogus city.

### Salary
Pay is returned when the board itself publishes it, and left `null` otherwise rather than guessed — **Ashby**, **Lever**, **Recruitee** and **Rippling** expose structured pay ranges in their APIs (Rippling's `payRangeDetails` is per geo tier — the Actor picks the tier matching the posting's own remote-ness when more than one is published, never averaging or summing across tiers), and **Greenhouse** boards with pay transparency switched on render the range as a structured block in the posting itself, which this Actor reads. **BambooHR** publishes pay as a short employer-typed free-text string on the per-job detail call ("$50,000-$80,000 per year", "$18-$22 Hourly DOE", "$100k - $150k"), not a structured field — this Actor extracts the figures and period from it the same way it does for Workday's prose below, with one BambooHR-specific wrinkle: a bare `k` suffix means thousands (`"$100k"` → `100000`). **Workday** has no salary field in its API either, but under pay-transparency law many employers write a real pay figure straight into the free-text job description, and this Actor parses it: it anchors on a labeled pay phrase the board itself printed ("Compensation", "Salary", "Pay Range", "expected base salary range", "annual rate of", "hourly rate" — never a bare `$N`, which on Workday boards is just as often a sign-on bonus, benefits allowance or shift differential as real pay), and reports the widest span across every qualifying figure (a posting with per-level or per-city pay bands can genuinely pay anywhere in that outer range). Measured on 50 live postings across 5 tenants: 24/24 correct where any pay figure was present, 26/26 correctly `null` where none was, zero false positives from the bonus/allowance/differential text sharing the same description. Workable and SmartRecruiters carry no compensation data through any standard field, so `salaryMin`/`salaryMax` stay `null` on those two — SmartRecruiters' one documented exception is a freeform, per-company `customField` that genuinely carries pay text on one real board checked, not parsed here since the field's label and format are admin-configured and not part of the API's contract (see the [SmartRecruiters deep-dive](https://fetchsmith.com/blog/smartrecruiters-job-board-json-api)).

Coverage measured on live boards (September 2026): Ashby `ramp` 141/148 postings, Greenhouse `airbnb` 139/166, `databricks` 472/874, `figma` 99/152. Greenhouse boards that never turned pay transparency on (`stripe`, `discord`) return `null` — there is nothing in their payload to read.

Two Greenhouse specifics worth knowing. **The currency comes from the ISO code the board prints, not from the symbol** — 17 of airbnb's ranges pay in CAD and still show `$`, so reading the symbol would mislabel them USD; where a board prints a bare `$` with no code, `salaryCurrency` stays `null` instead of guessing. **A salary printed in prose is not parsed** — only Greenhouse's structured pay block is read, so a sentence like "the base salary range for this position is $196,000 to $220,500" buried in the description is left alone rather than risk picking up some other number from the text.

`salaryMin`/`salaryMax` are also filled on Greenhouse when `includeDescriptions` is `false` — the pay block is read out of the payload either way, so switching descriptions off to save bandwidth does not cost you the salary.

`salaryInterval` says what the number actually means — `year`, `month`, `week`, `day` or `hour`. Each ATS spells its period differently (`1 YEAR`, `monthly`, `per-year-salary`); they are normalized to one vocabulary so an hourly rate and an annual salary are never silently compared.

## Watch mode (only new postings since last run)
Set `watchLabel` to any name you like (`"backend-remote-eu"`) and the run stops returning the whole open-roles list every time and starts returning **only the postings that appeared since the previous run under that label**. This is the job-alert shape: schedule it hourly or daily and each run's dataset is your diff.

- **The first run for a label is a free baseline.** It records which postings are currently open (up to 5,000), returns **zero rows** and charges **nothing**. Run it again later to get what's new.
- **Already-delivered postings are dropped before any charge**, so a run with nothing new costs you nothing.
- **The baseline lives in your own Apify account** — a named key-value store `fetchsmith-ats-watch`, key `watch-<label>-<fingerprint>`. Nothing is kept on our side.
- **The fingerprint covers the company list and every filter** (`titleKeyword`, `titleExcludeKeyword`, `locationKeyword`, `locationExcludeKeyword`, `employmentTypeKeyword`, `hasSalary`, `remoteOnly`, `postedAfter`, `includeDescriptions`, plus `departmentKeyword`, `descriptionKeyword`, `descriptionExcludeKeyword`, `postedBefore`, `minSalary` and `maxSalary` when you set them). Change any of them and you get a fresh baseline instead of a dump of postings the old filters had excluded. `maxJobsPerCompany`/`maxResults` are *not* in the fingerprint — they are cost caps, not criteria.
- **`maxJobsPerCompany` caps what is delivered, not what is checked.** In watch mode the run scans the whole match set for each company (so a new role that sorts 40th is still found) but still delivers at most `maxJobsPerCompany` new postings per company per run; the rest arrive on the following run.
- **Baseline size cap:** the recorded baseline holds at most 20,000 posting ids per label; once a label crosses that, the oldest ids are dropped to make room. A dropped id is re-delivered — and re-charged — as "new" on a future run. This only bites a very broad, unfiltered watch on a long company list; narrowing `titleKeyword`/`locationKeyword` or trimming `companies` keeps a label well under the cap. A run that actually drops ids logs a warning and says so in its status message.
- **`closed` tells you a role you were tracking came down — "was that req filled or pulled?"** Tick `closed` in `watchEvents` and the run also reports every posting this label had already delivered that is no longer on its board at all, as `watchEvent: "closed"`. It is **opt-in on purpose**: leaving `watchEvents` empty keeps the old `new` + `salaryAdded` behaviour exactly, so an existing watch never starts billing for a new row class by itself. Closed rows are charged at the same per-posting rate as any other row. Three things to know before you rely on it. **(1) It is deliberately conservative about incomplete boards.** A board that errors, 404s, returns no postings at all, returns only part of itself (a page that failed after retries) or gets truncated by a cap is **never diffed**, because a board read short is indistinguishable from one whose roles all closed at once — that case is logged per board and counted in `watchClosureBoardsSkipped` in the `webhookUrl` payload, next to the `watchClosureBoardsChecked` boards that were diffed. A false closure would bill you for a posting that is still open, so the bias is always towards saying nothing. **(2) "Closed" means gone from the board, not "stopped matching your filters."** The diff runs against the board listing itself, so a posting that is still published but drifted out of your `titleKeyword`/salary/location filters is *not* reported as closed. **(3) A closed row carries its `company`, `atsSource` and `jobId`/`jobUrl`, with the other fields `null`** — the posting is gone, so there is nothing left to re-read; `previousHasSalary` carries the salary state recorded the last time the posting was delivered. A delivered closure is dropped from the baseline, so if the same posting is re-published later it correctly arrives again as `new`.
- **`watchEvents` picks which kinds of change get delivered.** By default (empty) a watch reports both a brand-new posting and an already-delivered posting that gained a salary since you last saw it (`watchEvent: "new"`/`"salaryAdded"`, with `previousHasSalary` on the changed row). Greenhouse, Ashby, Lever and Recruitee postings commonly publish without a salary and add one later under the same posting id — a pay-transparency add-on or a plain edit — and without this event that edit was invisible to a watch forever; SmartRecruiters/Workable/Workday never carry a salary, so `salaryAdded` simply never fires on those. Pick just `["salaryAdded"]` to be alerted only on that and never pay for a brand-new posting. `salaryAdded` only starts firing on the run *after* a baseline recorded before this feature existed — the run that upgrades an old baseline has nothing to compare a salary against yet.
- **Never pin a watch to `postedBefore`.** A newly-published posting's `publishedAt` is its own post time, so once today's real date passes a fixed `postedBefore`, nothing new can ever fall on or before that cutoff again — the watch goes permanently quiet while still reporting a healthy "nothing new" every run. A run in that state logs two warnings and sets `watchDeadDateBound: true` in the `webhookUrl` payload. `postedAfter` alone is safe to keep in a watched query; it only trims old postings, it never excludes new ones.

## FAQ
**How do `titleKeyword`, `locationKeyword`, `descriptionKeyword`, `remoteOnly` and the date bounds combine?** All of them must pass (AND) — set only the ones you need, leave the rest empty/`false`.

**Can I filter on the description without paying for description columns?** Yes. `descriptionKeyword`/`descriptionExcludeKeyword` work with `includeDescriptions: false`: the text is fetched, matched against your keyword, then stripped from the row, so you get lean rows filtered on their full body text.
**What if `companies` has the same `{ats, slug}` entry twice?** Deduped automatically — an exact repeat is only fetched (and charged) once per run.

**A watch already delivered this posting once — why is it back?** Because its salary changed. Watch mode diffs an already-delivered posting's salary state against what was recorded last time, not just its id — a posting that publishes without a salary and later adds one (common on Greenhouse/Ashby/Lever/Recruitee under pay-transparency rules) comes back once as `watchEvent: "salaryAdded"`, with `previousHasSalary: false` on the row, and is charged like any other delivered posting. Set `watchEvents: ["new"]` if you only ever want brand-new postings and never a salary-change re-delivery.

**My watch says "nothing new" every single run — is it broken?** Check whether you set `postedBefore`. A watch combined with a fixed upper date bound is a dead end: every brand-new posting is dated "now", so once the calendar passes your cutoff no new posting can ever satisfy it again, and the run honestly reports zero new rows forever. Such a run now logs two warnings and sets `watchDeadDateBound: true` in the `webhookUrl` payload so a scheduled watch can alert on it instead of trusting the quiet. Fix it by removing `postedBefore` from the watched query — keep `postedAfter` if you want a floor — or drop `watchLabel` if you genuinely wanted a one-off historical window rather than an ongoing watch. (Changing the filter starts a fresh free baseline, since `postedBefore` is part of the watch fingerprint.)

**What happens if a board has a transient connection blip mid-run?** Every ATS request (Greenhouse, Ashby, Lever, Recruitee, Workable, SmartRecruiters and Workday, including Workday's paged listing calls) is retried up to 3 times on a connection-level failure — measured at roughly 1 fresh request in 4 for HTTP/2 faults, 2026-09-21 — before that company is marked errored in the completion summary. A single blip no longer costs you that company's whole board.

**Does `maxJobsPerCompany` cap before or after my filters run?** After. Filters are applied first, then up to `maxJobsPerCompany` of the *matching* postings are kept per company — so `{"titleKeyword": "engineer", "maxJobsPerCompany": 3}` returns 3 postings that actually contain "engineer", not the first 3 raw postings off the board (verified live: a real Greenhouse board run with those exact inputs returned 3/3 titles containing "Engineer"/"Engineering").

**Date bounds: both ends inclusive, and a bad date stops the run.** `postedAfter` starts at 00:00:00.000 UTC on the day you name and `postedBefore` ends at 23:59:59.999 UTC on the day you name, so `postedAfter: "2026-08-01"` + `postedBefore: "2026-08-31"` is exactly August — no posting is trimmed off either end. Both accept `YYYY-MM-DD` or a full ISO datetime (`2026-08-01T12:00:00Z`) and **nothing else**: `06/15/2026`, `2026-8-1`, `last week` and calendar-impossible dates like `2026-02-30` fail the run with an error naming the input. That is deliberate. This Actor charges per posting, and the obvious alternative — parse what we can, ignore the rest — means an unreadable bound silently *deletes* your date filter and hands you (and bills you for) the entire unfiltered board. A filter that can't be honoured should stop the run, not quietly widen it.

**Will `postedAfter`/`postedBefore` filter out a posting that has no date?** No — if an ATS doesn't return a `publishedAt` for a posting, that posting is kept regardless of the date bounds. On Workday the date comes only from the per-job detail call, and setting either bound now triggers that call automatically, so the window applies to Workday boards too.

**Which ATSes expose salary?** Ashby, Lever and Recruitee publish a structured pay range in their API, and Greenhouse boards with pay transparency on print one in the posting body, which this Actor parses (139/166 postings on a live airbnb board, 472/874 on databricks). **Workday** has no salary field either, but this Actor parses a real pay figure out of the free-text job description when the employer printed one under pay-transparency law (24/50 postings filled, zero/zero false positives, measured across 5 tenants — see Salary above), so `hasSalary`/`minSalary`/`maxSalary` work on Workday boards too. Workable and SmartRecruiters carry no compensation data through any standard field, so `salaryMin`/`salaryMax` come back `null` on those two — see the [SmartRecruiters deep-dive](https://fetchsmith.com/blog/smartrecruiters-job-board-json-api) for the one real, narrow exception found on a single board's freeform custom field; `descriptionKeyword` can still find pay text there.

**Does `minSalary`/`maxSalary` compare against an annual salary?** Not necessarily — it compares the raw number as the ATS posted it, in whatever `salaryInterval` that posting uses (year, month, week, day or hour all appear in the wild). Mixing companies on very different intervals in one run means the filter isn't apples-to-apples; check `salaryInterval`/`salaryCurrency` on each row if that matters to you.

**A company I need isn't on any of these 12 ATSes — can it still be scraped?** Only if it uses one of the 12 (or a client-side board no ATS API backs, which this Actor can't reach). Message support@fetchsmith.com with the company's careers URL if you're unsure which ATS it runs on.

**I set `watchLabel` and got zero results — is it broken?** Usually not: either it was the baseline run (the log says so explicitly, and you were charged nothing), or nothing new has been posted on those boards since your last run. For a watch, zero is the normal, expected, free result most of the time. **Read the run's status message to tell the two apart from a real problem** — a misspelled board slug or a filter that matches nothing produces a zero-result run that looks exactly the same every time, so the status message names those causes explicitly ("Why you got nothing: ...") instead of calling it normal. If it says nothing is wrong, nothing is wrong.

**How do I reset a watch baseline?** Delete its record from the `fetchsmith-ats-watch` key-value store in your Apify account, or just use a new `watchLabel`. Changing any filter also starts a fresh baseline automatically.

**One of my boards failed during the baseline run — what happens?** That board contributes nothing to the baseline, so its currently-open postings will come back as "new" (and billable) on the next run. The baseline run logs a loud warning naming any board that failed, so you can re-seed before scheduling it.

**Why did a company I listed return zero postings?** Either it's genuinely down to 0 open roles, or it has migrated off that ATS — the run logs (not a failure) list any company that 404s so you can find its new slug/ATS instead of getting a silently empty result.

**I listed several companies and one of them is missing from the result, with no error for it at all — why?** It's almost certainly `maxResults`: companies are fetched in the order you list them, and once `maxResults` is reached the run stops immediately — any company after that point in the list is never fetched, never checked, never 404'd, just skipped outright. That's different from "not found" or "fetch error", so it gets its own line in the status message naming exactly which companies were skipped and why (e.g. `"1 of the 2 compan(ies) you listed (greenhouse:thisdoesnotexist98765xyz) were never checked at all, because 'maxResults' (5) was already reached..."`). Fix: raise `maxResults`, put the companies you care most about earlier in the list, or split a long list into several runs.

**One slow company used to cost me all the others. Does it still?** No — fixed in 0.1.122. Companies are fetched one after another against a single run time budget, so a board that hangs instead of answering (unreachable host, dead proxy tunnel) used to be able to spend the whole budget on its own retries and leave every company after it in the list unfetched. Measured on a 180-second run with the first company pointed at a black-holed host: the second company, a healthy board that answers in about a second, was never asked and the run returned **0 postings**. Now each company that has not been tried yet holds back a reserve of the remaining time (never more than half of what is left, so the company being fetched is not starved in turn), and the same forced test returns the healthy board's postings instead. Either way the status message names what happened — a board that failed to answer, or a company stopped early to protect the rest of your list — so an incomplete result is never silent. If you routinely list many companies, raising the run timeout is still worth it: the reserve shares the time you give it, it cannot create more.

**How is `webhookUrl` different from Apify's own platform webhooks?**
Apify's platform webhooks are configured separately per Task/Actor via the Console or the Webhooks API — useful if you already live in the Apify Console, but extra setup if you're calling this Actor's API directly and just want a completion ping. `webhookUrl` is a plain input field: set it on the run itself and it POSTs a JSON body (`actorRunId`, `defaultDatasetId`, `finishedAt`, `pushed`, `companiesScanned`, `companiesErrored`, and — if `watchLabel` is set — `watchSeeding`/`watchNewCount`/`watchSkippedCount`/`watchEvents`/`watchChangedCount`/`watchEventsFilteredCount`/`baselineTruncated`/`baselineTruncatedTotal`) once the run finishes and every posting is already pushed and charged. Especially useful with `watchLabel` on a scheduled job alert: your endpoint gets told how many new postings landed without polling the dataset, and `companiesErrored` warns you when a board failed to answer. It's best-effort — a slow or failing webhook only logs a warning, it never fails the run, changes the result set, or affects billing.
