# SAM.gov Scraper – US Federal Procurement, Contracts, Bids, Wage Determinations & Grants

Scrape live US federal contracting opportunities from SAM.gov — presolicitations, solicitations, combined synopses, sources sought, special notices and award notices — with **no API key, no login, no proxy and no browser**. Filter by keyword, NAICS code, set-aside type, notice type, place-of-performance state and issuing organization, and optionally enrich every row with the contracting officer's contact details, NAICS codes, set-aside and place of performance.

In short: a federal RFP data API and an organization-only Excluded Parties List check in one keyless Actor — the same run lists open solicitations and tells you whether a firm is debarred.

## What it does
- **Six public SAM.gov datasets, one Actor, no key.** `dataType` picks which one: `opportunities` (default — solicitations, presolicitations, sources sought, awards), one of three Department of Labor wage-determination sets SAM.gov publishes — `wage-determinations-dbra` (Davis-Bacon Act, construction), `wage-determinations-sca` (Service Contract Act, services) and `wage-determinations-cba` (collective bargaining agreements) — `assistance-listings`, the Catalog of Federal Domestic Assistance (CFDA) grant/loan/direct-payment programs, or `exclusions`, the federal debarment/suspension list (organizations only — see below). All six come off the same keyless public search backend, so none of them needs a registered API key.
- Calls the same backend that powers sam.gov's own public opportunity search page, so results match what you see on the site. **SAM.gov's official developer API (`api.sam.gov/opportunities/v2`) requires a free registered API key — this Actor needs none.** You do not have to register with GSA, wait for key approval, or rotate a key across a team.
- **`enrichDetail` joins each row with the per-opportunity record**, which is where the fields a bidder actually qualifies on live: `naicsCodes`, `setAside`, `placeOfPerformanceState`/`placeOfPerformanceCountry`, and `pointOfContact` (the contracting officer's name, email and phone, primary and secondary). None of these are on the search row. Off by default because it costs one extra HTTP call per row; turn it on when you are qualifying, not just listing.
- **Multi-value filters really OR.** `naicsCodes: ["541511", "541512"]` returns the union of both, not just the first. This is worth stating because SAM.gov's backend silently accepts a repeated query parameter and then honours only the first value — verified live: `naics=541511` → 607 hits, `naics=541512` → 312, repeated-key form → 607 (wrong, and no error), comma-joined form → exactly 919. This Actor sends the comma-joined form for every multi-value filter (`naicsCodes`, `setAsideTypes`, `noticeTypes`, `states`), so a two-code search does not quietly drop half your pipeline.
- **`noticeTypes` uses SAM's own notice-type codes** — `p` presolicitation, `o` solicitation, `k` combined synopsis/solicitation, `r` sources sought, `a` award notice, `s` special notice, `g` sale of surplus, `i` intent to bundle, `u` justification. Every row also comes back with both the raw `noticeTypeCode` and the human-readable `noticeType`. Four more codes exist in SAM.gov's historical data but are no longer issued and don't appear in SAM's own current UI dropdown — `m` modification/amendment/cancel, `f` foreign government standard, `j` justification and approval (J&A), `l` fair opportunity/limited sources justification (all retired 2019-2020, ~97k rows fleet-wide, live-verified cycle 835). Useful for historical research; leave them out for a current-solicitations pipeline.
- **`setAsideTypes` takes SAM.gov's own set-aside codes, and this Actor fixes the case for you.** The full vocabulary, each value live-verified non-zero against the opportunity index on 2026-09-30: `SBA` total small business, `SBP` partial small business, `8A` 8(a) competed, `8AN` 8(a) sole source, `HZC` HUBZone competed, `HZS` HUBZone sole source, `SDVOSBC` service-disabled veteran-owned competed, `SDVOSBS` SDVOSB sole source, `WOSB` women-owned, `WOSBSS` WOSB sole source, `EDWOSB` economically-disadvantaged WOSB, `EDWOSBSS` EDWOSB sole source, `LAS` local area set-aside, `IEE` Indian economic enterprise, `ISBEE` Indian small business economic enterprise, `BICiv` Buy Indian, `VSA` veteran-owned competed, `VSS` veteran-owned sole source. SAM.gov's backend matches these **case-sensitively and fails closed**, so before this was handled `setAsideTypes: ["sba"]` returned zero rows on the largest set-aside category in the index (1.2M opportunities) with no error to tell you why — measured live: `SBA` → 1,204,971 hits, `sba` → 0. This Actor now canonicalises the case, so `sba`, `SBA` and `Sba` are the same query. Note that upstream is *not* uniformly uppercase — `BICiv` really is mixed-case (`BICiv` → 4,498 hits, `BICIV` → 0), which is why this is a code lookup and not a blanket upper-casing. The umbrella names buyers actually say — `8(a)`, `SDVOSB`, `HUBZone` — are accepted too and expand to the real code(s) they cover (`SDVOSB` → `SDVOSBC` + `SDVOSBS`, since SAM.gov splits competed from sole-source and "SDVOSB" means either). Any value that is not a code or an alias is still sent as-is, which is safe — SAM.gov fails closed on it, so it matches **zero** rows rather than silently widening your search to the unfiltered index — and the run logs a warning naming the value and listing the valid codes.

  **Re-audited both directions on 2026-10-10**, which is how the list above got three values it was missing. Every prior pass only checked *our* codes against SAM.gov (all 18 still return rows, nothing dead, counts up only by natural growth: `SBA` 1,204,971 → 1,206,126). The reverse direction — what SAM.gov accepts that we never listed — had never been run, because SAM.gov publishes no set-aside reference endpoint to read (re-confirmed: no `facets`/`aggregations` on the search response, `locationservices/v1/api/setasidetypes` 500s, every other guessable path 404s). So it was derived empirically instead: 1,500 live opportunity rows sampled across the index for the set-aside code each row carries itself, plus a brute-force probe of the entire 1- and 2-character code space (1,332 values, of which only `8A` is real — so that space is now closed). Three real, filterable codes turned up, all of them previously reported to you as typos:
  - **`setAsideTypes: ["NONE"]`** — SAM.gov's explicit *unrestricted / no set-aside* tag. **38,997 opportunities, 3,349 of them active**, newest modified the day of the audit, so this one is live and useful. Note what it does and does not mean: it **narrows** your search to opportunities SAM.gov tagged `NONE` outright, and is **not** the same as leaving `setAsideTypes` empty — the millions of unrestricted opportunities that carry no set-aside field at all are not in it. The run logs that distinction when you use it.
  - **`setAsideTypes: ["SDB"]`** (Total Small Disadvantaged Business, 464 rows, newest modified 2019-06-27) and `setAsideTypes: ["ESB"]` (Emerging Small Business, 714 rows, newest 2020-01-20) — retired programs with **zero active opportunities**, the same historical-only class as the legacy `m`/`f`/`j`/`l` notice types below. Nothing has posted under either since 2020, so they are for research, not for a bid pipeline; they are supported because those rows are otherwise unreachable through this filter. The run logs a note when you use them.
- **`states` filters on place of performance, not the issuing office.** SAM's official API calls this `state`; on this backend that parameter name is silently ignored and returns zero rows, a trap this Actor sidesteps by sending `pop_state`.
- `activeOnly` (default on) restricts to opportunities still open for response. Turn it off for historical and award research.
- Pay per result: charged only for rows actually returned, **with no Actor-start fee** — a search that matches nothing costs nothing.
- **`watchLabel` — only what's new since your last run.** Name a saved search and every run after the first returns just the opportunities not already delivered under that label and filter combination. The first run for a label is a free baseline (0 results, 0 charged); it records what already matches in a key-value store on your own Apify account, keyed by the label plus a fingerprint of your other filters, so editing a filter starts a fresh baseline instead of dumping every previously-excluded opportunity as "new". Built for a daily/weekly scheduled run.
- **`postedFrom`/`postedTo` and `deadlineFrom`/`deadlineTo` — real two-sided date windows, and you are not charged for what they drop.** SAM.gov's search backend has no date-range parameter at all (which is why most Actors on this index make you post-process the whole result set yourself, paying for every row you then throw away). This Actor applies the window after fetching each row and **before pushing or charging it**, so a window is free narrowing: `deadlineFrom` set to today gives you only opportunities you can still bid on, `postedFrom`/`postedTo` gives you one quarter's postings, and the rows outside never appear on your bill. Both ends are inclusive and compared on the calendar date the notice itself carries, never re-zoned. Honest trade-off: because the filtering is ours and not SAM.gov's, the window does **not** reduce what is read upstream — a narrow window over a broad keyword still walks the full match set, so keep your keyword/NAICS filters narrow too, and read `dateWindowDropped` in `RUN_SUMMARY` (plus `declaredMatches`, which stays SAM.gov's pre-window count) to see exactly what the window removed.
- **`solicitationNumber` — exact-match lookup, not a keyword guess, now with a one-request fast path.** Give it a real solicitation number (dashes/spaces optional, matching is case-insensitive) and the run drops every fetched row whose own solicitation number isn't an exact match **before pushing or charging it** — the same pre-charge placement as the date windows above. Searching by `keyword` alone can false-positive on a number that merely appears in a title or description; this field matches the number the row actually carries. SAM.gov's search backend silently ignores a `solnum`-style parameter (confirmed live), but it does honour `notice_id` as an exact, case-sensitive, raw-punctuation match on the solicitation number — this Actor tries that first (one probe request), and when your value matches, the whole run completes in a single page instead of walking the broader keyword search; when it doesn't, it falls back automatically to sending the value as the search keyword and walking, same as before. Opportunities only.
- **`minAwardAmount`/`maxAwardAmount` — a real dollar range on award notices, and you are not charged for what it drops.** SAM.gov's search backend only supports an exact award-amount match (`award_amount=<n>`) and rejects every range syntax with HTTP 400, so this is applied the same way as the date windows above: after fetching each row, before pushing or charging it. `award.amount` is null on every notice that hasn't been awarded yet, so pair this with `noticeTypes: ["a"]` or most fetched rows will be dropped as having nothing to compare (read `awardAmountMissing` in `RUN_SUMMARY` to see how many). Opportunities only.
- **`includeIncumbentAwards` answers the question you actually have about a notice: who holds this work today?** For each opportunity's NAICS code it attaches the top 3 US federal contract awards by dollar value from **USAspending.gov** as `incumbentAwards` — recipient name and UEI, amount, start and end dates, awarding agency, and a usaspending.gov link — matched on NAICS and, where the issuing department maps to one of USAspending's top-tier agency names, on agency too (every row's `incumbentAwardsMatchedBy` tells you which of the two it got). **Not billed separately: no extra per-result charge.** Two things worth knowing, both reported in `RUN_SUMMARY`: NAICS codes are not on SAM.gov's search row, so this turns `enrichDetail` on automatically (one extra request and ~200 ms per row, and you get the contact/set-aside/place-of-performance fields along with it); and `incumbentYears` is matched against each award's **last-modification date, not its start date**, so a long-running contract that began before your window but was recently modified is included — intentionally, because it is still the incumbent, and every award carries both dates so you can tell. Lookups are deduped per unique NAICS+agency pair, so 200 opportunities spread across 5 NAICS codes cost 5 USAspending requests, not 200.
- **`description` is the full solicitation text**, not a truncated snippet — the same original HTML SAM.gov itself stores, which can run to several thousand characters on a detailed notice.
- **`includeAttachments` lists each notice's files — drawings, full statements of work, forms — with a direct, no-login download URL for each.** One extra HTTP call per row, off by default. Every link is SAM.gov's own stable file-download path, not a short-lived signed URL, so it works whenever you actually click it, not just at scrape time. Export-controlled and sign-in-required attachments are excluded from the list — this Actor never hands you a link that 403s or bounces to a SAM.gov login, so every URL you get back actually works with no account. A notice with genuinely no files returns `attachments: []`; a failed lookup returns `null` and is reported in `RUN_SUMMARY`, so the two are never confused.
- **`watchChanges` — also catch a deadline extension, a lifecycle transition, or an award landing.** Add this to `watchLabel` and an opportunity you already have gets re-delivered (at the normal per-row price, tagged `_watchChangeType`/`_watchPrevious`) if its `isActive` flag, `noticeTypeCode` (a presolicitation turning into a solicitation, or a solicitation turning into an award), `responseDate` (deadline moved), `modifiedDate`, `modificationsCount` or `awardeeName` (an award landing) has changed since you last saw it — not just brand-new opportunities. Off by default so existing watches keep their current behaviour. **Don't combine it with `activeOnly` (on by default!) or `noticeTypes`** — see the FAQ "don't filter on the field you're watching".

## Wage determinations
Set `dataType` to one of the three wage-determination options and the same filters you already know (`keyword`, `states`, `activeOnly`, `maxResults`, `watchLabel`, `watchChanges`, `webhookUrl`) apply to Department of Labor determinations instead of solicitations.

| `dataType` | What it returns | Live record count |
|---|---|---|
| `wage-determinations-dbra` | Davis-Bacon Act determinations — construction, with `constructionTypes` (Building / Heavy / Highway / Residential) | ~85,400 (~4,200 active) |
| `wage-determinations-sca` | Service Contract Act determinations — services, with a `services[]` list of covered categories | ~2,700 (~1,500 active) |
| `wage-determinations-cba` | Collective bargaining agreement determinations | ~107,600 (~10,100 active) |

- **Coverage is normalized across all three.** SAM.gov returns the covered geography in three different shapes (DBRA nests a single `location.state`, CBA an array of `location.states`, SCA an array whose counties split into `include`/`exclude` lists). Every row here carries the same flat `coverage` array of `{ stateCode, stateName, isStateWide, counties, excludedCounties }`, plus `stateCodes` and `countyCount` for filtering. SCA's *excluded* counties are kept in their own field rather than merged into the covered list — an excluded county is the opposite of a covered one.
- **Dates are normalized too.** `publishDate` comes back as an ISO string on CBA rows but as epoch milliseconds on DBRA/SCA rows; this Actor emits ISO 8601 for every row so you are not parsing two formats.
- **`states` filters on the state the determination covers**, and multiple states OR together the same way: measured live, `AL` → 3,509 and `TX` → 6,909 CBA determinations, `["AL","TX"]` → 10,415 (the 3 determinations covering both states are returned once, not twice).
- **`activeOnly` means "currently in force"** — a determination superseded by a later revision has `isActive: false`. Combine with `watchLabel` + `watchChanges` and a run tells you when a determination you track is revised (`revisionNumber` moves) or goes inactive.
- **`keyword` searches the reference number, not trades.** On these indices `q` matches the determination's own number (e.g. `AK20260001`), so `q=roofing` returns zero against 85,000+ live Davis-Bacon records. Filter by state and construction/service type instead, and leave `keyword` empty to get the whole set. **The exact-match behavior is also narrower than it looks** — a complete reference number matches exactly one row, but adding so much as a space silently switches the query to an OR across every token, so `q=AK 20260001` returns the 106 determinations that merely start with `AK`, not the 1 you asked for, with no error either way. See [the full measurement](https://fetchsmith.com/blog/sam-gov-wage-determination-keyword-matches-reference-number-not-trade) — this is why `keyword` defaults to empty on every wage-determination run from this Actor rather than passing a caller's value straight through.
- **What this does NOT include: per-occupation hourly wage rate tables.** SAM.gov does not publish the rate schedule on any of the three search indices, so every row has `wageRates: null`. This Actor gives you the determination *index* — which determination applies to which state and counties, its revision number, its construction/service scope and whether it is current — which is what you need to pick the right determination; read the rates themselves from the determination's own page on sam.gov.
- `naicsCodes`, `setAsideTypes`, `noticeTypes`, `organizationId`, `enrichDetail` and `includeAttachments` are opportunity-only. If you set one in a wage-determination run it is ignored and the run logs a warning saying so, rather than silently returning an unfiltered set that looks filtered. `includeIncumbentAwards` is opportunity-only too, but it **stops the run** instead of being ignored: a wage determination or exclusion record carries no NAICS code, so there would be nothing to match an incumbent award on, and every delivered row would be billed with an empty `incumbentAwards`.

### Example wage-determination input
```json
{
  "dataType": "wage-determinations-dbra",
  "states": ["TX", "NM"],
  "activeOnly": true,
  "maxResults": 500
}
```

## Assistance listings (CFDA)
Set `dataType` to `assistance-listings` to pull the Catalog of Federal Domestic Assistance — ~7,400 federal grant/loan/direct-payment programs (~2,900 currently active), each with its objective, eligibility rules, funding-obligation history, related programs and the agency's own published program contact.

- **Supports `keyword`, `organizationId`, `activeOnly`, `maxResults`, `watchLabel`, `watchChanges`, `webhookUrl`.** `naicsCodes`, `setAsideTypes`, `noticeTypes` and `states` are opportunity-only and are ignored (with a log warning) here — assistance-listing programs are nationwide, not filtered by place of performance. `enrichDetail` and `includeAttachments` are also ignored: the search row already carries the full record, and CFDA programs have no notice attachments.
- **`keyword` matches title, objective and program number** (e.g. `q=flood` → 60 of 7,392 programs), not a reference-number-only match like the wage-determination indices.
- **`programNumber`** (e.g. `"12.103"`) is the CFDA number buyers actually search by — the natural reference for cross-checking against grants.gov or an agency's own NOFO.
- **`obligations`** is shipped as SAM.gov's own raw per-assistance-type funding history (`{ assistanceType, values: [{ year, actual, estimate, flag, explanation }], additionalInfo }`) rather than normalized into a single amount field. Measured over the **entire catalog** (all 7,396 programs, cycle 1988): the amounts are mostly there — 4,205 programs carry a non-empty block and 4,093 of those (97.3%) carry a real number — but any single normalized amount field would be silently wrong on over a third of the 16,594 year-entries. **`0` is a placeholder, not a quantity** (2,943 `estimate: 0` + 2,737 `actual: 0` = 34.2% of entries; e.g. `10.856` FY2013 is `{flag: "ena", estimate: 0, explanation: "Program not funded"}`); **`estimate` and `actual` co-occur on 1,771 entries and disagree** by up to ~50% (e.g. `14.880` FY2019 estimate $20.0M vs actual $29.97M); and the flag vocabulary is exactly two values, `ena` (696, estimate not available) and `nsi` (340, not separately identifiable — the money is booked under another program number, given in `explanation`, e.g. `14.159` FY2014 → `"Reported under 14.117"`). Raw keeps those distinctions; a plausible-looking single number would destroy them. Full measurement: [a zero in federal program funding history doesn't mean zero dollars](https://fetchsmith.com/blog/cfda-funding-history-zero-is-not-zero).
- **`contacts`** is the agency's own published program contact (name/title/phone/address) from the public listing, the same disclosure class as opportunities' `pointOfContact`.
- **`watchChanges` on assistance listings** re-delivers a program if its active or funded status, modified date, or historical-index entry count has changed since you last saw it — there is no revision number or response deadline on this dataset, so funded/active status is the closest signal to "this program moved."

## Exclusions
Set `dataType` to `exclusions` to pull SAM.gov's federal debarment/suspension list — entities barred from receiving federal contracts, grants or other assistance — **restricted to organizations only (firms, vessels and special entity designations, ~35,200 records)**.

- **This Actor never returns the individual-person exclusion records SAM.gov also publishes.** SAM.gov's exclusions index carries 168,673 records total, and 79% of them (133,478) name a private person with a home city, state and zip — not a company. Turning that into a bulk-downloadable dataset would be a people-search product, which this Actor deliberately does not offer: the `classification` filter that separates organizations from individuals is hard-coded into every request this Actor makes, with no input anywhere that can widen it. If you need to check whether a specific named individual is excluded, look them up one at a time on [sam.gov/search](https://sam.gov/search/?index=ei) directly — SAM.gov's own public exclusions checker is exactly built for that single-lookup use case.
- **Supports `keyword` (matches the excluded entity's name), `organizationId`, `maxResults`, `watchLabel`, `watchChanges`, `webhookUrl`.** `naicsCodes`, `setAsideTypes`, `noticeTypes` and `states` are opportunity-only and are ignored (with a log warning) here. `activeOnly` has **no effect** on this dataset — SAM.gov's exclusions index does not support server-side active-status filtering, so every matching record is returned regardless of the setting; check each row's own `isActive`/`terminationDate` if you need to filter locally. `enrichDetail` and `includeAttachments` are also ignored: the search row already carries the full record, and exclusion records have no notice attachments.
- **Rows SAM.gov itself flags "do not display" are dropped before you ever see them**, regardless of classification — a small number of exclusion records carry SAM.gov's own `noPublicDisplayFlag`, and this Actor honors it the same way sam.gov's own public search does.
- **`watchChanges` on exclusions** re-delivers a record if its active status or termination date has changed since you last saw it — the two signals that mean a debarment was lifted.

## Use cases
- **GovCon bid pipelines** — pull every active solicitation in your NAICS codes and set-aside category (`naicsCodes` + `setAsideTypes` + `noticeTypes: ["o", "k"]`) into a CRM, already qualified by place of performance.
- **Small-business / 8(a) / SDVOSB capture** — filter to the set-asides you actually hold and stop reading opportunities you are not eligible for: `setAsideTypes: ["8(a)"]`, `["SDVOSB"]` or `["HUBZone"]` work as written, as do the underlying codes (`8A`, `SDVOSBC`, `HZC`, …).
- **Contracting-officer outreach on sources-sought notices** — `noticeTypes: ["r"]` plus `enrichDetail` gives you the pre-RFP notices where a vendor can still shape the requirement, together with the officer's published contact details.
- **Competitive award research** — `activeOnly: false` with `noticeTypes: ["a"]` returns award notices including `awardeeName` and `awardeeUeiSAM`, so you can see who is winning in your NAICS.
- **Agency- or state-specific monitoring** — `organizationId` for one department/agency, or `states` for the geographies your team can actually staff.
- **Daily cron alerts** — `watchLabel` on a narrow keyword/NAICS search on a schedule returns only the handful of new notices, instead of refreshing sam.gov by hand or re-paying for the whole result set every run.
- **Davis-Bacon compliance for construction bids** — `dataType: "wage-determinations-dbra"` with the states you build in tells you which determination covers each county and whether it is the current revision, so a bid is priced against a determination that is actually in force.
- **Service Contract Act scoping** — `dataType: "wage-determinations-sca"` returns the service categories each determination covers, so you can map a services solicitation to the right determination before pricing labour.
- **Wage-determination revision alerts** — `watchLabel` + `watchChanges` on a state-filtered wage-determination search re-delivers a determination only when its `revisionNumber`, active status or modified date moves — the signal that an in-flight bid or a running contract needs repricing.
- **Deadline-extension / lifecycle alerts** — `watchLabel` + `watchChanges` flags a presolicitation turning into a solicitation, a deadline extension, or an award landing on a solicitation you're already tracking.
- **Grant-eligibility screening** — `dataType: "assistance-listings"` with a keyword returns each matching program's `eligibleApplicants`/`eligibleBeneficiaries` and `objective`, so a grant writer can shortlist which CFDA programs a client actually qualifies for before drafting anything.
- **New/defunded grant program alerts** — `watchLabel` + `watchChanges` on `assistance-listings` flags a program going active, funded, or unfunded since your last check.

## FAQ
**Do I need a SAM.gov API key?** No. The official `api.sam.gov` developer API does require a free registered key, but this Actor uses the unauthenticated backend behind sam.gov's own public search page instead. Nothing to register, nothing to rotate.

**Is there a posted-date range filter?** Yes, since build 0.1.74 (2026-10-28): `postedFrom`/`postedTo` on `publishDate`, and `deadlineFrom`/`deadlineTo` on `responseDate` (the response deadline), all `YYYY-MM-DD` and inclusive on both ends, each side usable on its own as an open-ended range. **The backend still has none** — SAM.gov's search API exposes no date-range parameter on any of these indices, so this is the Actor's own post-fetch filter, and the one thing worth understanding about it is *where* it sits: the row is fetched, then dropped **before it is pushed or charged**, so you are never billed for a row outside your window. What that does not buy you is a cheaper upstream walk — SAM.gov still serves every row matching your server-side filters (`keyword`, `naicsCodes`, `states`, …), so a narrow window over a broad keyword can hit the run's time budget before `maxResults` is filled. Keep the other filters narrow, and reconcile with `RUN_SUMMARY`: `declaredMatches` is SAM.gov's **pre-window** count, `dateWindowDropped` is what the window removed, and `dateWindowMissing` is rows whose own date field was absent or unreadable — those are dropped too, deliberately, because we won't bill you for a row we can't prove is inside the window you asked for. A run that delivers far fewer rows than `declaredMatches` for this reason is reported as COMPLETE, not short. An unreadable date (`2026-02-31`), a reversed window (`postedFrom` after `postedTo`), or a window on a `dataType` that has no such date (`deadlineFrom` on wage determinations, any posted window on `exclusions`) stops the run before the first request with an explanation instead of quietly handing you — and billing you for — the unwindowed set. (`activeOnly` is still the cheapest way to separate open from closed opportunities.)

**Can I look up one exact solicitation number?** Yes, since build 0.1.23 (2026-10-28): set `solicitationNumber` to the number, with or without dashes/spaces (`"SPRRA2-22-R-0016"` and `"SPRRA222R0016"` are the same query). **Correction (build 0.1.76, 2026-10-28): SAM.gov's backend does have one real exact-match parameter for this, `notice_id`** — a `solnum`-style query parameter is still silently ignored, confirmed live by probing it directly, but `notice_id` genuinely narrows server-side (it just matches the *solicitation number*, not the opportunity id its name implies, and it wants the value exactly as typed — raw punctuation, case-sensitive). The Actor tries it first with one lightweight probe request: when your value matches it exactly, the whole run walks on `notice_id` and usually finishes in a single page instead of reading the broader index; when it doesn't (different case, approximate input, or truly no match), the run falls back automatically to the pre-charge post-fetch filter described below, unchanged from how this feature worked before `notice_id` was found. Either way, a fetched row is only ever pushed and charged once its own solicitation number (compared the same punctuation-stripped, case-insensitive way SAM.gov compares it internally) exactly matches — `notice_id` is an efficiency win, never trusted unchecked. On the fallback path, the value is sent to SAM.gov as the search keyword to narrow the walk (it overrides `keyword` if you also set one — you'll get a warning), but that only scopes the walk, it does not reduce how much is read upstream, so a number that happens to be a weak/short substring can still walk the whole index before the exact check runs. Use `RUN_SUMMARY.noticeIdFastPath` to see which path a run took, and `.solicitationNumberMismatch`/`.solicitationNumberMissing` to see what the exact-match filter removed. Not supported for wage determinations, `assistance-listings` or `exclusions` — those records carry no solicitation number, and the run stops before any request rather than billing you for the unfiltered set.

**Is there an award-amount range filter?** Yes, since build 0.1.77 (2026-10-29): `minAwardAmount`/`maxAwardAmount`, inclusive, either side usable alone. SAM.gov's search backend only supports an *exact* award-amount match (`award_amount=<n>`, confirmed live) and rejects every range syntax (`100000-200000`, `[100000 TO 200000]`, comma pairs, `>100000`) with HTTP 400, so like the date windows and `solicitationNumber` above, this is the Actor's own post-fetch filter: a fetched row is dropped **before it is pushed or charged** if its own `award.amount` is outside your range or missing entirely. `award.amount` is a real field on every opportunity row, but it is `null` until SAM.gov records an award against it — set `noticeTypes: ["a"]` to scope the walk to award notices, or most fetched rows will be dropped as `awardAmountMissing` rather than `awardAmountDropped` (the run logs a one-line reminder if you don't). Reconcile with `RUN_SUMMARY.awardAmountDropped` (out of range) and `.awardAmountMissing` (no award amount at all). Opportunities only; wage determinations, `assistance-listings` and `exclusions` carry no award object, and the run stops before any request rather than billing you for the unfiltered set.

**Can I see who currently holds the work a notice is re-soliciting?** Yes, since build 0.1.79 (2026-10-29): set `includeIncumbentAwards: true` and each opportunity gains an `incumbentAwards` array — the top 3 US federal contract awards by dollar value from **USAspending.gov** matching that notice's NAICS code, with recipient name, UEI, amount, start/end dates, awarding agency and sub-agency, and a `usaspending.gov` link for each. When the issuing department maps to one of USAspending's top-tier agency names the match is narrowed to that agency as well; every row records which it got in `incumbentAwardsMatchedBy` (`naics+agency`, `naics`, `no-naics` or `lookup-failed`). **No extra charge** — this is a second upstream, not a second billed event.

Three honest limits. **(1) `incumbentYears` is matched against each award's last-modification/obligation date on USAspending, not its award or start date.** Measured live: a 3-year window legitimately returns a contract that *started* in 2007 and was last modified in 2025, because an option exercise on a long-running contract is a recent action. That is the right answer for "who is performing this today", but it is not what "look-back" sounds like, so every returned award carries both `startDate` and `lastModifiedDate` and the exact window is written to `RUN_SUMMARY.incumbentAwards.lastModifiedBetween`. **(2) Definitive contract awards only** (USAspending award types A/B/C/D) — not IDV vehicles, grants, loans or sub-awards, because USAspending rejects a request mixing award-type groups and "who performs the work" is the contract, not the vehicle. **(3) NAICS is not on SAM.gov's search row** (its raw row carries only id/title/solicitation number/type/award/organization/descriptions), so this needs the per-opportunity detail call and turns `enrichDetail` on for you with a warning rather than silently returning nulls. A notice with no NAICS code at all gets `incumbentAwards: null` with `incumbentAwardsMatchedBy: "no-naics"` — distinct from `[]`, which means the lookup ran and USAspending genuinely holds no matching award.

**Is `description` the full notice text?** Yes — the full solicitation description as SAM.gov itself stores it (original HTML markup preserved), not a truncated snippet; it can run to several thousand characters on a detailed notice. Attachments (drawings, full statements of work as separate documents) are not part of `description` — set `includeAttachments: true` to list them.

**How deep can a search go?** The backend caps paging at 10,000 rows per query, so a very broad keyword will stop there. Narrow with `naicsCodes`, `noticeTypes` or `states` rather than trying to page past it.

**Is `pointOfContact` personal data?** These are government contracting officers' official work contact details, published by the agency itself as a required part of the statutory public notice — the same disclosure class as the contacts on our NIH RePORTER and EU TED Actors. They are returned as SAM.gov publishes them; they are not aggregated across sources, cross-referenced with any other dataset, or resold as a people-lookup product.

**How does the price compare?** $0.0015 per returned row with **no Actor-start fee**. The comparable paid SAM.gov Actors on the Store range from about $0.0005 (two 1–2-user listings' flat rate, verified live 2026-10-04) to $0.003 per row — see Pricing above for the full live ranking, including the handful of free listings — and some add an Actor-start fee of $0.00005–$0.50 on top, charge extra for attachments or change alerts, or require your own SAM.gov API key, none of which this Actor does.

**Can I download the bid attachments, not just get their links?** Set `includeAttachments: true` — every row then carries an `attachments` array with each file's name, size, MIME type and a direct, no-login `downloadUrl`. This Actor does not fetch the file bytes into the dataset itself (a notice can attach a 10+ MB drawing set, and this is a 2 GB box); the URL is SAM.gov's own stable download path, so your own pipeline fetches the actual bytes only for the files it wants, when it wants them, without ever needing a SAM.gov login. Two comparable rivals (`jungle_synthesizer/samgov-scraper`, `scrapesage/sam-gov-scraper`) also offer an attachment-download feature; this closes that gap.

**How does `watchLabel` know what's already new, and where is that baseline stored?** In a key-value store on your own Apify account, keyed by the label plus a fingerprint of `keyword`/`naicsCodes`/`setAsideTypes`/`noticeTypes`/`states`/`organizationId`/`activeOnly`. The first run for a label just records every currently-matching opportunity id and returns zero rows (you pay nothing); every run after that returns only ids not already in that record. Changing any of those filters starts a fresh baseline under the same label instead of comparing against the old filter's results.

**Does `watchChanges` cost extra?** No extra fee — a changed opportunity is billed at the same $0.0015/row as a new one, so you only pay when there's actually something to see. Plain `watchLabel` never re-delivers an opportunity it has already sent you, even if the agency later extends the deadline or the notice moves from presolicitation to solicitation to award. Set `watchChanges: true` and each run also compares every already-delivered opportunity's `isActive`/`noticeTypeCode`/`responseDate`/`modifiedDate`/`modificationsCount`/`awardeeName` (plus an internal fingerprint of `description`) against what it looked like last time; if anything moved, the row is re-delivered tagged with `_watchChangeType` (which field(s) changed) and `_watchPrevious` (their prior values — `description`'s previous value is a fixed note, since only a fingerprint of that text is stored, never the full text). Verified live: seeding a baseline, editing a delivered opportunity's recorded `isActive` flag and `responseDate` directly in the stored snapshot, then rerunning returned exactly those 2 rows with the correct change tags and nothing else — and a plain unchanged rerun after that returned 0 rows again.

**Don't filter on the field you're watching.** `watchChanges` compares each already-delivered row's watched fields against what they looked like last time — but two of this Actor's own filters are server-side narrowings on fields it also watches, so combining them with `watchChanges` makes exactly the change you're trying to catch structurally unreportable. `activeOnly` (**on by default**) sends SAM.gov `is_active=true`; `isActive` is the #1 watched field (the active → inactive/awarded transition, flagged as the single most valuable alert in this niche). The moment a row flips inactive, the filter stops it from matching the query at all — it is never fetched again, so `watchChanges` is never even asked about it, and the run just reports "nothing new." Live-verified cycle 1567 against a real sam.gov row (naics 221122): present with no filter, absent the instant `is_active=true` is added. Set `activeOnly: false` on any watch run where you need that transition — you'll get both active and inactive rows back and can filter on `isActive` yourself after delivery, or run two labels (one `activeOnly: true` for new rows, one `activeOnly: false` with `watchChanges` for the inactive transition). `noticeTypes` is the narrower second instance (opportunities only): it sends `notice_type`, and `noticeTypeCode` is watched for the presolicitation → solicitation → award lifecycle, so filtering to one type blinds the transition out of that type — leave it empty on a watch run that needs to see lifecycle moves. Both cases log an explicit warning (and, if the run also ends up with nothing new, a NOTE on that message) rather than silently reporting a clean, quiet watch.

**Don't pin `postedTo` on a watch, either — same trap, different mechanism.** `activeOnly`/`noticeTypes` above make `watchChanges` blind to a specific transition; a fixed `postedTo` is worse, because it kills `watchLabel` itself (new-opportunity detection, with or without `watchChanges`). `publishDate` is the date SAM.gov posted the notice, confirmed live to be assigned once and never bumped forward (active opportunities from as far back as 2011 still carry their original `publishDate`), while a brand-new notice's `publishDate` always equals today. So once today's date passes a fixed `postedTo`, no notice can ever again fall on or before it — the watch goes permanently quiet, and "nothing new" looks identical to "this watch is dead." `postedFrom` alone has no such problem (a one-sided lower bound only limits how far back the first baseline reaches). The run logs a warning when this combination is detected, and `RUN_SUMMARY.watchDeadDateBound` reports it so a pipeline can check from code. Drop `postedTo` from a watched query and reseed instead.

**How do I know a run returned everything, without reading the log?** Every run writes a `RUN_SUMMARY` record to its own key-value store — fetch it with `GET https://api.apify.com/v2/actor-runs/<runId>/key-value-store/records/RUN_SUMMARY` (no webhook needed; it's also sent as `summary` on any `webhookUrl` POST). It carries `declaredMatches` (what SAM.gov itself says matches your filters — `null`, never `0`, if the search never answered with a count), `reachableMatches` (those minus anything past SAM.gov's 10,000-row depth cap), `scanned`, `delivered`, `pages`, `pagesFailed`, `duplicateRowsDropped`, `republishedRowsDropped` (opportunities dataset only) and a boolean `complete`. When `complete` is `false`, `incompleteReason` is one of `upstream-error` (SAM.gov stopped answering mid-walk, after 4 retries), `short-page` (SAM.gov returned an empty page before its own declared total was reached), `depth-cap` (the query is deeper than the 10,000 rows this backend will serve), `duplicate-rows` (SAM.gov served its whole result set but repeated rows across pages, so there were fewer distinct opportunities than it declared), `max-results` (your `maxResults` is below the match count — the common, harmless one), `charge-limit` (the run's pay-per-event limit stopped it), `enrich-failed` (`enrichDetail` was on and some detail lookups failed, so their `naicsCodes`/`setAside`/`pointOfContact` are `null` for that reason rather than because SAM.gov has none), `attachments-failed` (`includeAttachments` was on and some attachment lookups failed, reported separately as `attachmentLookupsFailed` — their `attachments` field is `null` for that reason, not because the notice has no files), or `incumbents-failed` (`includeIncumbentAwards` was on and some **USAspending** lookups failed — a different upstream from SAM.gov, so the reason names it rather than letting SAM.gov take the blame; those rows' `incumbentAwards` is `null`, not an empty array). `incompleteDetail` spells out the numbers and `lastApiError` gives the underlying HTTP cause (SAM.gov's; USAspending's own last error is reported separately under `incumbentAwards.lastError`). A short run still finishes as `SUCCEEDED` — the rows it did return are real — so this record, plus the run's status message, is how a pipeline tells "200 of 200 matches" apart from "200 of 12,297".

**What if a blank value ends up in one of my list filters?** It is never silently ignored, because an ignored list filter is the most expensive mistake this Actor could make. `naicsCodes`, `setAsideTypes`, `states` and `noticeTypes` are OR-ed lists, and a blank or whitespace-only entry (the usual shape when the input is built from a spreadsheet column or a templated schedule) cannot be sent to SAM.gov. If *every* entry you gave is blank, the whole filter would vanish from the query — which does not return zero rows, it returns the *unnarrowed* result set and charges for every row of it (measured: an opportunities search narrowed by one NAICS code returns ~33 matches; the same search with the `naics` parameter missing returns ~16,110). So that run **fails immediately, before any request or charge**, naming the field to fix. If only *some* entries were blank, the surviving values are applied normally and the run reports exactly what it dropped — in the log, in the run status message, and as `RUN_SUMMARY.blankFilterEntriesDropped` (`{"naicsCodes": 1}`, or `null` when nothing was dropped) — so a pipeline can assert on it. The run status message is capped at Apify's own 500-character limit, and on a run whose status text is already long (e.g. a 0-match search naming several filters at once) this NOTE is reserved out of that budget rather than appended last, so a long run never loses the blank-entry disclosure to silent truncation — only the less critical detail ahead of it gets shortened. Unrecognised non-blank values are a different case and are deliberately *kept*: SAM.gov fails closed on a value it does not know, so keeping it matches nothing (safe) while dropping it would widen the search (expensive).

**My run FAILED with a long input value, and the message looked cut off — is something being hidden from me?** No, and since build 0.1.27 it can't happen: a hard-fail message (bad `postedFrom`/`postedTo`/`deadlineFrom`/`deadlineTo` date, a `solicitationNumber` that's all punctuation, or a watch baseline that couldn't complete) always echoes the value you supplied so you can see what was rejected, but these fields have no length limit on our side — a very long value could, before this fix, have pushed Apify's own 500-character status-message cap past the point where it silently cut off the rest of the sentence, taking the "stopping before any row is delivered or charged" / "no baseline was saved" disclosure off the end along with it. The echoed value is now capped at 40–60 characters (with `...`) and the billing-safety sentence is reserved space out of the 500-character budget, so it always survives intact no matter how long the input was. You are never charged for a run that fails this way, regardless of message length.

**A run finished SUCCEEDED with 0 rows and no error — what happened?** Two different reasons, both now reported in the run's status message (not just the log), and neither is a bug on your account: (1) **"Nothing new since the last run"** — on a `watchLabel` run, every matching row had already been delivered under that label on a prior run and none of them changed (set `watchChanges: true` if you need to catch edits, not just new rows) — the common, expected result of running a monitor on a schedule when nothing has moved. (2) **A genuinely empty search** — every filter value you supplied is valid, and SAM.gov simply has no match for that combination; the message names the filters actually applied so you know which one to widen first. Either way you are charged nothing — `Actor.charge()` is never called for a row that was never pushed. A `watchLabel` **baseline (seed)** run returning 0 rows is a third, separate, always-expected case (see above) and is not flagged as a status message — it's the designed first-run behavior, not an empty search.

**Can the same opportunity come back twice (and be charged twice)?** No, in either of the two ways this can happen. First, SAM.gov's backend pages by offset over a live, relevance-sorted index, so rows genuinely do repeat across pages under the same `opportunityId`. Repeats are dropped inside the walk, before any `Actor.charge()` call, so you are only ever billed for distinct `opportunityId` values; `RUN_SUMMARY.duplicateRowsDropped` tells you how many there were. **The repeat rate is not a fixed number — it varies run to run on the identical query.** Walking the same active-opportunities query (52,374 matches) to the 10,000-row depth cap twice, seconds apart, returned 8,925 distinct ids one time and 8,370 the next (89.25% vs. 83.70% yield), with duplicates landing on different pages each run. A narrower query that stays under 10,000 total matches sees none of this (measured 0 repeats on a 604-match query). Don't budget around a single "~X% repeats" figure for a query near or past the cap — read `RUN_SUMMARY.duplicateRowsDropped` for the actual run, or narrow filters until `declaredMatches` sits under 10,000. Full measurement: [SAM.gov's 10,000-row depth cap doesn't promise 10,000 rows](https://fetchsmith.com/blog/sam-gov-depth-cap-yield-varies). This is also why a very broad query can return fewer rows than `declaredMatches` even when nothing failed — that case reports `incompleteReason: "duplicate-rows"` rather than pretending the backend broke.

Second — and separate from paging repeats — SAM.gov itself sometimes posts the exact same solicitation twice under two brand-new `opportunityId`s, which an id-keyed dedup can never catch, since the id is exactly what differs between the copies. Measured live 2026-09-24 on a 400-row `activeOnly` opportunities sample: 2.2% of rows were byte-identical republications (same `title`/`solicitationNumber`/`description`/`agency`/`office`, only the id, `sourceUrl` and a timestamp seconds apart differed) — one VA asbestos-monitoring notice was posted 3 times in under a second. Every run now also dedupes on a content hash (`solicitationNumber` + `noticeTypeCode` + `title` + a fingerprint of `description`) within the opportunities dataset, dropping repeats before they are charged; `RUN_SUMMARY.republishedRowsDropped` reports how many. This guard is scoped to the opportunities dataset only — wage determinations, assistance listings and exclusions were not part of this measurement.

**Could a SAM.gov change silently turn my filtered search into an unfiltered one — and bill me for it?** Not without stopping the run first. SAM.gov's backend fails *closed* on a filter value it doesn't recognise (`naics=999999` → 0 matches) but fails *open* on a filter **name** it doesn't recognise: the parameter is silently dropped and the same HTTP 200 comes back carrying the entire index. Measured live: `naics=541511` → 604 matches, the one-letter typo `naic=541511` → 52,460, an 86× widening with no error anywhere — and under per-result pricing every one of those rows would be a charged "match". So before it fetches a single billable page, every run sends one tiny probe per filter name it is about to use, with a value that cannot match anything. A filter SAM.gov still honours returns 0; a dropped one returns the whole index, and the run aborts with an explicit error naming the parameter instead of delivering and charging for unfiltered rows. The probes are `size=1`, deliver nothing and cost you nothing. This also guards the exclusions dataset's individual-person exclusion — the `classification` filter that keeps private people out of the output is a parameter name like any other, and it is probed on every exclusions run whether or not you set any filters of your own.

**What happens if a watch baseline run doesn't finish?** It is flagged rather than silently trusted. A baseline that stopped early would report everything past the stopping point as brand new — and charge for it — on your first incremental run, so an incomplete seed saves with `lastRunStatus: "seeded-incomplete"`, logs a `BASELINE INCOMPLETE` warning naming the reason, and sets a run status message telling you to re-seed before scheduling. `RUN_SUMMARY` reports `mode: "watch-seed"`, `complete: false` and `baselineSize` so you can check it from code. The same applies if a baseline ever outgrows the 60,000-entry record cap (`baselineTruncated`).

**How is `webhookUrl` different from Apify's own platform webhooks?** Apify's platform webhooks are configured separately per Task/Actor via the Console or the Webhooks API — useful if you already live in the Apify Console, but extra setup if you're calling this Actor's API directly and just want a completion ping. `webhookUrl` is a plain input field: set it on the run itself and it POSTs a JSON body (`actorRunId`, `defaultDatasetId`, `finishedAt`, `pushed`, `rowsScanned`, the full `summary` object described above, and — if `watchLabel` is set — `watchSeeding`/`watchNewCount`/`watchChangedCount`/`watchSkippedCount`) once the run finishes and every opportunity is already pushed and charged. Especially useful with `watchLabel` on a scheduled bid alert: your endpoint is told how many new solicitations landed without polling the dataset, and `watchSeeding: true` distinguishes "this was the free baseline run" from "your watch is live and quiet" — both report zero new rows otherwise. It's best-effort — a slow or failing webhook only logs a warning, it never fails the run, changes the result set, or affects billing.
