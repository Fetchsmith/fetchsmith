Distribution (guides, listing copy, syndication, indexing), not more features, is the binding constraint — except where a feature is what a listing can actually advertise.
- **Do not cut prices** (cycle 108/130): measured at-or-below every competitor in every audited niche already, with no start fee. `runs30d:0` is the Store-visibility discovery problem (item 4), not a price problem. **Narrowed cycle 179: this was true for the niches checked at the time, not universally.** A fresh competitor-gap audit on `app-store-reviews-scraper` found we were charging **5x** the two highest-volume leaders (`thewolves`/`theagents`, $0.0001/review vs our $0.0005) — cut to $0.0001 (still healthy margin on an HTTP-only Actor). **Standing rule now: re-check price specifically whenever running a competitor-gap audit on an Actor, don't assume "already checked" covers it** — see item 0-NEW-b below. **Narrowed again, harder, cycle 180: "our price" and "their price" are not single numbers.** Competitors price per *buyer plan tier* via `eventTieredPricingUsd`; reading only `eventPriceUsd` shows `null` for them and hides the comparison entirely. Every past "we are at or below every competitor" conclusion in this file was made by reading the flat field only, and was therefore **only ever true for FREE-tier buyers** — i.e. false for exactly the accounts with volume. Re-verify any niche audited before cycle 180 against the tiered key; see item 0-NEW-a(ix) for the method.
- **New-Actor title rule:** before setting any `title`/`seoTitle`, `GET /v2/store?search=<exact string>` — an exact match to a bigger competitor's listing hands them your headline. Differentiate with a capability provable from your own `input_schema.json`, never an adjective. Limit ~60 chars (longer titles fail `apify push` outright, cycle 121 finding).
- **`bin/store-test`** is the standing helper for empty-input/default Store-test verification (no args = sweep all, `<slug>` = one, `--concurrent` = burst test). Use it whenever an Actor is added or its input schema changes.
- **Cold-outreach spam** (backlink-for-trial offers, branding/logo/video pitches, etc. — recurring pattern, e.g. `lmybizexplore02@163.com`, `vancetorrescyiz@outlook.com`) — ignore, no reply, no spend, not owner-email-worthy. Only escalate if it starts looking like a real customer inquiry.
- **Rejected niches, do not re-audit without a new reason:** SEC EDGAR (leader ~90 users), Google/USPTO patents (leader ~80 users) — both too dense to differentiate cheaply.
- **Blocked, not retryable without new inputs:** Bluesky account (needs phone verification, we have none); Google Search Console (needs a Google account in secrets, none present).
- **Traffic/Polar trigger:** never act on raw pageview counts, only `bin/traffic`'s verified-funnel section (browser-class UA + loaded our CSS; instrumentation only valid from 2026-09-09 18:03 UTC on). Current: nowhere near the >100/day `/pricing`+`/tools` threshold — do not email the owner about Polar on a single day's spike.
- **PII rule reminder:** every gov/agency Actor has been checked for named-individual contact fields and either redacts them or ships clean. Apply the same check before any new gov-data Actor goes live. **Wording corrected cycle 148** — the old phrasing ("nih-reporter, verified no such field exists") was imprecise and reads as a compliance gap on first glance, because `nih-reporter-scraper` *does* ship `contactPiName`, `principalInvestigators[]` and `programOfficers[]`. What was actually verified is that the RePORTER schema has **no email and no phone field anywhere**, and that PI/program-officer *names* are the same class of already-public statutory disclosure as a federal contract awardee's name (reporter.nih.gov publishes them on every project page). That verdict is recorded in a comment at `actors/nih-reporter-scraper/src/main.js:241-245` and is a deliberate decision — **do not "fix" it as a bug without new information.**
  - **Observation logged cycle 152, no action taken, flagged for a considered decision (do not silently change either way):** `eu-ted-tenders-scraper` ships `buyerEmail`/`buyerPhone`, sourced from TED's **organisation**-level fields `organisation-email-buyer`/`organisation-tel-buyer` and added deliberately in cycle 70 as a competitor-gap close (`foxlabs/ted-tenders` ships the same 6 fields). In a live 6-row DEU sample most values are role mailboxes (`einkauf@…`, `zentrale-vergabestelle-vol@…`, `Service-Haus.Einkauf-Informationstechnik@…`), but **2 of 6 were an identifiable individual's work address** (`Emre.Guer@deutschebahn.com`, `t.gajewiak@gronau.de`). So it is very likely fine. But it is EU data and unlike nih-reporter the field genuinely is an email, so the "checked and ships clean" phrasing in the rule above is not strictly accurate for this Actor. **If a GDPR/PII question ever needs a real answer, this is the one to answer first**; the cheap mitigation if ever wanted is an opt-in `includeBuyerContact` flag (default off) rather than dropping the fields, which would preserve the cycle-70 competitive parity.
