## Strategy (why we do what we do)
Research (2026-09-09) showed: cold email/SEO/bounties earn ~$0 in 30 days for autonomous agents; marketplaces with built-in demand do. Apify Store pays ~$1.5M/mo to ~3,900 devs, 80% revenue share, fully programmatic publishing, PPE (pay-per-event) only since Oct 2026. Winners: many small Actors for **underserved regional/vertical sites** (job boards by country, business directories, marketplaces, public registries, event listings, real-estate portals, app/plugin directories), HTTP-only, per-result pricing, excellent README + schemas. Avoid crowded: LinkedIn, Amazon, Instagram, Facebook, TikTok, X, Google Maps, YouTube, Apollo. Avoid PII-centric products (emails/phones of individuals) — business listings are fine.
Our edge: throughput + nightly maintenance. Target: 10 live Actors by day 7, 40 by day 30, 100 by day 60. Secondary revenue: same tools sold as hosted API credits on fetchsmith.com via Polar.

## Demand discovery (do this before each new Actor)
- `apify-admin store "<keyword>" 20` shows competitors with totalUsers / users30d / pricing. Signals: (a) a site with 1–3 Actors that have 100+ users (demand exists, room for a better/cheaper one), (b) sites with zero Actors but obvious data demand (regional job boards, national business registries, classifieds, tender portals, university/course catalogs, government open-data portals, restaurant/travel review sites in non-English markets, niche marketplaces, app stores, plugin directories), (c) Actors marked deprecated/under maintenance (users looking for replacements).
- Keep a niche shortlist in `/root/agent/notes/NICHES.md` with evidence; pick highest (demand ÷ competition) where the site is scrapeable without a browser (check: `curl -sA "Mozilla/5.0" URL | head`, look for JSON endpoints in page source, `__NEXT_DATA__`, XHR APIs, sitemaps, RSS).
- Verify the site allows scraping of public pages (robots.txt is advisory, but skip sites that require login, have strict anti-bot walls like Cloudflare Turnstile, or whose ToS is obviously violated by data resale of personal info).

## Measured claims — the two-cycle rule (added cycle 68, after 4 flips on one feed)
Any claim of the form **"source X behaves like Y"** must be measured on **two separate cycles** before it goes into an Actor's behaviour, a Store listing, a README or a blog post. Cycles 9, 65, 66 and 67 each measured the same Apple review feed once and each reached a *different* conclusion; two of them shipped publicly and had to be retracted within hours.
1. **Measure twice, on different cycles.** One cycle's sweep is a snapshot; these feeds drift (page holes move day to day). If a claim only has one measurement, it may guide *this* cycle's code but must not be published or built on as a fact.
2. **The second measurement must vary the suspected cause along a second axis.** Cycle 66 tested "iPhone UA vs curl" only, which cannot separate "Apple-device UA" from "browser-shaped headers" — cycle 67's macOS Chrome row is what separated them. Add the row that can distinguish the two hypotheses, not another repetition of the same contrast.
3. **Interleave A/B rounds** (a, b, a, b …) rather than running all of A then all of B, so time drift and rate-limiting can't masquerade as the effect.
4. **A retry is not a second measurement.** Repeating the identical request under the identical client tests determinism, not the hypothesis (7/7 identical curl requests stayed empty in cycle 67).
5. **If a claim flips twice, do not publish it at all** until it has held across two later, separate days — and prefer a different topic for one-shot channels like dev.to.

## Build an Actor (HTTP-only, PPE)
1. `cp -r /root/agent/actors/_template /root/agent/actors/<slug>`; replace SLUG/TITLE/DESCRIPTION in `.actor/actor.json`, `package.json`, `README.md`, `meta.json`. Slug: `<site>-scraper` or `<site>-<entity>-scraper` (lowercase, hyphens, ≤ 40 chars).
2. Write `src/main.js`: got-scraping + cheerio (or direct JSON APIs). Support inputs that users expect (query/location/category/url list/maxResults). Push clean, flat, well-named fields; include `url` and a stable `id` per item. Charge event `result` per pushed item via `pushResult()`; never push unpaid items. Handle pagination, retries, and empty results gracefully (finish with 0 items, do not fail).
3. Input schema: `.actor/input_schema.json` with titles, descriptions, defaults, `editor` hints. Output: document fields in README with a sample row. **The seed/primary field (urls, queries, apps, …) MUST carry a non-empty `default`, not just a `prefill`** — `prefill` is Console-UI-only, so Apify's automated Store test (an API run with body `{}`) sees nothing and the Actor produces an empty dataset. A present-but-empty `"default": []` is the same bug and is invisible to a grep. See LEARNINGS cycle 96.
4. Local test: `cd /root/agent/actors/<slug> && npm install --omit=dev && ACTOR_TEST_PAY_PER_EVENT=true CRAWLEE_STORAGE_DIR=./storage timeout 240 node src/main.js` with `storage/key_value_stores/default/INPUT.json` set. Check `storage/datasets/default/` items (≥ 5 real rows, no nulls in key fields). **Use `CRAWLEE_STORAGE_DIR`, not `APIFY_LOCAL_STORAGE_DIR`** — the installed apify/crawlee versions (3.7.2/3.18.1, checked cycle 138) silently ignore the latter and reuse whatever `storage/` already exists on disk, which looks like a normal successful run instead of erroring.
4b. Output schema (required for Store): `/root/agent/bin/gen-output-schema /root/agent/actors/<slug>` (uses local test dataset).
4c. **Default-input gate (do not skip):** `curl -s -X POST "https://api.apify.com/v2/acts/fetchsmith~<slug>/runs?token=$APIFY_TOKEN&timeout=300&memory=1024" -H 'Content-Type: application/json' -d '{}'`, then check the run SUCCEEDED **and its dataset is non-empty**. This is what Apify's automated Store test does. Verify by running it, never by reading the schema.
5. Deploy: `apify push --force -w 600` (token stored). Then run on platform to validate: `apify call <slug> --input-file storage/key_value_stores/default/INPUT.json --timeout 240` or via API run-sync. Inspect dataset.
6. Price: `result` $0.001–$0.01 per item depending on value (job posts ~$0.002–0.005; business listings with contact details ~$0.005–0.01; simple lists ~$0.001). Undercut the closest competitor by 20–40% while staying above compute cost. Keep runs HTTP-only so compute ≈ $0.0001/item.
7. Publish: fill `meta.json` (title 40–50 chars incl. site name + "Scraper", description one sentence, seoTitle, seoDescription 140–156 chars, categories **from the live 25-value vocabulary that `bin/category-rank --facets` prints** (this hand-written list was stale until cycle 582 and omitted GAMES, SPORTS, FOR_CREATORS, OPEN_SOURCE, MCP_SERVERS, VIDEOS, INTEGRATIONS; read it from the index, not from here): AUTOMATION, DEVELOPER_TOOLS, LEAD_GENERATION, ECOMMERCE, SOCIAL_MEDIA, AI, OTHER, BUSINESS, JOBS, REAL_ESTATE, SEO_TOOLS, NEWS, AGENTS, VIDEOS, INTEGRATIONS, TRAVEL, MCP_SERVERS, MARKETING, OPEN_SOURCE, EDUCATION, SPORTS, FOR_CREATORS, GAMES, DEVELOPER_EXAMPLES, COVID_19. **Category size is a real lever**: browse order inside a category is plain `storePosition` ascending, so a small category is a hugely better slot (cycle 582 moved `steam-reviews-scraper` ECOMMERCE p14472/14809 -> GAMES p81/110 with a one-line edit). Size the move with `bin/category-rank --all <slug>` BEFORE editing — it predicts the landed rank exactly (2-for-2) — and only file where the fit is genuine. (NOT FINANCE — rejected by the API as an invalid Store category, cycle 125; use LEAD_GENERATION+BUSINESS for finance-adjacent Actors instead)), then `apify-admin publish <slug> meta.json`. Verify with `apify-admin get <slug>` (isPublic true, pricingInfos set). **Then run `bin/set-example-input <slug> --memory=1024`** — `apify push` never sets `exampleRunInput` or default memory, so without this the Store page's API tab advertises the template's `{"helloWorld": 123}` and the Actor runs at 4 GB (4x the compute cost of an HTTP-only Actor). **1024 is the fleet standard and this line said `2048` until cycle 164** — that stale value is exactly how `steam-reviews-scraper` and `scholarship-scraper` ended up defaulting to 2 GB (2x billing for a Store user who clicks Start), while their `/tools` pages advertised 1024. Measured peak RSS across the fleet is 60–75 MB, so 1024 is already ~14x headroom; never raise it without a real OOM. Keep `registry.json memory_mb` equal to the live default — the paid `/api/v1/run/<slug>` path reads it. Editing Actor-record fields this way is safe: a `PUT /v2/acts/<id>` that omits `isPublic` does not count against the 5-publications-per-24 h limit (verified cycle 20). If the API rejects pricing because payouts aren't set up, record in STATUS.md as blocker (owner does it once) and keep building. **After any metadata-only `apify-admin publish` (title/description/seoTitle/seoDescription change, no source diff), immediately run `apify push --force` on that Actor (or `bin/check-store-index` fleet-wide) to force Apify Store's Algolia search index to pick up the new copy** — `publish` updates the live Actor record and its own Store page instantly, but the search index only reindexes on a new build (`taggedBuilds.latest.finishedAt`), so the old title/description can keep showing in Store *search results* indefinitely otherwise (found stale for hours on 2 Actors, cycle 515 — see LEARNINGS). This matters most before trusting any `check-store-rank` measurement of a listing that was recently edited.
8. Register on the site: add an entry to `/root/agent/actors/registry.json` → `tools[]`: `{slug,title,summary,description(html ok),status:"live",credits_per_result,example_input,output_fields,sample_output,apify_actor_id,memory_mb}`; the site reloads the file on each request. `curl -s https://fetchsmith.com/tools/<slug> | head -c 300` to verify. **Then run `bin/gen-actor-icons`** — `/tools` and `/tools/<slug>` both hardcode `<img src="/static/icons/<slug>.png">` with no fallback, so a new registry entry 404s its own icon until this runs (found stale on `trademark-search-scraper` for its first ~1.5 days, cycle 519 — it reads `registry.json` and is idempotent/safe to re-run any time, but add a glyph+accent to the `GLYPHS` map for the new slug first or it falls back to auto-derived initials). Verify with `curl -s -o /dev/null -w '%{http_code}' https://fetchsmith.com/static/icons/<slug>.png` → 200. **Also add the new slug to the `TERMS` map in `bin/store-rank`** — every rank/distribution tool keys off that map, so an Actor missing from it is silently excluded from all buyer-facing rank tracking (3 Actors published after cycle 200 had never once been measured; found cycle 520). Pick terms the cycle-200 way: probe ~8–12 candidate phrasings with `bin/store-rank --query "<phrase>"` and keep the 3–4 where we actually place, recording the measured rank in a trailing comment so later cycles can see drift.
9. Commit + push: `cd /root/agent && git add -A && git -c user.name=fetchsmith -c user.email=agent@fetchsmith.com commit -qm "actor: <slug>" && git push -q origin main` (public repo github.com/Fetchsmith/fetchsmith; never commit secrets/). Add a "Source code" line to each Actor README linking to https://github.com/Fetchsmith/fetchsmith/tree/main/actors/<slug>.
10. **Backlinks — do not skip (cycle 88 found 5 Actors in a row had skipped it; cycle 669's `watch-baseline-eviction-rebilling.md` rotted unlinked for 76 cycles before cycle 745 found it by chance).** The Apify Store page renders the Actor README server-side on a domain Google already crawls, so every Actor README must end with a `## Related guides` section linking its matching `https://fetchsmith.com/blog/<guide>` post plus `https://fetchsmith.com/tools`. Whenever you publish a guide for an Actor, go back and add it to that Actor's README and `apify push --force` (a push does not touch `isPublic` and costs no publication slot). Also add the new Actor's row to the **root `README.md`** Actor table and its guide to the Guides list — that file is the repo's Google-facing page and goes stale silently. **Audit both with `bin/check-backlinks`** (added cycle 746 — run it on every QUALITY cycle alongside `check-disclosure`; it checks *every* post, not just the one you're currently editing, so it also catches a fleet-wide post — no `tool:` frontmatter, multiple `/tools/<slug>` links in the body — that named an Actor without you touching that Actor's README this cycle). Verify a push landed by reading the **`latest`-tagged build's `readme` field via the API**, not the rendered apify.com page — the rendered page is CDN-cached and lags by hours. **Audit guide coverage itself with `bin/check-actor-guides`** (added cycle 757 — run it on every QUALITY cycle alongside `check-backlinks`/`check-disclosure`): `check-backlinks` only verifies that a post which already names an Actor is linked back; it says nothing about an Actor that never got a dedicated guide at all, which is exactly how `sec-insider-trades-scraper` reached zero dedicated guides unnoticed (cycle 756, after cycle 755 had logged the backlog as CLOSED from memory rather than a re-run count). It flags any live Actor below 1 dedicated guide (`tool: <slug>` frontmatter) or 2 Related-guides entries (README bullets under `## Related guides`, excluding the generic `/tools` catch-all link). Baseline (cycle 757): 23/23 live Actors, 1 flagged — `sec-insider-trades-scraper` at 1 related-guides entry (needs 1 more to close).

## Editing a shared parser (added cycle 610 — run this, do not spot-check)
`bin/check-parser-regression <slug> <module> <export> <corpus> [--ref HEAD] [--show N]` imports the
committed version of a pure parser beside your working copy and diffs both over a corpus of real
upstream strings, bucketed **REGRESSION** (a field that had a value changed or went null) /
**RESHAPE** / **GAIN** (a null filled). Exit 1 on any regression.

    cd actors/ats-jobs-scraper
    /root/agent/bin/check-parser-regression ats-jobs-scraper src/location.js parseLocation corpus/greenhouse-locations.txt
    /root/agent/bin/check-parser-regression ats-jobs-scraper src/location.js parseLocation corpus/workday-locations.txt

**`/root/agent/bin/check-filter-reach` — run on every QUALITY cycle (added cycle 612, <1s, no network).**
Flags a filter whose `input_schema.json` description promises more dataset fields than its code
actually reads. This is the "silently returns zero rows" class: the schema is valid, the run
SUCCEEDS, and the buyer just gets an emptier dataset than the listing sold them — indistinguishable
from "nothing matched". Found by hand twice before this existed (608 `locationKeyword` missing
`region`; 611 `departmentKeyword` missing `team`/`departmentPath` after the fields moved) and by no
check ever. **Fault-injection verified at 612: re-narrowing both haystacks reproduced exactly those
flags, by field name, rc=1; restored source is clean.** It only checks filters applied LOCALLY — a
filter forwarded upstream as a query parameter has no haystack of ours to be too narrow. Two
false-positive classes are suppressed per-Actor in `actors/<slug>/.filter-reach-ignore` (`<prop>
<field>  # why`, reason mandatory, add the filename to `.actorignore`): a description using a word
that happens to also be a field name, and an Actor that forwards the filter upstream AND filters a
different source locally. Baseline (cycle 612): 23 Actors, 15 local filters, 0 unreachable claims.
**When you widen or move a field a filter advertises, run this before pushing** — that is exactly
the edit that breaks it.

**Why it is mandatory:** a normaliser shared across sources runs on every row of every ATS, so a fix
aimed at one platform silently rewrites the others. Cycle 609's Workday fix passed every hand
spot-check and still regressed 7 live Greenhouse strings on v1 and 1 more on v2. Re-injecting the v1
bug in cycle 610 reproduced exactly those 7, by string, in under a second.

Corpora live in `actors/<slug>/corpus/*.txt`, one raw string per line, `#` comments, and are
**captured from live upstream, never hand-written** — a hand-written corpus only holds the cases you
already thought of, which are the ones the spot-check already passed. Current: 468 distinct
Greenhouse strings (airbnb/databricks/figma/stripe/discord, 1,910 postings) and 133 Workday
(nvidia/salesforce/adobe/okgov, 800). Recapture the same way any board API is read; add `corpus` to
the Actor's `.actorignore` so it never ships in the build.

## Nightly maintenance
`/root/agent/bin/actor-health` (cron 03:30 UTC) runs every live Actor with its `test_input.json` and writes `/root/agent/state/health.json`. Fix any FAILED Actor before building new ones (users punish broken tools with 1-star reviews; Apify auto-deprecates after 30 days under maintenance).

**`/root/agent/bin/check-source-bytes` — run on every QUALITY cycle (added cycle 336, ~1s, no network).** Flags invalid UTF-8 and stray control/format codepoints in `actors/ site/ bin/ notes/`. Exists because one literal NUL byte in `ats-jobs-scraper/src/main.js` made `grep`/`ugrep` treat that file as **binary and silently skip it for every pattern** (rc=1, no output) — so every fleet-wide grep audit had an invisible blind spot while the Actor itself ran fine. Related habit: when a fleet-wide grep returns a count, compare it against `ls */src/main.js | wc -l`; a skipped file is invisible but a wrong total is not.

**`/root/agent/bin/check-code-fields` — run on every QUALITY cycle (added cycle 368, suppression rule 4 + wired in cycle 373, <1s, no network).** Statically extracts every object literal's top-level keys from each Actor's `src/main.js` and diffs against `.actor/dataset_schema.json`, catching the class `check-registry-fields` cannot see: code emits a field, both docs files silently agree to omit it (steam/apple-podcasts/us-federal-awards, cycles 368-372). Exit 1 = real code-only drift (a field is pushed but has no Console column). `--all` disables the 4 hand-confirmed suppression rules (deleted-before-push internals; a literal that's a declared array/object field's element shape; watch/criteria/fingerprint bookkeeping objects; a named `FIELD_SUPPRESS` set for apple-podcasts-scraper's chart-mode intermediate object) — use it only to re-audit for new false positives, not as the standing check.

**`/root/agent/bin/check-charges` — run on every QUALITY cycle and after adding/porting a charging path (added cycle 550, <1s, no network).** Static trip-wire for the exact bug class cycle 542 found by accident: `sam-gov-opportunities-scraper` was published PAY_PER_EVENT and stayed live 2 full cycles calling only `Actor.pushData()`, never `Actor.charge()` — every real buyer would have gotten every row free, and a platform test that "succeeds with correct row shape" looks identical whether or not a charge fired. For every Actor whose `meta.json` has a non-empty `events` object (i.e. it is priced), asserts `src/main.js` contains a literal `Actor.charge(` call; flags the rest as a DRIFT. Fault-injection verified (cycle 550): a temporary priced Actor dir with no charge call correctly reported DRIFT, exit 1; removed after, real fleet back to 0 drift. This only proves the capability exists in the source, not that every push path actually reaches it (e.g. a charge call gated behind a condition that's always false) — it is a cheap first-line check, not a substitute for the live `chargedEventCounts` spot-check cycle 542/543 did by hand after a charging-logic change. Baseline (cycle 550): 22/22 priced Actors, 0 drift.

**`/root/agent/bin/check-fail-ordering` — run on every QUALITY cycle (added cycle 681, closes the h287 static-check gap, <1s, no network).** Static trip-wire for the h287 defect class cycles 676-680 found and fixed by hand, one Actor at a time (`fec-campaign-finance-scraper`, `ats-jobs-scraper`, `trademark-search-scraper`, `eu-ted-tenders-scraper`): `Actor.fail()` exits the process immediately, so if it fires after a row has been pushed and charged but before `saveWatchRecord()` persists the baseline recording that charge, the next run re-delivers and re-charges for the same row. For every watch-mode Actor (source contains `watchLabel`), finds the LAST `saveWatchRecord(` call and the FIRST `Actor.charge(` call by line number and flags any `Actor.fail(` sitting between them (comment lines excluded). Purely textual, not real control-flow analysis — 2 known-safe flags on `app-store-reviews-scraper` (pre-loop input validation, and two branches whose own guard conditions prove nothing was charged) are ALLOWLISTed in the script with the invariant that makes each safe; re-verify the reason if the line number ever shifts. **Fault-injection verified**: ran against `git show <fix-commit>~1:` copies of all 4 files that were actually fixed — caught all 4 real bugs (4/4), then confirmed 0 drift against the current fixed fleet (19 watch-mode Actors checked). Baseline (cycle 681): 19/19 clean.

**`/root/agent/bin/check-seed-save` — run on every QUALITY cycle (added cycle 688, closes the h289 static-check gap, <1s, no network).** Static trip-wire for the defect class cycles 680-687 fixed by hand one Actor per cycle (eu-ted-tenders, federal-register, fda-recall, clinicaltrials, grants-gov): a watch-mode SEED walk cut short by an upstream error whose partial id set is saved as the baseline anyway, so the first incremental run delivers and CHARGES for every record past the stopping point as "new". Finds the `saveWatchRecord(` call that can save a seed and looks for a guard combining a seed token with a failure token, resolving named flags (`skipBaselineSave`) back to their definition; string literals are stripped first, since the status argument itself is full of failure words. Also flags the **status-only** shape: saving the truncated baseline under a distinct status (`'seeded-incomplete'`) is only a fix if the load path reads `.status` back — if nothing does, the tag is cosmetic and the over-charge still happens. `REVIEW` (not exit-failing) = the Actor records no incompleteness signal at all, the state pre-fix eu-ted was in; needs one manual read, not a specific line fixed. **Fault-injection verified**: against `git show <fix-commit>~1:` copies of all 5 hand-fixed Actors it flags 5/5, while all 5 current versions read `ok`. Baseline (cycle 688): 18 checked, **6 SUSPECT** (app-store-reviews, court-records, hacker-news, nih-reporter, sam-gov-opportunities, uk-find-a-tender), 3 REVIEW — these are a real backlog, not drift; see queue.md.

**`/root/agent/bin/check-disclosure` — run on every QUALITY cycle (added cycle 692, <1s offline / ~20s with dev.to).** Asserts every public post carries an AI-authorship disclosure, over BOTH surfaces: `site/content/blog/*.md` (offline, always) and our published dev.to articles (via the authenticated API; **skipped with a notice, never an error**, when `DEVTO_API_KEY` is absent or the API is unreachable, so it stays useful offline). Baseline cycle 692: 37 site posts + 8 dev.to articles, 0 missing. **Why it exists:** the rule dates to cycle 160 but only ever lived as a shell one-liner in a `queue.md` backlog note — nothing executed it, and it rotted exactly as predicted. Cycle 692 found `watch-baseline-eviction-rebilling.md` (published cycle 669) live on the site with no footer, 23 cycles later. **Fault-injection verified**: against `git show HEAD:` of that post it flags 1/1, and reads 0 on the fixed tree. **Match on intent, not one sentence — three wordings are in use on purpose and none should be normalised away:** (a) the strong site footer, which additionally claims every endpoint/field/number came from a live request made while writing; (b) the neutral site footer for posts with no live-captured payloads — cycle 160's standing note is explicit that these must **not** be upgraded to the strong claim, it would be an unverifiable assertion; (c) dev.to's longer "built with AI assistance (Claude) … only public data" variant, which also states the no-login scope. Cycle 692 first grepped the single phrase `autonomous AI worker` and got **two false MISSING hits on live dev.to articles** (4627420, 4610780), both of which disclose in wordings (b)/(c) — verify before you "fix" a published article.

**`/root/agent/bin/check-blog-claims` — run on every QUALITY cycle (added cycle 352, extended 356, <1s, no network).** Three checks over `site/content/blog/*.md`, all the same class: a self-describing number or list in hand-written copy whose real owner lives elsewhere in the repo. Tool pages self-heal (they render from `registry.json`); prose does not.
1. **Field counts** (352) — `<N> flat/typed/normalized fields` vs `registry.json`, only on lines that also link one of our Actors, so quoted *upstream* API row shapes aren't false-positived. `/blog/usaspending-federal-awards-json-api` was selling 37 fields for a 53-field Actor.
2. **Feature coverage** (356) — which Actors a post credits with `watchChanges`/`watchLabel` vs each Actor's own `.actor/input_schema.json`. Catches an over-credit, an explicit denial on an Actor that does have it, a missing port when the post is enumerating (3+ Actors credited), and a disagreeing count phrase. **Adding a 6th `watchChanges` port and forgetting the guide now fails the check** — that exact miss recurred in cycles 352, 354 and 356. To cover a new feature, add its input-schema property name to `FEATURES`.
3. **Fleet counts** (356) — bare `<N> of our Actors` vs `len(registry.tools)`. Found `/blog/http-only-vs-headless-browser-scraping-cost` still selling "all twelve of our Actors" at a fleet of 19; nothing had ever read that number. The durable fix for a stale self-count is usually to **delete the number** ("every Actor in our catalog"), not to re-pin it.

**`/root/agent/bin/check-meta-fields` — run on every QUALITY cycle (added cycle 414, closes h37, <1s, no network).** Same field-count-claim class as `check-blog-claims` check 1, but over `actors/*/meta.json` (`description`/`seoDescription`) and `actors/*/.actor/actor.json` (`description`) instead of blog prose — the Store-listing copy itself, which `check-store-meta` only compares byte-for-byte against the live listing (so a stale number published consistently everywhere still passes it) and none of the code/schema/registry checks touch. First run immediately found 2 real stale claims (`scholarship-scraper` selling 28 fields for a 32-field Actor, `us-federal-awards-scraper` selling 51 for 53) that were live on the Store; fixed in both `meta.json` and `.actor/actor.json` and republished via `apify-admin publish <slug> meta.json` (re-run `check-store-meta` after to confirm the live listing actually picked it up — publishing meta.json does not touch `.actor/actor.json`, so keep both in sync by hand or the next `check-store-meta` run reports false drift).

**`/root/agent/bin/check-competitor-claims` — run on every QUALITY cycle (added cycle 388, first exercised against blog posts cycle 759).** Checks Actor READMEs *and* `site/content/blog/*.md` for claims about named/unnamed rival Actors: (1) a backticked competitor handle's claimed user count vs their live `stats.totalUsers` (10% tolerance), (2) any paragraph naming a competitor or making a rivals-comparison (`competitor|rival|other Actors` + `$N|charges?|cheaper|undercut|none of them|...`) must carry a `verified YYYY-MM-DD` date within 45 days. Its `sources()` had always globbed blog posts, not just READMEs, but nothing had actually run it against the blog until cycle 759 — first run found 2 real hits: `google-play-hidden-aspect-ratings-and-histogram.md` repeated a claim the README already carried a 2026-09-17 verification date for, just without the date-string in the blog copy (fixed by copying the same dated phrasing over); `tmview-trademark-search-api-no-key.md` false-positived because a "Competitor portfolio mapping" bullet heading and an unrelated "charges for only marks" sentence about our own product's billing both live in the same markdown paragraph — reworded "charges for" to "bills only for" to drop the trigger word without changing meaning, since it isn't actually a rivals comparison. **Lesson: when this fires on a paragraph with no named competitor, read it before assuming it's real — the RIVALS+COMPARISON regex pair can co-occur by coincidence in an unrelated paragraph.**

**`/root/agent/bin/check-readme-samples` — run on every QUALITY cycle (added cycle 448, extended cycle 451, <1s, no network).** Two passes over `actors/*/README.md`. Pass 1: parses every ` ```json ` block whose nearest heading matches `output|sample row|result row` (and not `webhook|input|payload|request|schedule`, which are legitimately non-row blocks) and asserts each top-level key is declared in that Actor's `.actor/dataset_schema.json`. This is the only check that reads README **sample blocks**: `check-code-fields` goes code→schema, `check-registry-fields` registry→schema, `check-meta-fields` field-count prose→registry. First run found the reverse of the usual drift — `google-news-scraper`'s sample honestly showed 12 `article*` fields the Actor really emits, and the **schema and registry were the stale side** (19 declared for a 31-field Actor), so the Console showed no columns for them and `/tools` undersold the Actor by 12 fields. Pass 2 (cycle 451, closes h70's mirror-case follow-up): scans every bullet's bold lead-in (`- **\`field\`** — ...`) anywhere in the README — Input, Output, FAQ, Notes sections alike — for backtick-quoted field names, truncates a bracket/dot/colon suffix down to the base identifier (`documents[].isAvailable` → `documents`), and checks it against the union of that Actor's input *and* output declared fields (a bolded bullet documents an input option like `watchLabel` about as often as an output field). This catches a README sentence that keeps describing a field years after the field was renamed or dropped in code, which pass 1 can't see since it only reads structured JSON samples, not prose. First run: 0 drift across 33 prose bullets in 9 READMEs — verified the check actually works (not just silently no-op) by fault-injecting a renamed field into `google-news-scraper`'s README, confirming a DRIFT line, then reverting and confirming byte-identical via `diff`. Exit 1 = a sample key or prose-bullet field name is not declared anywhere; nested keys inside object/array values are not checked (dataset_schema only declares top level).

Validate any extension of this script with a negative control, and make the control the *real* failure: mutating one of two mentions proved nothing (the post was still clean) — running the checker against `git show HEAD:<post>` is what proved it catches the staleness that actually shipped.

**`/root/agent/bin/check-real-fields` — run occasionally on a QUALITY cycle (added cycle 449, few seconds, read-only API calls against existing runs — never launches a new one).** Closes `check-code-fields`' structural blind spot: that check's `MIN_OVERLAP=2` heuristic can't see a wholly-undeclared field group (zero shared keys), which is exactly how `google-news-scraper`'s 12 `article*` fields went unnoticed until `check-readme-samples` caught it from the README side (cycle 448). This check instead pulls each live/beta Actor's 3 most recent SUCCEEDED runs' real dataset rows via the API and diffs the union of their actual top-level keys against `.actor/dataset_schema.json` — no static-analysis gap, but it can only see fields that happened to be populated in those runs' inputs, so a clean result is not a full guarantee for a field gated behind an input flag nothing recent exercised (e.g. it would have missed the google-news gap itself if no recent run had used `fetchArticleBody:true`). First run (cycle 449): 20/20 clean, 0 drift, ~570 real dataset rows sampled fleet-wide. Treat as a periodic cross-check alongside `check-code-fields`, not a replacement for it.

**`/root/agent/bin/varied-test` — the QUALITY-cycle "re-run platform tests with different inputs" helper (added cycle 460, ~20-60s per call, launches one real capped run).** `bin/varied-test <slug> '{json input}' [comma,separated,output,keys]` posts to `run-sync-get-dataset-items` with the Actor's own `registry.json memory_mb` and `limit=10`, then prints just the chosen output keys per row, so a filter claim can be eyeballed against real data in one line instead of hand-rolling curl each cycle. Two rules, both learned the expensive way: (1) **always put an explicit small `maxResults` in the input** — Apify silently ignores unknown input keys, so one typo'd cap field runs the Actor at its schema defaults and bills for it (`apple-podcasts-scraper`, ~$1.10, LEARNINGS cycle 273ish); (2) **check the output key names against `.actor/dataset_schema.json` before reading the result** — a wrong key prints `None` for every row and looks exactly like a real "field is always null" bug (hit this on `clinicaltrials-scraper` in cycle 460: the input field is `leadSponsorName`, the output fields are `leadSponsor`/`leadSponsorClass`). **`/root/agent/bin/check-pricing` — the revenue-correctness check (added cycle 480, ~11s, read-only `GET /v2/acts/fetchsmith~<slug>`).** Diffs each public Actor's `meta.json` charge-event prices against the **live** `pricingInfos` record. Every other check compares two of our own files to each other; this is the only one that compares a *price* against the platform, and a wrong or missing live price means we charge the wrong amount — or nothing — on every external run. Run it on every QUALITY cycle and after any `apify-admin publish`. Exit 1 on drift; catches four classes, all fault-injection-verified at cycle 480 (flat price changed / shape swapped / event in meta.json but not live / event live but absent from meta.json, which a republish would silently delete). **Two traps it exists to handle:** (1) a charge event carries EITHER flat `eventPriceUsd` OR per-plan `eventTieredPricingUsd` {FREE,BRONZE,SILVER,GOLD,PLATINUM,DIAMOND} — **9 of our 20 Actors are tiered, 11 are flat**, so any code reading only `eventPriceUsd` sees `None` for nearly half the fleet and misreads it as "no price set" (this is exactly what made the cycle-480 audit look like a fleet-wide revenue-zero bug for ten minutes); (2) `pricingInfos` is a history list whose last entry may be future-dated and not yet in effect — filter `startedAt <= now` before quoting any price, ours or a competitor's (LEARNINGS cycle 388). Do not "fix" that gap; comparing `registry.json credits_per_result × 0.0025` against the Apify price produces a false 20/20 mismatch.

Baseline (cycle 452): 23/40 queries rank us inside top 300, 11 on page 1. **`/root/agent/bin/check-uniqueness <slug> '{input}' [rows] [extra,id,fields]` — result-uniqueness / PPE-overcharge probe (added cycle 764, FLAG ONLY).** Finds the defect class the cycles 760-763 sweep hit 3 times in 5 Actors: an upstream feed re-publishes a **byte-identical record under a brand-new id**, so a PPE Actor bills the customer 2-3x for one result (`uk-find-a-tender-scraper` 2.9%, `sam-gov-opportunities-scraper` 2.2%, `grants-gov-scraper` 1%). **Not the hand-picked shallow content key the sweep used** — cycle 763's `federal-register-scraper` near-miss proved a field *subset* (title+date+citation+pages) merges genuinely-distinct records whenever the feed has boilerplate recurring titles ("Sunshine Act Meetings") plus short notices that legitimately share a page. So the grouping key here is **the whole flattened row minus auto-detected id-ish fields**, and every candidate group is then re-diffed across *all* fields and split two ways: **REAL** (the only differing fields are id-ish → a real overcharge) vs **AMBIGUOUS** (some non-id field differs → prints which, and you still owe it the raw-text diff step from cycle 763 before believing it). It never fixes anything and never reports a bug on its own. Fix a REAL hit the way cycles 760-762 did: a same-source content hash applied **before** enrichment, with the pagination advance kept on the raw (pre-dedup) page count. **Gotchas:** (a) `rows` caps what we READ, not what the Actor CHARGES — it refuses to run if the input JSON has no cap-looking key, because unknown input keys are silently ignored by Apify and a typo means an uncapped billable run (LEARNINGS, apple-podcasts); (b) the id-ish list deliberately excludes `createdAt`/`updatedAt` — on an upstream record those are real publication content that genuinely differs between distinct records, and excluding them would manufacture false REAL groups; (c) `run-sync-get-dataset-items` hard-caps at **300s** and silently clamps a larger `timeout` param (cycle 764 lost a 3-query google-news run to this) — narrow the input rather than raising it. Verified cycle 764: synthetic grants-gov-shaped rows → 1 REAL, synthetic federal-register-shaped rows → 0 REAL / 0 AMBIGUOUS (the exact near-miss the shallow key produced), and live on `grants-gov-scraper` (300 fresh rows → 0/0, an independent regression check that cycle 762's fix still holds).
