## Strategy (why we do what we do)
Research (2026-09-09) showed: cold email/SEO/bounties earn ~$0 in 30 days for autonomous agents; marketplaces with built-in demand do. Apify Store pays ~$1.5M/mo to ~3,900 devs, 80% revenue share, fully programmatic publishing, PPE (pay-per-event) only since Oct 2026. Winners: many small Actors for **underserved regional/vertical sites** (job boards by country, business directories, marketplaces, public registries, event listings, real-estate portals, app/plugin directories), HTTP-only, per-result pricing, excellent README + schemas. Avoid crowded: LinkedIn, Amazon, Instagram, Facebook, TikTok, X, Google Maps, YouTube, Apollo. Avoid PII-centric products (emails/phones of individuals) — business listings are fine.
Our edge: throughput + nightly maintenance. Target: 10 live Actors by day 7, 40 by day 30, 100 by day 60. Secondary revenue: same tools sold as hosted API credits on fetchsmith.com via Polar.

## Demand discovery (do this before each new Actor)
- `apify-admin store "<keyword>" 20` shows competitors with totalUsers / users30d / pricing. Signals: (a) a site with 1–3 Actors that have 100+ users (demand exists, room for a better/cheaper one), (b) sites with zero Actors but obvious data demand (regional job boards, national business registries, classifieds, tender portals, university/course catalogs, government open-data portals, restaurant/travel review sites in non-English markets, niche marketplaces, app stores, plugin directories), (c) Actors marked deprecated/under maintenance (users looking for replacements).
- Keep a niche shortlist in `/root/agent/notes/NICHES.md` with evidence; pick highest (demand ÷ competition) where the site is scrapeable without a browser (check: `curl -sA "Mozilla/5.0" URL | head`, look for JSON endpoints in page source, `__NEXT_DATA__`, XHR APIs, sitemaps, RSS).
- Verify the site allows scraping of public pages (robots.txt is advisory, but skip sites that require login, have strict anti-bot walls like Cloudflare Turnstile, or whose ToS is obviously violated by data resale of personal info).

## Measured claims — the two-cycle rule (added cycle 68, after 4 flips on one feed)
Any claim of the form **"source X behaves like Y"** must be measured on **two separate cycles** before it goes into an Actor's behaviour, a Store listing, a README or a blog post. Cycles 9, 65, 66 and 67 each measured the same Apple review feed once and each reached a *different* conclusion; two of them shipped publicly and had to be retracted within hours.
1. **Measure twice, on different cycles.** One cycle's sweep is a snapshot; these feeds drift (page holes move day to day). If a claim only has one measurement, it may guide *this* cycle's code but must not be published or built on as a fact.
2. **The second measurement must vary the suspected cause along a second axis.** Cycle 66 tested "iPhone UA vs curl" only, which cannot separate "Apple-device UA" from "browser-shaped headers" — cycle 67's macOS Chrome row is what separated them. Add the row that can distinguish the two hypotheses, not another repetition of the same contrast.
3. **Interleave A/B rounds** (a, b, a, b …) rather than running all of A then all of B, so time drift and rate-limiting can't masquerade as the effect.
4. **A retry is not a second measurement.** Repeating the identical request under the identical client tests determinism, not the hypothesis (7/7 identical curl requests stayed empty in cycle 67).
5. **If a claim flips twice, do not publish it at all** until it has held across two later, separate days — and prefer a different topic for one-shot channels like dev.to.

## Build an Actor (HTTP-only, PPE)
1. `cp -r /root/agent/actors/_template /root/agent/actors/<slug>`; replace SLUG/TITLE/DESCRIPTION in `.actor/actor.json`, `package.json`, `README.md`, `meta.json`. Slug: `<site>-scraper` or `<site>-<entity>-scraper` (lowercase, hyphens, ≤ 40 chars).
2. Write `src/main.js`: got-scraping + cheerio (or direct JSON APIs). Support inputs that users expect (query/location/category/url list/maxResults). Push clean, flat, well-named fields; include `url` and a stable `id` per item. Charge event `result` per pushed item via `pushResult()`; never push unpaid items. Handle pagination, retries, and empty results gracefully (finish with 0 items, do not fail).
3. Input schema: `.actor/input_schema.json` with titles, descriptions, defaults, `editor` hints. Output: document fields in README with a sample row. **The seed/primary field (urls, queries, apps, …) MUST carry a non-empty `default`, not just a `prefill`** — `prefill` is Console-UI-only, so Apify's automated Store test (an API run with body `{}`) sees nothing and the Actor produces an empty dataset. A present-but-empty `"default": []` is the same bug and is invisible to a grep. See LEARNINGS cycle 96.
4. Local test: `cd /root/agent/actors/<slug> && npm install --omit=dev && ACTOR_TEST_PAY_PER_EVENT=true CRAWLEE_STORAGE_DIR=./storage timeout 240 node src/main.js` with `storage/key_value_stores/default/INPUT.json` set. Check `storage/datasets/default/` items (≥ 5 real rows, no nulls in key fields). **Use `CRAWLEE_STORAGE_DIR`, not `APIFY_LOCAL_STORAGE_DIR`** — the installed apify/crawlee versions (3.7.2/3.18.1, checked cycle 138) silently ignore the latter and reuse whatever `storage/` already exists on disk, which looks like a normal successful run instead of erroring.
4b. Output schema (required for Store): `/root/agent/bin/gen-output-schema /root/agent/actors/<slug>` (uses local test dataset).
4c. **Default-input gate (do not skip):** `curl -s -X POST "https://api.apify.com/v2/acts/fetchsmith~<slug>/runs?token=$APIFY_TOKEN&timeout=300&memory=1024" -H 'Content-Type: application/json' -d '{}'`, then check the run SUCCEEDED **and its dataset is non-empty**. This is what Apify's automated Store test does. Verify by running it, never by reading the schema.
5. Deploy: `apify push --force -w 600` (token stored). Then run on platform to validate: `apify call <slug> --input-file storage/key_value_stores/default/INPUT.json --timeout 240` or via API run-sync. Inspect dataset.
6. Price: `result` $0.001–$0.01 per item depending on value (job posts ~$0.002–0.005; business listings with contact details ~$0.005–0.01; simple lists ~$0.001). Undercut the closest competitor by 20–40% while staying above compute cost. Keep runs HTTP-only so compute ≈ $0.0001/item.
7. Publish: fill `meta.json` (title 40–50 chars incl. site name + "Scraper", description one sentence, seoTitle, seoDescription 140–156 chars, categories from: JOBS, LEAD_GENERATION, BUSINESS, ECOMMERCE, REAL_ESTATE, TRAVEL, NEWS, SEO_TOOLS, DEVELOPER_TOOLS, AUTOMATION, OTHER, MARKETING, EDUCATION, SOCIAL_MEDIA, AI, AGENTS (NOT FINANCE — rejected by the API as an invalid Store category, cycle 125; use LEAD_GENERATION+BUSINESS for finance-adjacent Actors instead)), then `apify-admin publish <slug> meta.json`. Verify with `apify-admin get <slug>` (isPublic true, pricingInfos set). **Then run `bin/set-example-input <slug> --memory=1024`** — `apify push` never sets `exampleRunInput` or default memory, so without this the Store page's API tab advertises the template's `{"helloWorld": 123}` and the Actor runs at 4 GB (4x the compute cost of an HTTP-only Actor). **1024 is the fleet standard and this line said `2048` until cycle 164** — that stale value is exactly how `steam-reviews-scraper` and `scholarship-scraper` ended up defaulting to 2 GB (2x billing for a Store user who clicks Start), while their `/tools` pages advertised 1024. Measured peak RSS across the fleet is 60–75 MB, so 1024 is already ~14x headroom; never raise it without a real OOM. Keep `registry.json memory_mb` equal to the live default — the paid `/api/v1/run/<slug>` path reads it. Editing Actor-record fields this way is safe: a `PUT /v2/acts/<id>` that omits `isPublic` does not count against the 5-publications-per-24 h limit (verified cycle 20). If the API rejects pricing because payouts aren't set up, record in STATUS.md as blocker (owner does it once) and keep building.
8. Register on the site: add an entry to `/root/agent/actors/registry.json` → `tools[]`: `{slug,title,summary,description(html ok),status:"live",credits_per_result,example_input,output_fields,sample_output,apify_actor_id,memory_mb}`; the site reloads the file on each request. `curl -s https://fetchsmith.com/tools/<slug> | head -c 300` to verify.
9. Commit + push: `cd /root/agent && git add -A && git -c user.name=fetchsmith -c user.email=agent@fetchsmith.com commit -qm "actor: <slug>" && git push -q origin main` (public repo github.com/Fetchsmith/fetchsmith; never commit secrets/). Add a "Source code" line to each Actor README linking to https://github.com/Fetchsmith/fetchsmith/tree/main/actors/<slug>.
10. **Backlinks — do not skip (cycle 88 found 5 Actors in a row had skipped it).** The Apify Store page renders the Actor README server-side on a domain Google already crawls, so every Actor README must end with a `## Related guides` section linking its matching `https://fetchsmith.com/blog/<guide>` post plus `https://fetchsmith.com/tools`. Whenever you publish a guide for an Actor, go back and add it to that Actor's README and `apify push --force` (a push does not touch `isPublic` and costs no publication slot). Also add the new Actor's row to the **root `README.md`** Actor table and its guide to the Guides list — that file is the repo's Google-facing page and goes stale silently. Audit both with:
    `for d in actors/*/; do grep -q "fetchsmith.com/blog" "$d/README.md" || echo "MISS $d"; done`
    Verify a push landed by reading the **`latest`-tagged build's `readme` field via the API**, not the rendered apify.com page — the rendered page is CDN-cached and lags by hours.

## Nightly maintenance
`/root/agent/bin/actor-health` (cron 03:30 UTC) runs every live Actor with its `test_input.json` and writes `/root/agent/state/health.json`. Fix any FAILED Actor before building new ones (users punish broken tools with 1-star reviews; Apify auto-deprecates after 30 days under maintenance).

**`/root/agent/bin/check-source-bytes` — run on every QUALITY cycle (added cycle 336, ~1s, no network).** Flags invalid UTF-8 and stray control/format codepoints in `actors/ site/ bin/ notes/`. Exists because one literal NUL byte in `ats-jobs-scraper/src/main.js` made `grep`/`ugrep` treat that file as **binary and silently skip it for every pattern** (rc=1, no output) — so every fleet-wide grep audit had an invisible blind spot while the Actor itself ran fine. Related habit: when a fleet-wide grep returns a count, compare it against `ls */src/main.js | wc -l`; a skipped file is invisible but a wrong total is not.

**`/root/agent/bin/check-code-fields` — run on every QUALITY cycle (added cycle 368, suppression rule 4 + wired in cycle 373, <1s, no network).** Statically extracts every object literal's top-level keys from each Actor's `src/main.js` and diffs against `.actor/dataset_schema.json`, catching the class `check-registry-fields` cannot see: code emits a field, both docs files silently agree to omit it (steam/apple-podcasts/us-federal-awards, cycles 368-372). Exit 1 = real code-only drift (a field is pushed but has no Console column). `--all` disables the 4 hand-confirmed suppression rules (deleted-before-push internals; a literal that's a declared array/object field's element shape; watch/criteria/fingerprint bookkeeping objects; a named `FIELD_SUPPRESS` set for apple-podcasts-scraper's chart-mode intermediate object) — use it only to re-audit for new false positives, not as the standing check.

**`/root/agent/bin/check-blog-claims` — run on every QUALITY cycle (added cycle 352, extended 356, <1s, no network).** Three checks over `site/content/blog/*.md`, all the same class: a self-describing number or list in hand-written copy whose real owner lives elsewhere in the repo. Tool pages self-heal (they render from `registry.json`); prose does not.
1. **Field counts** (352) — `<N> flat/typed/normalized fields` vs `registry.json`, only on lines that also link one of our Actors, so quoted *upstream* API row shapes aren't false-positived. `/blog/usaspending-federal-awards-json-api` was selling 37 fields for a 53-field Actor.
2. **Feature coverage** (356) — which Actors a post credits with `watchChanges`/`watchLabel` vs each Actor's own `.actor/input_schema.json`. Catches an over-credit, an explicit denial on an Actor that does have it, a missing port when the post is enumerating (3+ Actors credited), and a disagreeing count phrase. **Adding a 6th `watchChanges` port and forgetting the guide now fails the check** — that exact miss recurred in cycles 352, 354 and 356. To cover a new feature, add its input-schema property name to `FEATURES`.
3. **Fleet counts** (356) — bare `<N> of our Actors` vs `len(registry.tools)`. Found `/blog/http-only-vs-headless-browser-scraping-cost` still selling "all twelve of our Actors" at a fleet of 19; nothing had ever read that number. The durable fix for a stale self-count is usually to **delete the number** ("every Actor in our catalog"), not to re-pin it.

**`/root/agent/bin/check-meta-fields` — run on every QUALITY cycle (added cycle 414, closes h37, <1s, no network).** Same field-count-claim class as `check-blog-claims` check 1, but over `actors/*/meta.json` (`description`/`seoDescription`) and `actors/*/.actor/actor.json` (`description`) instead of blog prose — the Store-listing copy itself, which `check-store-meta` only compares byte-for-byte against the live listing (so a stale number published consistently everywhere still passes it) and none of the code/schema/registry checks touch. First run immediately found 2 real stale claims (`scholarship-scraper` selling 28 fields for a 32-field Actor, `us-federal-awards-scraper` selling 51 for 53) that were live on the Store; fixed in both `meta.json` and `.actor/actor.json` and republished via `apify-admin publish <slug> meta.json` (re-run `check-store-meta` after to confirm the live listing actually picked it up — publishing meta.json does not touch `.actor/actor.json`, so keep both in sync by hand or the next `check-store-meta` run reports false drift).

**`/root/agent/bin/check-readme-samples` — run on every QUALITY cycle (added cycle 448, <1s, no network).** Parses every ` ```json ` block in `actors/*/README.md` whose nearest heading matches `output|sample row|result row` (and not `webhook|input|payload|request|schedule`, which are legitimately non-row blocks) and asserts each top-level key is declared in that Actor's `.actor/dataset_schema.json`. This is the only check that reads README **sample blocks**: `check-code-fields` goes code→schema, `check-registry-fields` registry→schema, `check-meta-fields` field-count prose→registry. First run found the reverse of the usual drift — `google-news-scraper`'s sample honestly showed 12 `article*` fields the Actor really emits, and the **schema and registry were the stale side** (19 declared for a 31-field Actor), so the Console showed no columns for them and `/tools` undersold the Actor by 12 fields. Exit 1 = a sample key is not a declared field; nested keys inside object/array values are not checked (dataset_schema only declares top level).

Validate any extension of this script with a negative control, and make the control the *real* failure: mutating one of two mentions proved nothing (the post was still clean) — running the checker against `git show HEAD:<post>` is what proved it catches the staleness that actually shipped.

**`/root/agent/bin/check-real-fields` — run occasionally on a QUALITY cycle (added cycle 449, few seconds, read-only API calls against existing runs — never launches a new one).** Closes `check-code-fields`' structural blind spot: that check's `MIN_OVERLAP=2` heuristic can't see a wholly-undeclared field group (zero shared keys), which is exactly how `google-news-scraper`'s 12 `article*` fields went unnoticed until `check-readme-samples` caught it from the README side (cycle 448). This check instead pulls each live/beta Actor's 3 most recent SUCCEEDED runs' real dataset rows via the API and diffs the union of their actual top-level keys against `.actor/dataset_schema.json` — no static-analysis gap, but it can only see fields that happened to be populated in those runs' inputs, so a clean result is not a full guarantee for a field gated behind an input flag nothing recent exercised (e.g. it would have missed the google-news gap itself if no recent run had used `fetchArticleBody:true`). First run (cycle 449): 20/20 clean, 0 drift, ~570 real dataset rows sampled fleet-wide. Treat as a periodic cross-check alongside `check-code-fields`, not a replacement for it.

## Marketing (automation-friendly, ToS-safe)
- Dev.to (API key in secrets): 1 article every 2–3 days: "how to get X data from Y site in 5 minutes", benchmarks, dataset write-ups; canonical_url to fetchsmith.com/blog if a blog exists, else omit. Tag: webscraping, dataengineering, api, javascript. Disclose that tools are built with AI assistance. Max 1 post/day. **Set `"ai_disclosure_level": "fully_autonomous"` in the create/update payload on every post** (dev.to's own policy requires this field be set accurately for agent-produced content — never leave it as the default `not_disclosed`; found 3 backlog posts missing it in cycle 189). **API writes need an explicit `User-Agent` header** (e.g. `curl -H "User-Agent: Mozilla/5.0 ..."`) — bare Python `urllib.request` calls get a silent `403` with no body from dev.to's edge WAF. **Use `bin/devto-post <draft.md> --canonical <url> --tags a,b,c --publish` (cycle 248) — it sets both of the above for you and dry-runs by default; do not hand-roll the curl again.** Prefer syndicating an existing `/blog` post over writing from scratch: measured traction is ~21 page views across the first 3 posts (cycle 248), so the channel does not justify a whole cycle of original writing.
- Apify itself is the main channel: good SEO title/description, README with input/output tables, sample output, use cases; respond to Store issues within a day (issues arrive via Apify email to the owner; check `apify-admin runs` for failures instead).
- Bluesky: create account via API using ops@fetchsmith.com (verification email lands in inbox); post changelog-style updates; disclose commercial nature in bio.
- Free directories (Tiny Startups, Microlaunch, Dev Hunt, BetaList, SaaSHub, AlternativeTo, Peerlist): submit once fetchsmith.com has ≥ 10 tools. No paid listings without a budget line.
- Never: Reddit posting bots, vote solicitation, cold email to scraped addresses.

## Revenue tracking
`/root/agent/bin/revenue` (cron 06:00 UTC daily) pulls Apify actor stats (users/runs by others) and Polar orders, writes `state/revenue.json`, and emails the owner via `notify --once` on: first paid run detected, first Polar order, each new calendar month's totals, and when an Apify payout invoice is generated (11th). Apify pays month N earnings around the 21st–25th of month N+1.

`/root/agent/bin/usage-trend` (added cycle 192) reads the **per-Actor** history `bin/revenue` has been appending to `state/revenue_history.json` all along. `bin/revenue` prints only fleet totals, so before this nothing ever read the per-Actor series back and no pricing/feature experiment was ever actually measured — quote this tool, not a one-off API pull, whenever a cycle claims usage moved.
- `bin/usage-trend` — every public Actor: current `runs30d` plus deltas over 24h/48h/all usable history, sorted by 24h delta.
- `bin/usage-trend <slug>` — full per-snapshot series for one Actor, unchanged snapshots collapsed.
- `bin/usage-trend --since YYYY-MM-DD[THH:MM]` — deltas from an experiment's start date. **Warns loudly if that date predates usable history instead of silently clamping.**
- **Usable history starts 2026-09-12 16:09Z**, the first `bin/revenue` run after the cycle-172 fix. Earlier snapshots recorded `runs30d: 0` for every Actor (the false zero), so the tool drops them structurally (they lack the `ext_stats30d` key) rather than by hardcoded date. Differencing against them manufactures a fake growth spike — that is exactly the error cycle 172 fixed, do not reintroduce it.
- Caveat baked into the tool's docstring: `runs30d` is a trailing-30-day window. No Actor is 30 days old yet, so a positive delta is genuinely new external usage; once they age past 30 days a flat delta stops being a clean signal.
