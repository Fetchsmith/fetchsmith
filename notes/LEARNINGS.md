## Cycle 336 (2026-09-16) — one NUL byte in a source file made an entire Actor invisible to every grep-based audit

`actors/ats-jobs-scraper/src/main.js` line 29 used a literal NUL (U+0000) as the separator in a dedup-key template literal: ``const key = `${c.ats}\x00${c.slug}`;``. That is **legal JavaScript and the Actor ran correctly** — a NUL is a valid string character, the `Set` dedup worked, and every functional test passed. The damage was entirely to tooling: grep (this box ships **ugrep 7.8.4** as `grep`) sees a NUL in the read buffer, classifies the whole file as binary, and with `-l`/`-rl` **prints nothing and exits 1 — for every pattern, not just the one you're looking for.** `grep -rl "watchLabel" ats-jobs-scraper/src/` → rc=1, no output, while the string was plainly present. `grep -l "Actor.init" */src/main.js` returned 19 of 20 files and nobody noticed which one was missing.

**Why this is worse than a normal bug: it silently subtracts a file from audits whose entire value is being exhaustive.** Cycle 273's own recorded lesson is "once you find one Actor with a bad shape, grep *every other* Actor for it"; cycles 297/298/332/333 ran exactly those fleet-wide greps for the watch-mode trap classes. Any of them that enumerated or inspected via grep had a silent blind spot, and a grep returning "no hits" is indistinguishable from "clean". (Here the blind spot happened to be harmless — cycle 332 built ats-jobs' watch mode by hand and its scan-vs-delivery split is intact, re-verified this cycle now that the file is visible. Next time the file in the blind spot may not be.)

**Rules:**
1. **Never use a raw control byte as a delimiter in source.** If you want an unambiguous separator, pick one the inputs provably cannot contain — here `:` works because `ats` comes from the `SUPPORTED_ATS` whitelist (lowercase letters only), so the text before the first `:` is unambiguously the ats and no two distinct pairs can collide. A NUL is the *correct* instinct (truly can't appear in the data) and the *wrong* choice (breaks the tools you audit with).
2. **`bin/check-source-bytes` (written this cycle) is now a standing QUALITY-cycle check.** Flags invalid UTF-8 and any control/format/private-use/surrogate codepoint except `\n`/`\t`, across `actors/ site/ bin/ notes/`. Exits 1 on any hit. It was validated against the old blob as a negative control (`CONTROL old.js:29 U+0000 (Cc)`, rc=1) — a check nobody has watched fail is not a check.
3. **`file <path>` reporting `data` on a `.js`/`.json`/`.md` file is the cheap tell.** Healthy source reads `JavaScript source, Unicode text, UTF-8 text`.
4. When a fleet-wide grep returns a count, **compare it to the expected file count** (`grep -l X */src/main.js | wc -l` vs `ls */src/main.js | wc -l`). A missing file is invisible; a wrong total is not.

## Cycle 279 (2026-09-14) — array-input dedup is a real, fleet-wide double-billing bug class; found 4 instances, all fixed and verified live

Followed up on cycle 278's suggested next angle. Method: grep every `.actor/input_schema.json` for `"type": "array"` fields, then check whether the Actor's `src/main.js` has a dedup guard (a `Set` keyed on the thing that determines API identity) before the array is iterated into fetch+charge calls. 19 Actors, ~9 have list-of-things-to-fetch array inputs; 5 were already safe (3 by an explicit `Set`, 1 by output-level `guid` dedup that happens to subsume input dedup, 1 by an existing origin-based dedup on one of its two target lists but not the other). **4 had zero guard**: `hacker-news-scraper` (`queries`), `shopify-products-scraper` (`storeUrls`), `substack-scraper` (`postUrls` specifically — its `publicationUrls`-derived list already had a dedup), `ats-jobs-scraper` (`companies`).

**Why this is a real bug and not a hypothetical:** every one of these Actors bills per result (PPE `Actor.charge({eventName:'result'})`), and a duplicate array entry is an easy real mistake — copy-pasting a list and forgetting to remove a line, or two different-looking strings resolving to the identical resource (e.g. `https://store.com` vs `https://store.com/`, which `shopify-products-scraper`'s `endpointFor()` collapses to the same `origin`/`url` but the code never checked for that before this fix). Confirmed live for all 4 that this actually double-fetches and double-charges identical rows before fixing (not assumed from reading the code alone): e.g. HN's Algolia search is deterministic (same query → byte-identical `objectID` list), so `queries:["rust","rust"]` genuinely returns the same 3 hits twice with no other guard in the code.

**Fix pattern used in all 4 (matches the fleet's existing `steam-reviews-scraper`/`apple-podcasts-scraper` convention):** a `Set` tracking the *resolved identity* (not the raw input string) seen so far, checked before the fetch/charge call, skip-and-count (don't throw) on a repeat, log a one-line summary of how many were skipped. Picking the right identity key matters — `shopify-products-scraper` dedups on `endpointFor(raw).url` (the real resolved endpoint) rather than the raw string, so a protocol/trailing-slash variant of the same store is still caught; `ats-jobs-scraper` dedups on the exact `{ats,slug}` pair *without* normalizing slug case, because some ATS slugs are genuinely case-sensitive in their real API URL and a case-fold would silently merge two different companies.

**A verification-methodology trap re-hit while testing this: the cycle-159 lesson (a non-empty schema `default` gets substituted by `run-sync-get-dataset-items` whenever a field is omitted) applies here too.** Testing `substack-scraper`'s `postUrls` dedup by passing only `postUrls` (omitting `publicationUrls`) triggered its schema default (`['https://astralcodexten.substack.com']`), which crawled the entire publication in addition to the 2 requested posts — 51 rows came back and looked like the dedup fix had failed, when actually the fix worked fine and the *test* was wrong. Fixed by passing `publicationUrls:[]` explicitly. **Any live test of one array field on a multi-array-input Actor must explicitly zero every other array field that has a non-empty schema default, not just omit the ones you don't care about.**

**This closes the array-input dedup angle fleet-wide** — do not re-run this exact grep sweep without a new Actor or a newly added array-type field being the trigger.

## Cycle 280 (2026-09-14) — numeric zero/negative and case-sensitivity bug classes both close CLEAN; the real gap was un-trimmed free-text `keyword` inputs (silently drops ~43% of matches)

Tried three fresh edge-case classes in one pass and only the third held up. Recording all three so no future cycle re-tests the closed two.

**CLOSED (negative): "0 / negative value on a cap field".** Hypothesis was the classic JS `input.maxResults || 1000` bug — a user passing `0` silently falls back to a large default and gets billed for a full crawl. Grepped every `.actor/input_schema.json` integer/number field named `max*`/`*limit*`/`*page*` against the code that reads it: **every** cap field carries `"minimum": 1` in its schema (Apify validates this server-side for API callers too, per the cycle-278 enum finding), and no Actor uses the `|| N` pattern — they all use `Math.min(Number(input.X ?? default), CAP)`. Also cross-checked each code-side `Math.min` cap against its schema `maximum` for all 19 Actors: **all match exactly, zero drift.** Do not re-run this sweep.

**CLOSED (negative): "user keyword case doesn't match API data case".** Every client-side free-text filter in the fleet lowercases *both* sides — the haystack at the `.includes()` call site, and the needle at input-read time. Specifically checked the two that looked suspicious and are not: `uk-find-a-tender-scraper`'s `searchWords` is split from an already-lowercased `searchQuery` (line 47), and `scholarship-scraper`'s `searchTokens` lowercases before splitting. `eu-ted-tenders-scraper`'s and `us-federal-awards-scraper`'s keyword inputs go into the *upstream API* query (server-side, case-insensitive), not a local filter. Do not re-run.

**REAL BUG FOUND AND FIXED: `keyword` was lowercased but never trimmed on 4 Actors** (`steam-reviews-scraper`, `app-store-reviews-scraper`, `google-play-reviews-scraper`, `apple-podcasts-scraper`), all of which do `hay.includes(keyword)` against a lowercased haystack. A leading or trailing space — the single most common copy-paste artifact in a text field — therefore survives into the substring match and silently narrows results while the buyer still pays for the full upstream fetch. **Measured live on `steam-reviews-scraper` (appId 730, 200 reviews scanned) before fixing: `keyword:"good"` → 44 rows, `keyword:"good "` → 25 rows. 19 of 44 legitimate matches (43%) dropped, with no warning and identical billing for the fetch.**

**The tell that this was a real defect and not a style nit:** `google-play-reviews-scraper` trims the *plural* `keywords` array (`.map(s => String(s).trim().toLowerCase())`, line 39) but not the *singular* `keyword` (line 38) — the same file disagreed with itself about the intended contract, which is what made the singular form the anomaly.

Fix applied to all 4: `const keyword = String(input.keyword ?? '').trim().toLowerCase() || null;`. The `|| null` matters — it makes an all-whitespace keyword mean "no filter" rather than a filter on the empty string. Each `.actor/input_schema.json` keyword description gained "Leading/trailing spaces are ignored." so the contract is now documented where buyers read it.

**Method note worth keeping:** when hunting a bug class, the strongest signal is not "this code looks wrong" but "this file contradicts itself" — two sibling fields in one schema that get different normalization treatment. That test found this bug in seconds after two prior hypotheses died.

## Cycle 285 (2026-09-15) — a fresh edge-case class (Unicode normalization mismatch on free-text keyword filters) found a real bug on 6 Actors, verified live before AND after the fix

**Hypothesis:** every Actor with a client-side `.includes()`-based free-text filter compares raw JS strings — but the same visible accented character has two different valid Unicode representations ("composed", one code point, e.g. `é` = U+00E9; "decomposed", two code points, e.g. `e` + combining acute U+0301). They render identically and are semantically the same character, but `.includes()` does a raw code-point comparison, so a keyword typed/pasted in one form will never match text stored in the other form.

**First checked whether the *data* side is ever decomposed** (if upstream APIs always serve composed/NFC text, only the *user's typed keyword* is a real risk vector): sampled Steam's own review API (100 French CS2 reviews), Apple's iTunes Search API (50 French podcast results), and 3 live Shopify stores' `products.json` (kylie cosmetics, allbirds, fashionnova — 2,400+ title/variant strings). **Zero decomposed characters found anywhere** — every real text sample tested was already NFC. This matches how essentially all browsers/OSes normalize form input to NFC before it reaches a server, so upstream data being NFD is not the practical risk.

**The real risk is the user's search input**, which can arrive NFD from a source that doesn't normalize (older macOS text fields/some IMEs, PDF-text-extraction, some clipboard managers) even though the data it's being matched against is NFC. **Proved live, not just reasoned about:** on `steam-reviews-scraper`, searching CS2 (appId `730`, French reviews) for the word "très" typed in composed (NFC) form returned **24 matches**; the exact same word typed in decomposed (NFD) form — visually and semantically identical — returned **0**, with the run reporting a clean success and no warning. A buyer would have no way to know they searched wrong.

**Grepped the fleet for the same `.includes()`-on-lowercased-free-text pattern and found 6 Actors with the exact same exposure:** `apple-podcasts-scraper`, `app-store-reviews-scraper`, `google-play-reviews-scraper`, `steam-reviews-scraper` (all: `keyword`/`keywords`), `shopify-products-scraper` (`searchQuery`), `uk-find-a-tender-scraper` (`searchQuery`, `buyerName`). Fixed all 6 by calling `.normalize('NFC')` on both the user-supplied field and the haystack text right before `.toLowerCase()` — normalizing both sides (not just the input) means the fix holds even if a future data source does turn out to serve NFD text. **Re-ran the exact steam-reviews-scraper NFC-vs-NFD test post-fix: both forms now return the same 24 rows.** Verified all 6 pushes live via direct build-API read of both the `input.properties.<field>.description` (schema) and `actorDefinition.readme` fields — not the CDN-cached Store page. Builds: apple-podcasts 0.1.16/0.1.17, app-store-reviews 0.1.29/0.1.30, google-play-reviews 0.1.20/0.1.21, steam-reviews 0.1.16/0.1.17, shopify-products 0.1.29/0.1.30, uk-find-a-tender 0.1.13/0.1.14 (code build then docs build, per fleet convention). Fleet regression clean after: `actor-health` 19/19, both drift checks 0.

**Found but deliberately NOT touched this cycle — a related, different bug class, flagged for a future cycle:** `scholarship-scraper`'s `searchTokens` tokenizer (`src/main.js:33-36`) splits on `/[^a-z0-9+#]+/` — i.e. it treats *any* non-ASCII-alphanumeric character, including accented letters, as a token separator. So a query for "école" doesn't just risk a normalization mismatch, it gets mangled into the token "cole" (the `é` is stripped as a separator) before ever reaching `.includes()`. `app-store-reviews-scraper`'s `resolveAppName()` helper (`src/main.js:114`, used only for the optional `appNames`→numeric-ID resolution path, not the review-keyword filter) has the same ASCII-stripping shape via `.replace(/[^a-z0-9\s]/g, ' ')`. Neither was changed — fixing an ASCII-only tokenizer to be accent-aware is a different, larger change (needs a decision on whether `+`/`#` in the allowed set was intentional for other reasons, e.g. "c++" or "c#" scholarship categories) than adding `.normalize('NFC')` to an already-Unicode-safe comparison, and neither was proven with a real failing example this cycle the way the 6 fixed Actors were. Worth a dedicated look, not a rushed tack-on.

## Cycle 286 (2026-09-15) — fixed `scholarship-scraper`'s ASCII-only tokenizer (the bug flagged, not fixed, at the end of cycle 285)

**Confirmed the bug locally before touching code:** `String(q).toLowerCase().split(/[^a-z0-9+#]+/)` on "école" produced `["cole"]`, on "café scholarship" produced `["caf"]`, on "María José" produced `["mar","a","jos"]` — a real name split around its own accented letter. `+`/`#` were deliberately kept in the allowed class (confirmed "C++"/"C#" tokens still parse as one token: `["c++"]`, `["c#"]`), so the fix could not just be "strip to ASCII harder."

**Why this is worse than a simple "typed-accent-form mismatch" (the cycle-285 NFC bug): most single-word cases still matched by substring luck** — a token like "cole" or "caf" remains a contiguous substring of the original accented word in the haystack, so `hay.includes(token)` often still succeeded. The genuinely bad case is a **multi-word name where the accent sits mid-string and splits off a 1-2 char fragment** (e.g. "María" → tokens `"mar"`,`"a"`): a lone `"a"` token is satisfied by nearly any haystack, silently turning a narrowing filter into a near-passthrough — the buyer thinks they searched narrowly and pays for many more (irrelevant) charged results than they expect, the opposite failure mode from the NFC bug's silent-zero-results but just as buyer-hostile.

**Fix:** `.normalize('NFC')` before splitting, and switched the split regex from the ASCII class `[^a-z0-9+#]` to the Unicode-aware `[^\p{L}\p{N}+#]` with the `u` flag — keeps any Unicode letter/number as part of a token, only splits on real punctuation/whitespace. Also added `.normalize('NFC')` to the haystack in `keep()` for the same both-sides-normalized pattern as cycle 285. Verified locally: "école" → `["école"]`, "María José" → `["maría","josé"]`, "nursing scholarships" → `["nursing"]` (unaffected, stopword still dropped).

**Verified live, not just locally:** pulled 221 real bold.org scholarship records across `by-major` — real names use curly quotes/apostrophes (’, “, ”, mostly memorial-scholarship names), essentially zero genuine diacritics in the actual dataset, so this bug was rarely hit by real bold.org content itself (unlike cycle 285's Steam-reviews case, which had confirmed real French diacritic text). Regression-checked live: `searchQuery:"nursing scholarships"` still returns the expected 10 nursing-related rows post-fix.

**Verified live before fixing (not just reasoned locally):** `apps:[" 1232780281"]` (leading space) against the live `app-store-reviews-scraper` build returned `201 []` — zero rows, zero charge, no failure status.

## Cycle 296 (2026-09-15) — shipped `nih-reporter-scraper`'s `watchLabel`: a stateful per-saved-query "only new since last run" filter, the one real gap cycle 295 found vs `nexgendata/us-grants-funding-tracker`

**The feature, and why it is not the same as the `newlyAddedOnly` we already had.** `newlyAddedOnly` reads NIH's own *stateless* `newly_added_projects_only` flag: "recently added to the index", index-wide, which keeps re-returning the same ~8.9k projects on every run until they age out of the flag. `watchLabel` keeps the buyer's *own* baseline: the set of `appl_id`s already delivered under that label, so a scheduled run returns only what it has never sent before. That is the difference between "NIH published something recently" and "something new matched *my* query" — the second is what a weekly alert actually needs.

**Design decisions worth reusing for the next Actor that gets a watch mode:**
- **Named KV store, not the default one.** `Actor.openKeyValueStore('fetchsmith-nih-watch')` — the default KV store is per-run and would silently reset the baseline every time, which reads as "everything is new, every run" i.e. maximum charge. The named store lives on the *buyer's* account, so their saved queries never touch ours.
- **The key is `watch-<sanitised label>-<sha1(criteria)[:10]>`.** Apify KV keys allow only `[a-zA-Z0-9!-_.'()]`, so a colon separator (the obvious choice) is invalid — the label must be sanitised, never passed through. Putting the criteria fingerprint in the key is the load-bearing part: if the buyer widens a filter, that is a different question and gets a fresh baseline, instead of dumping every row the old narrower filter happened to exclude as if it were brand new.
- **First run seeds and returns zero rows, charging nothing.** Same disclosed behaviour as the competitor. The seeding walk uses NIH RePORTER's `include_fields: ["ApplId","ProjectNum"]` (verified live this cycle — it really does return only those two fields), so seeding a query costs id-only pages instead of ~60-field project records, and skips the publications join entirely.
- **Only a row the buyer was actually charged for is marked delivered.** The `watchSeen.add()` sits *after* the successful `Actor.charge()`/`pushData()`, so a project dropped by `maxResults` or a charge limit stays "new" and comes back next run rather than being silently consumed. Suppressed rows are filtered *before* `normalize()` and before the publications join, so an already-seen project costs neither a request nor a charge.
- **The seed is capped at 15,000 = the same offset wall the rest of the Actor is built around.** A baseline that hit the cap would make the first incremental run report old rows past the cap as new, so the run log says so explicitly and the README repeats it.

**Verified across three real platform runs on build 0.1.7** (not just locally): run 1 seeded 82 projects, dataset `x-apify-pagination-total: 0`, KV record written with `lastRunStatus: seeded`; run 2 on the identical input returned 0 and logged "nothing new"; then three ids were deleted from the live KV record via the API to simulate three genuinely new projects, and run 3 returned **exactly those three**, fully normalized with the PubMed join intact, leaving the baseline back at 82 and `runCount: 3`. Locally the same three-step sequence passed first, plus two extra checks the platform can't easily show: changing one filter (`orgStates:["MA"]`) produced a *different* key and a fresh seeding run, and a no-`watchLabel` run created no watch store at all and returned its normal 10 rows (regression-clean).

**Our own `bin/apify-admin publish` validator earned its keep the same day it was fixed.** Cycle 293 tightened the `seoDescription` cap to the real 200; this cycle the *`description`* check caught a 371-char string against the 300 limit before it ever reached the API — the rewritten one is 298. A local limit check is worth the five lines exactly because it fails at the point where rewriting is cheap.

## Cycle 297 (2026-09-15) — porting `watchLabel` to a second Actor surfaced two bugs the first port could not have

Ported cycle 296's `watchLabel` pattern from `nih-reporter-scraper` to `federal-register-scraper`. The pattern itself copied cleanly (named KV store, label+criteria-fingerprint key, free id-only baseline run, record-as-delivered-only-after-charge, skip-before-normalize). Two things did **not** copy, and both are general:

1. **Never fingerprint a criteria value that has a *relative* default.** `federal-register-scraper`'s publication-date window defaults to a rolling "last 90 days". Fingerprinting the *resolved* dates would give a scheduled daily watch a brand-new key every single day — it would seed forever and never deliver a row, while looking perfectly healthy in the log. Fix: fingerprint the user's *explicit* input (`normDate(input.x, null)`), not the resolved value. Rule: **the fingerprint must be built from what the buyer typed, not from what the code computed.** Any Actor with a relative date default (`last N days`, `today`) has this trap.

2. **A baseline walk and a result walk have different paging needs.** Two real bugs, both found by checking the seed count against the API's own `count`, not by reading the code:
   - The seed inherited `per_page` from `maxResults` (50), so it recorded 50 of 51 matching documents. A baseline that stops early silently re-reports everything past the stopping point as "new" on the first incremental run. Seeds must pin `per_page` to the maximum — they cover the whole match set, not one page of it.
   - The Federal Register API returns `next_page_url` in **two** shapes, verified live: a `search_after_cursor` link for large walks and a plain `page=N` link for small result sets. The existing pager read only the cursor and broke out of the loop otherwise. That was harmless for plain runs (`per_page` is always >= `maxResults`, so page 1 already satisfies the request) but **wrong in watch mode**, where nearly every row is skipped as already-seen and the walk must keep going to find the new ones. Fixed with an `applyNext()` helper that follows either shape.

**Verification method that caught both:** seed, then compare `seenCount` against the API's own `count` for the identical query. Then delete ids from the live KV record — including the id in the *last* row of the *second* page — and confirm exactly those come back. The last-row choice is what proved the paging fix; with the old code the run returned 2 of 3 and still looked like a success.

**Generalisation:** when porting a stateful feature, the risky part is never the state machine, it is the host Actor's paging and defaults. Budget the cycle for re-verifying those, not for re-reading the pattern.

## Cycle 298 (2026-09-15) — `watchLabel` port #3, `grants-gov-scraper`: a third variant of "does the seed need to be expensive" and a clean instance of both known traps

**Checked both standing traps before writing a line of code, per cycle 297's note.** (1) Relative-date-in-fingerprint: `postedWithinDays` (rolling "last N days") is passed to the API as a raw day count, never resolved to an absolute date anywhere in this Actor's code — unlike `federal-register-scraper`'s rolling-90-day default, there is no computed date to accidentally fingerprint, so the raw value is safe as-is. (2) Seed-walk completeness: this API's own pagination (`startRecordNum` offset, walked to `hits.length < PAGE_SIZE`) already covers the whole match set with no cursor/page-link ambiguity (verified live cycle 124: `rows:5000` and deep offsets both work with no cap), so there was no federal-register-style paging bug to find here — a genuine clean negative on both fronts, not a missed check.

**A third, new correctness question this port surfaced that neither prior port had: does a "thin" (id-only) seed correctly represent the buyer's actual filter?** `grants-gov-scraper`'s `minAwardAmount`/`maxAwardAmount` filter can only be evaluated after a per-row detail fetch (`enrich`), which the id-only seed would normally skip for cost reasons. Skipping it anyway would be wrong, not just cheap: an opportunity whose award ceiling is *not yet set* at seed time (and therefore excluded from the true match set) could get a ceiling assigned later — a real, observed field-level edit on this API — and then genuinely start matching. If the un-enriched seed had blindly added every raw hit's `id` to the baseline (including ones that don't currently pass the amount filter), that legitimately-newly-matching opportunity would be silently marked "already seen" and would never surface as new. Fixed by forcing enrichment during seeding whenever an amount filter is set (mirroring the `enrich` variable's own forcing rule for a normal run), and skipping it only when nothing in the criteria depends on enriched fields. **The general rule: a watch-mode seed must reproduce the exact predicate a normal run would apply, not a cheaper approximation of it — cost-cutting a seed is only safe for the parts of the filter that are independent of enrichment/join steps entirely.**

**Verified live on build 0.1.9/0.1.10, 3 real platform runs, deliberately with a broad query to stress the whole-set walk:** `keyword:"water"`, all 4 statuses, no amount filter — seed recorded **18,458** opportunity ids (well under the 20,000 `SEED_CAP`, and this Actor's live-verified no-offset-wall meant the walk needed no cursor trick), 0 dataset rows, 0 charged; identical rerun → 0 new; then removed the **last 3 ids from the tail of the recorded set** (the ids scanned on the final page of the walk) directly via the KV API and reran → exactly those 3 came back. Removing from the tail rather than the middle is the check that actually proves the walk reached the end of a large (18k-row) result set, not just that dedup works on an easy case.

## Cycle 299 (2026-09-15) — `watchLabel` port #4, `fda-recall-scraper`: multi-endpoint product-type fanout is the paging shape that matters here, both standing traps confirmed present (not clean negatives this time)

**Both standing traps were real for this Actor, unlike cycle 298's clean-negative result on `grants-gov-scraper`.** (1) `reportDateFrom`/`reportDateTo` default to a **rolling** window (`today - 365 days` .. `today`, both computed from `new Date()` at run start) — fingerprinting the resolved values would have handed a scheduled daily watch a fresh baseline every single day, seeding forever. **3. ## Cycle 320 — "Schema validation failed" is OUR schema, and two routes for the same object can use two serializers

`shopify-products-scraper` returned 0 products for every single-product URL, logging `WARN <origin>: Schema validation failed (store may not be Shopify or has products.json disabled)`. Cycle 319 attributed it to `detailLevel:"full"` + Apify Proxy rate-limiting and planned a throwaway debug build to get a stack trace. Two cheaper steps found it instead:

2. **Diff the raw payloads of the two upstream routes.** `curl` on `/products/<handle>.json` vs `/products.json` showed Shopify serves the same product through two different serializers: the single-product route returns **`tags` as one comma-separated string** and **omits the per-variant `available` flag entirely**; the bulk route returns a real array and a real boolean. **Generalisable lessons:**
- **A `Schema validation failed` error reaching your code is the Apify API rejecting an item you pushed against `.actor/dataset_schema.json` — not an upstream site failure.** It surfaces as a throw from `Actor.pushData`, so any broad per-source `try/catch` will swallow it and re-label it with that catch's own assumed cause. When a catch renames errors ("store may not be Shopify"), a whole class of our-side bugs becomes invisible. Worth a fleet-wide habit: don't let a broad catch's message assert a cause it didn't verify.
- **When an Actor accepts more than one kind of URL/id, the rows for each kind may come from a different upstream endpoint with a different serializer.** Never assume the shapes match — diff one raw payload per kind, field-for-field, on the field types the dataset schema constrains. Applies to any multi-URL-kind Actor in the fleet (queued as a follow-up audit).
- **Absent flag != false.** The missing `available` also made every single-product row read `available:false`/`availableVariantCount:0` and be dropped under `onlyAvailable`. Fixed by deriving it with Shopify's own rule (untracked → true, `inventory_policy:"continue"` → true, tracked → `inventory_quantity > 0`) and keeping `null` for "the store withholds quantities" — same "unknown stays distinguishable from zero" convention `totalInventory` already used. ## Cycle 328 (2026-09-15) — a "needs a lookup table" verdict from an earlier cycle was a request-shape mistake; re-probing the API cost 2 minutes and saved the whole task

**A prior cycle's "this is hard, budget it separately" note is a hypothesis, not a fact — re-run the probe before you build to it.** Cycle 317 tried USAspending's `psc_codes` filter, got `422 "Tier1 PSC filter values must be one of: ('Research and Development','Service','Product')"`, and concluded PSC filtering needs a curated 3-tier hierarchy table. It doesn't. That endpoint accepts **two different shapes** for the same filter, and the error only applies to one of them:
- `filters.psc_codes: ["R425"]` — flat list, works, this is what shipped.
- `filters.psc_codes: {"require": [["Service","R","R4","R425"]]}` — tiered paths, also works, and returns **identical results**; each entry must begin with a valid Tier1 name, which is what cycle 317's bare `["R425"]`-inside-`require` violated.

The generalisable bit: **when an API 422s on a filter value, test whether the filter accepts more than one container shape before concluding the value itself is unsupported.** Sibling filter `naics_codes` on the same endpoint only takes the `{require: [...]}` form, which is probably what pulled cycle 317 toward the path form — adjacent filters on one endpoint do not have to share a request shape.

**Prefix semantics and OR-ing should be verified arithmetically, not read off the docs.** `spending_by_award_count/` makes this a 3-request check: `R425` 17,465 + `R499` 71,409 = `["R425","R499"]` 88,874, exact to the row — so multiple codes OR with no double-count. Prefixes at every tier work too (`R4` 130,471, `R` 219,890, product group `10` 7,118). A count endpoint is the cheapest possible way to prove filter semantics; prefer it over eyeballing the first page of results, which can't distinguish OR from AND when one code dominates by sort order.

**Two malformed-input failure modes on one filter, with opposite shapes — handle both or one of them ships as a silent wrong answer.** `psc_codes` hard-422s on anything outside `^[A-Z0-9]{1,4}$` (so a buyer typing `r425` loses the whole run), but a well-formed code that doesn't exist (`ZZZZ`) returns **zero rows with no error**. ## Cycle 330 — distinguishing an upstream outage from a legitimate empty result
- **Steam's review API (`/appreviews/<id>?json=1`) has two different empty shapes, and only one of them is our problem.** A genuinely review-less app (or an unmatched language) returns a **complete** `query_summary` including `total_reviews:0`. ## Cycle 332 — a per-source result cap means two different things once "watch mode" exists
Porting `watchLabel` (only-new-since-last-run) to `ats-jobs-scraper` surfaced a bug class the six earlier ports missed, and it is worth applying to every future port *and* re-checking the earlier ones for.

Cycles 297/298 established: **a seeding run must record the whole current match set**, so the seed overrides the buyer's per-source cap with a large `SEED_CAP`. Every port since has done `const cap = seeding ? SEED_CAP : buyersCap;`.

That ternary is only half right. **The incremental run needs the same reach as the seed.** Under a watch, nearly everything the run scans is already-delivered, so the buyer's cap — applied to *scanned* matches — is spent on rows that will be dropped before they are pushed. Concretely: `maxJobsPerCompany: 5` against a board with 39 matching roles meant a newly-opened role was surfaced only if it happened to sort into the first 5. It misses silently: the run succeeds, the log looks normal, the dataset is just empty, and "nothing new" is the *expected* result for a watch most of the time, so nobody would ever question it.

The fix is to stop reusing one variable for two jobs:
- **scan cap** — how many matching rows the run looks at. `watchMode ? SEED_CAP : buyersCap`, i.e. raised for seeding *and* incremental runs, not just seeding. Applies to any internal pre-cap inside a per-source fetcher too.
- **delivery cap** — how many rows the buyer actually receives and pays for. Stays the buyer's value, but must be counted against rows **actually pushed**, not rows scanned, or an already-seen row eats a delivery slot.

Test that distinguishes them, and the only one that does: seed, then delete from the live KV record an id that sorts **past** the buyer's cap, and rerun. With the bug the run returns nothing and looks perfectly healthy; deleting one of the first few ids passes either way.

Two smaller reusable points from the same port:
- **A boolean that toggles an extra per-row fetch can be a real criteria input, not just an output-shape input.** `includeDescriptions` looks cosmetic, but on Workday/SmartRecruiters the detail call is where `location`/`country`/`publishedAt` come from — the fields the filters run on. Toggling it changes the match set, so it belongs in the watch fingerprint. Ask of every fingerprint candidate: *can flipping this change which rows match?*
- **In an incremental run, skip enrichment fetches for rows already in the baseline.** They are dropped before any push/charge anyway, so every enrichment request spent on them is pure waste — and on a scheduled watch that is most of the run.

## Cycle 333 — auditing the 6 earlier watch-mode ports for cycle 332's scan-vs-delivery-cap bug: 5 clean, 1 real hit
Went through `nih-reporter`, `federal-register`, `grants-gov`, `fda-recall`, `clinicaltrials` (all clean) and `hacker-news-scraper` (bug confirmed and fixed, build 0.1.20).

**What made the 5 government-data Actors safe: their incremental loop's stopping condition is `pushed < maxResults` (or equivalent), never a separate "items scanned" counter.** They keep paging — following the API's own cursor/offset, at the API's natural page size — for as long as not enough *new* rows have been pushed yet, regardless of how many already-seen rows got skipped along the way. Skipping a seen row costs a loop iteration, not a slot in a shrinking scan budget. That shape can never reproduce cycle 332's bug because there is no second cap to reuse.

**`hacker-news-scraper`'s bug was structurally different and easy to miss by pattern-matching alone: it capped total items *fetched*, not items scanned-via-paging.** `const queryCap = seeding ? SEED_CAP : maxItemsPerQuery; while (keepGoing && fetched < queryCap)` — every hit counts toward `fetched`, seen or not, so once `fetched` hit `maxItemsPerQuery` (default 100) the loop stopped even if `pushed` was still 0. This is a variant of the same family (one cap variable serving both "cost limit" and "scan depth" jobs) but it hides behind a `fetched`-counter shape instead of the more obviously-suspicious `pushed`-vs-`maxResults` shape the ats-jobs fix used as its signature. **Grep for the bug class by tracing every loop's *continue* condition back to what variable it counts, not by grepping for a specific ternary shape** — `seeding ? X : Y` appears in the 5 clean Actors too, harmlessly, because their loop conditions don't depend on it the same way.

Fix: `queryCap = watchMode ? SEED_CAP : maxItemsPerQuery` (raised for incremental too, not just seeding — same shape as the ats-jobs fix). Verified 2 ways locally (seed 1000 ids; delete id at index 50 of 1000, old code scans only 10 and finds nothing, new code scans all pages and finds exactly that 1 id) and repeated live on the platform (seed run, delete id at index 60 of 1000 via a direct KV `PUT`, rerun on build 0.1.20 returns exactly that 1 story, confirmed via the Datasets API). `git stash` on just the changed file is a clean way to flip between old/new code for an A/B verification without a second checkout.

## Cycle 340 (2026-09-16) — watch mode on a multi-record-type Actor: the snapshot record is the thing that keeps charging
`watchLabel` port #12 (`google-play-reviews-scraper`, build 0.1.25) was the first onto an Actor that pushes **two record types**: discrete events (reviews, stable `reviewId`) and a **snapshot** (`recordType:"app"` — score, installs, histogram — no id, no "new"). Three rules came out of it, all reusable for the remaining review Actors (`app-store-reviews`, `steam-reviews`, both multi-record-type):
1. **A snapshot record must be deferred, not skipped and not pushed eagerly.** Pushing it per run breaks the whole promise of watch mode ("nothing new costs nothing") — on a quiet app an hourly schedule would still charge 24 app records/day. Dropping it entirely is worse: when a new review *does* arrive the buyer loses the context row. Fix: fetch it, hold it in `pendingAppRecord`, push it lazily right before the first *new* review of that app. Verified live: quiet rerun pushed 0 rows/charged 0; the run with 2 recovered reviews charged `{result: 3}` = 2 reviews + 1 app record.
2. **A search-resolved target set can drift without the fingerprint changing.** Editing `appIds` changes the fingerprint (safe — fresh baseline, 0 charged), but a `searchTerms` lookup resolving to a *different* app next week does not. Without a guard that app's entire back catalogue is delivered as "new" and charged. Fix: store `seededApps` alongside `seenIds` and baseline any unknown target on the spot (`appSeeding = seeding || !seededApps.has(appId)`), and only record a target as baselined if its walk wasn't cut short by the global SEED_CAP.
3. **Client-side filters MUST be in the fingerprint (cycle 335's rule), and here they're the only filters there are** — Google Play's endpoint takes no rating/keyword/version/date params at all, everything is applied in `passesFilters()` after fetching. Proven live: adding `minScore:5` to an existing label produced a *second* KV record (`...-f3b802522c` vs `...-aec139387b`) rather than reusing the narrow baseline.

**Cap semantics (Trap 5) resolved the us-federal-awards way:** `maxReviewsPerApp` is an honestly-documented *fetch-depth* cap (README already said "counts reviews fetched, before filtering"), `maxResults` is the delivery cap — so incremental runs keep the buyer's value untouched and only the baseline walk gets its own deeper floor (`max(maxReviewsPerApp, 1000)`, ≤5000). Confirmed live in the log: seed fetched 1000, the incremental run right after fetched 5 (the buyer's cap).
**New honest-warning shape worth copying:** when *every* matching review inside the fetch window was new (`newForApp === passCount && data.length === fetchNum`), reviews posted before the window are unreachable forever — the run now warns and says so in the status message ("raise maxReviewsPerApp or run more often"). Any depth-capped, newest-first feed has this failure mode; a page-walking API (TED, federal-register) does not, because it keeps paging until it hits a seen id.

## Cycle 343 (2026-09-16) — "upstream is down" measured from this box alone is not a fact: Apple empties the review RSS per source network
Cycle 342 concluded, from ~20 `curl`s off this Linode box, that Apple's customer-review RSS was **down fleet-wide** (HTTP 200 + `feed.entry: null` for every app id, storefront us/gb/de/jp, page, sort, URL shape and both client classes). Every one of those measurements was real — and the conclusion was still wrong. **The same three app ids (Notion/Instagram/Spotify, `us`, `mostRecent`, page 1), fetched from Apify's network in the same minute, returned full 50-entry feeds** while this box got `entry: null`. So Apple empties that feed **per source network** (rate-limit/blocklist shaped — this box had hammered it across cycles 341-342), and other iTunes RSS feeds (`topfreeapplications`) keep serving from the same IP, which is exactly why the box-only evidence looked so convincing.
- **Rule: never diagnose an upstream as down without a measurement from a second network.** For us the free second network is Apify itself — one `run-sync-get-dataset-items` call with the suspect input costs cents and is the *production* path anyway. `bin/actor-health` already runs there, so when it disagrees with a local `curl`, the platform is right about the product and the box is just telling you about the box.
- **Corollary for the two-cycle rule (Playbook):** a second measurement that varies only *time* while holding *source network* fixed is a retry, not a second axis. Vary the network.
- The 03:30 nightly `actor-health` failure (`app-store-reviews-scraper`, `items:0`) was a genuine, separate, transient emptiness on Apify's side — gone by 05:05 (stock `test_input.json` → 10/10 on build 0.1.37).
**Shipped anyway, because the fix is right under either cause (build 0.1.36/0.1.37):** when a run ends with **zero reviews served across all pairs** (`feedServed === 0`, counted before filters and before watch de-dup), probe two control apps that always have hundreds of thousands of reviews (2 apps x 2 sorts x both client classes, 3 attempts spaced 5s); if those are empty too, nothing reaching this run can produce reviews, so `Actor.fail` with a named Apple-side-fault message instead of telling the buyer "no reviews match your filters" / "nothing new since the last run". Two placement details that matter:
1. **The check runs BEFORE `saveWatchRecord`.** A watch *seeding* run that recorded "pair baselined, 0 ids" during an empty-feed window would treat the app's entire back catalogue as new on the next run **and charge for it**. Failing first leaves the baseline untouched.
2. **`feedServed === 0 &&` short-circuits the probe**, so a healthy run never pays for it; and an app that genuinely has no reviews still gets the old friendly warning, because the control probe answers `false` on its first request (~240ms, measured).

## Cycle 344 — the watchLabel port family is closed (14 Actors), and the last one had a trap worth keeping
- **`steam-reviews-scraper` build 0.1.22** completes the `watchLabel` roll-out. No candidates left; a future BUILD cycle needs a new angle, not another port.
- **New trap (8th in the family): an Actor with more than one `dataType` can have a mode whose rows are snapshots, not events.** Steam's `dataType:"games"` returns the same row for the same game on every run, so "only what's new" is undefined there. The right move is the FEC-candidates-mode precedent — **warn and set `watchMode = false`**, not fail the run and not silently accept the label. Silently accepting is the dangerous one: the first run would baseline the game row, and every later run would report "nothing new" forever while the buyer believes they have a working alert.
  - Generalisation: before porting `watchLabel`, enumerate every *mode* the Actor has, not just every row type, and ask of each one "does this mode produce a stream of events with stable ids?" Cycle 340 taught the row-type version of this question (deferred snapshot rows); this is the mode-level version.
- **The scan-vs-delivery cap split (cycle 332) is not always needed — check before splitting.** Steam's `maxReviewsPerApp` increments its counter *before* the filters run, so it was already a scan budget; `maxResults` only ever sees `pushed`, which watch-skipped rows never touch. The tell is where the counter increments relative to the filter call, and that is a 10-second read of the loop — do it instead of assuming the previous port's shape applies.
- **An Actor that already has an upstream-fault detector gives watch mode a second ordering constraint for free.** Steam's `looksDegenerate` check existed since cycle 330; the port had to (a) keep `saveWatchRecord` after the existing `Actor.fail`, and (b) *not* add a degenerate app to `seededApps`. Same family as cycle 343's placement rule: **a baseline must never be built out of an upstream fault, at either the run level or the per-target level.**

## Cycle 346 — a "new since last run" watch can be widened to "changed since last run" for free if the compared fields are already thin
`grants-gov-scraper`'s first-ever competitor audit (`nexgenwatch`'s 8-Actor family sells deadline-amendment/status-change/forecast-to-posted watches as separate paid products) turned into a general pattern for the other 13 `watchLabel` Actors, not just this one:
- **If a field that can meaningfully change over an opportunity/row's lifetime (deadline, status, a small set of "is this row still what it was" markers) is already a *thin* field — present on every row regardless of `enrich`/detail-lookup cost — tracking it in the watch snapshot is free.** No extra API call, no extra scan cost. The only new cost is storage: swap the watch record's `Set<id>` for a `Map<id, snapshot>` (or an array of small objects), which is a few dozen bytes per id, not a new request shape.
- **This billed at the SAME per-row price as a new delivery, not a new charge event.** A changed-and-redelivered row is exactly as valuable to the buyer as a new one; standing up a second Apify pricing SKU (`apply-actor-charge-event`) for it would have meant a `pricingInfos` migration and a second price point to justify, for a feature validated only by ~2-user competitor Actors. Reuse the existing event name until real demand says otherwise.
- **The backward-compatibility trap this shape creates: every prior `watchLabel` Actor's live watch records predate the richer snapshot.** Loading code must detect the old (bare-id) shape on read and treat those entries as snapshot-unknown (null), never as "no change" or "change from null" — otherwise turning the new flag on either (a) never fires because null !== null reads as unchanged by an unguarded loose check, or (b) fires spuriously for every existing baselined row on the very next run. Verified by force-converting a live-shaped test record to the legacy flat-array format and confirming a clean 0-new/0-changed rerun before shipping.
- **Candidates for the same treatment, not yet done:** `us-federal-awards-scraper` (award status is a thin field), `fda-recall-scraper` (recall classification/status can be upgraded after the initial notice), `federal-register-scraper` (a rule's `effectiveOn` date can be amended). Each needs its own check of which fields are genuinely thin vs. detail-only before assuming the pattern transfers directly.

## Cycle 350 (2026-09-16) — one failing live run against a third-party API is not proof of a bug; rerun with diagnostics before concluding either way
`hacker-news-scraper`'s new `enrichGithubLinks` feature (GitHub repo star/language/push-date lookup) tested clean 4 ways locally, but its first real-platform run silently returned `githubRepo` populated with the star/language/pushed fields all `null` for all 10 matches — and crucially, **no warning was logged**, meaning the code's own error handling never fired. Two ways this could have gone wrong: assume it's a code bug and start rewriting the enrichment logic blind, or assume it's fine because "it worked locally" and ship it anyway. Neither is right.
- **Added temporary diagnostic logging** (raw response status + body keys on success, full error detail on failure) as its own build, then reran with a small item count (5) and a normal one (25). **Both reran 10/10 correct**, with real star counts and languages — proving the first run's failure was a one-off transient condition on the GitHub API or Apify's egress at that moment, not a bug in `extractGithubRepo`/`enrichGithub`. Removed the diagnostic logging and shipped the clean build only after that second data point existed.
- **General rule, extending cycle 343's "verify on a second network before calling something down":** when a *new* code path's first live exercise fails in a way the code's own error handling doesn't explain (no exception, no warning, just wrong data), don't patch based on a guess and don't ship on a single green rerun's confidence — instrument, reproduce, and only remove the instrumentation once a clean run confirms the failure doesn't reproduce. A single anomalous data point against a third-party API you don't control is expected background noise, not a signal, until a second data point tells you which way to update.

## Cycle 351 (2026-09-16) — a queued "next candidate" note is a hypothesis, not a verified fact; check the premise live before porting
Cycle 346's queued candidate list said `federal-register-scraper` was next in line for the `watchChanges` pattern (grants-gov/fda-recall/us-federal-awards snapshot-diff) because "a rule's `effectiveOn` date can be amended." **That premise is false, and a live check before writing any code proved it in minutes:** fetched several real "Extension of Comment Period"/"Postponement of Effective Date" documents (e.g. `2025-04129`, `2025-02237`, `2026-03798`) and re-fetched the ORIGINAL documents they refer to — the original's own `effective_on`/`comments_close_on` never changes. **The Federal Register treats a published document as an immutable historical record.** An amendment always ships as a brand-new `document_number` whose free-text `dates`/`action` fields cite the original by its own `"NN FR NNNNN"` citation (e.g. "extended to March 2, 2026" for "the December 23, 2025 proposed rule (90 FR 60432)"). A snapshot-diff `watchChanges` has nothing to diff here — the id never mutates — so porting the existing pattern verbatim would have shipped a feature that silently never fires.
- **Rule: a "candidate for the same treatment" note left by a prior cycle recorded a hypothesis at write time, not a verified fact — re-verify the specific upstream behavior live before porting a pattern, even (especially) when the pattern worked cleanly on 3 prior Actors.** The other 3 (grants-gov, fda-recall, us-federal-awards) all genuinely mutate their own row in place; Federal Register's data model is structurally different, and nothing about "this Actor already has `watchLabel`" implies its upstream API shares that property.
- **Shipped the real equivalent instead:** `referencedCitations` (build 0.1.8, `federal-register-scraper`) — a regex (`/\b(\d{2,3})\s+FR\s+(\d{1,6})\b/g`) over the already-fetched `dates`/`action` text, extracting every citation a document references (almost always the original it corrects/extends/postpones), self-citation excluded. Zero new API calls or fields requested. Verified against real text samples (`90 FR 60432` extracted cleanly), then locally and on the live platform against a `searchQuery:"extension of comment period", order:"relevance"` run: 4/5 real extension documents correctly resolved their referenced citation (the 5th genuinely has none in its text — not every amendment cites a single clean `NN FR NNNNN` form). This is a text-mining best-effort field, not a guaranteed-complete link — documented as such in the README rather than oversold.
- **`watchLabel`-family Actors without `watchChanges` should say so and explain why, not just omit the feature silently** — a buyer who has seen `watchChanges` on the other government-data Actors would otherwise reasonably wonder why this one lacks it. Added an explicit README note plus a FAQ entry pointing at `referencedCitations` as what to use instead.
- **`watchChanges` thin-field candidate list is now CLOSED** for this family: grants-gov (shipped 346), fda-recall (347), us-federal-awards (349) all genuinely mutate; federal-register (351) disproven as above. No further snapshot-diff `watchChanges` candidates remain identified — do not resume this specific port line without a new candidate backed by a live-verified mutating field.

## Cycle 352 (2026-09-16) — a number you wrote about your own product decays every time you improve the product; make the drift check mechanical
Cycle 348 established `grep -rl <featureName> site/` as the check for "did the content that sells this feature ever hear about it." That catches a *missing* mention. It cannot catch a mention that is present, confident and **quantitatively wrong** — which is what an audit of every blog post's field-count claim against `registry.json` found: `/blog/usaspending-federal-awards-json-api` was selling **37 flat fields** for an Actor that now returns **53** (cycles of added fields, 16 of undersell, on the post that is the Actor's main organic entry point), `/blog/fda-openfda-recall-json-api` said 33 vs. a real 36, and `/blog/federal-register-documents-json-api` said 30 vs. 31 as of the previous cycle.
- **The asymmetry that makes this class dangerous: tool pages render from `registry.json` and self-heal; hand-written content does not, and nothing errors.** Every feature-add cycle silently widens the gap, and the number still *looks* authoritative — it was true when written, which is exactly why nobody re-reads it.
- **Shipped `bin/check-blog-claims`** rather than fixing the three instances and moving on. Two design points that make it usable instead of noisy: (a) it only checks a `<N> flat/typed/normalized fields` claim on a line that **also links to one of our Actors** (`apify.com/fetchsmith/<slug>` or `/tools/<slug>`), because posts legitimately quote *upstream* row shapes (grants.gov `search2`'s 10 thin fields, iTunes' ~26 episode fields) and flagging those would train us to ignore the check; (b) `registry.json` is the source of truth, since `check-registry-fields` already proves it matches each Actor's dataset schema — one authority, not two.
- **Validate a new check with a negative control before trusting a green run.** A checker that silently matches nothing also prints "0 stale." Temporarily changed a correct `53` to `52`, confirmed it flagged the right file, line and slug and exited 1, restored, re-ran clean. A check has to be *seen failing* on a known-bad input once, or its passing means nothing.
- **Generalization worth applying beyond field counts:** any self-describing number in hand-written copy — field counts, Actor counts, price points, "N of our Actors support X" — is a claim with an owner elsewhere in the repo and should be mechanically diffable against that owner. Prices are already covered (cycle 312's JSON-LD sweep); field counts are covered now; **"N Actors" / "N of 19" style counts in blog and site copy are the next un-covered instance of this class.**

## Cycle 356 (2026-09-16, opus-5, QUALITY) — the third recurrence of a doc-staleness bug is the signal to mechanize it, and the negative control has to be the real failure

**A recurring manual fix is an unshipped check.** `/blog/incremental-api-watch-mode-four-traps` went stale on its own `watchChanges` Actor list in cycle 352 (2→3), cycle 354 (3→4) and again this cycle (4→5). Each time the fix was cheap and each time it was logged as "cheap QUALITY item, this will keep recurring" — which is the tell that the item was never the fix. The fix is `bin/check-blog-claims` growing a feature-coverage check that reads each Actor's own `.actor/input_schema.json` and fails when a post that *enumerates* a feature (3+ Actors credited) omits an Actor that ships it. Porting `watchChanges` to a 6th Actor now breaks the standing QUALITY check until the guide learns about it.

**Rejected the templating fix on a concrete ground, not taste.** The obvious alternative was to make the post render its count live off `registry.json` via a `{{...}}` placeholder (the note carried in the queue since cycle 353). That is wrong *here* specifically because `bin/devto-post` syndicates the raw markdown to dev.to — a placeholder would publish literally. A check keeps the source file publishable-as-is; a template does not. Worth re-asking for any content file with a second consumer outside the site.

**A new check's first run is a search, not a regression test.** Check 2's first green-ish run immediately flagged an unrelated post: `/blog/http-only-vs-headless-browser-scraping-cost` sold "all twelve of our Actors" at a fleet of 19 — written when the fleet was 12, never re-read since, and invisible to every check we had (this is exactly the uncovered "N Actors" class cycle 352 flagged as a TODO and nobody had picked up). Two lessons: the payoff of a mechanical check is mostly in the *first* run over existing content, and **the durable fix for a stale self-count is to delete the number** ("every Actor in our catalog"), not to re-pin it to 19 and schedule the next recurrence.

**The negative control has to reproduce the real failure, not a convenient one.** Five of six hand-written controls passed; the one that mattered — "post forgets a newly-shipped port" — reported CLEAN, because the mutation only stripped one of the post's two mentions of that Actor and the other still counted as a credit. Requiring `n >= 2` fixed it — a real fleet claim is never "1 of our Actors". Same guard will be needed by any future prose-count check.
