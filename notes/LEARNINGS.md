## Cycle 548 — being the ONLY title-matcher on a query does not mean ranking well on it: proximity is applied BEFORE `attribute`

1. **The highest-value title-edit shape found so far: sole title-matcher + bad proximity.** `apple-podcasts-scraper` was the *only* record in the whole Algolia index with both `podcast` and `publisher(s)` in its TITLE on two queries (nbHits 714 and 611) — and still sat at **p31** on both, buried under ~30 description-only matches, because its token span was 4 ("Apple **Podcasts** Scraper – Episodes, Reviews, Charts & **Publishers**"). Making the phrase contiguous ("… Episodes, Reviews & **Podcast Publishers**") took it to **p1 on both**, same storePosition, same day. Algolia's criteria run `proximity` *before* `attribute`, so a scattered title match loses to an adjacent description match; the attribute advantage only breaks ties among records with equal proximity. Cycles 545/546 found "0 title-matchers = free win"; this is the stronger sibling — "1 title-matcher, and it's us, with span > 0" is a guaranteed p1-shaped win, because there is literally nobody who can outrank us once proximity is equalised. `bin/store-rank --attr` now prints a `*** HIGHEST-VALUE SHAPE` flag when it sees `len(titled) == 1` with `span > 0`.
2. **Prefer a small predicted jump into an EMPTY block over a big one into a crowded block.** The biggest predicted gain this cycle was `podcast api`: nbHits 1129, p286, verified 9-record block, only 7 better storePositions → predicted ~p8. It was rejected, because the only 63-char title that makes "Podcast API" contiguous drops "Publishers" and so costs both p1s above. `--attr`'s predicted rank is capped by the storePosition of everyone already in the block — so a *crowded* block with a flashy predicted jump is worth less than a thin one with a modest-looking one. Rank the opportunity by `who can still outrank me after the edit`, not by the size of the predicted move.
3. **A title edit's side effects are not always losses.** Dropping "Charts" from the title (the deliberate trade, `podcast charts` p45, span 3) did not hurt: that query went p45 → **p36** on description matching alone. And `podcast reviews` improved p26 → **p9** with its span unchanged at 2, presumably from the second literal "Podcast" occurrence adding word-level hits. Simulate spans to avoid regressions (that part worked exactly as predicted on all four protected queries: p44/p62/p19/p17 byte-unchanged), but measure the untargeted queries too — the local span model does not predict everything Algolia counts.
4. **Simulate every candidate title against every tracked query at once.** A 9-line local `token_span` table over ~8 candidate titles x 9 queries found, in one shot, the single 63-char arrangement that was *strictly dominant* (one new span-0 phrase, every other span identical). Two of the arrangements that read best to a human silently regressed `apple podcast reviews` from span 2 to 4. Never hand-reason about proximity — tabulate it.

## Cycle 544 — aggregate-only stats still identify a culprit if you snapshot them per-item; and the surface you actually sell on needs a time series, not a print

1. **An aggregate counter you snapshot repeatedly becomes a traceable event log.** `bin/revenue` stores `ext_stats30d` *per Actor* on every run, so a fleet-level `ext_bad30d=1` that sat untraced for 43 cycles was resolved in two minutes with zero API calls: diff the per-Actor history and both the culprit (`google-news-scraper`) and the event's first-seen timestamp fall out. The lesson generalises — when a metric is only exposed as a total, snapshot its finest available breakdown, not the total.
2. **Apify shows an Actor owner NO detail about external runs.** `publicActorRunStats30Days` is the whole story; `GET /v2/acts/<id>/runs` returns only runs *we* started. There is no input, log or error to read for a stranger's failed run. Do not queue "go look at the failing run" tasks for external runs again — the reachable questions are "is the failure mode still possible with today's code?" and "does the default-input path still pass?", both answerable locally.
3. **Check the fix before chasing the bug.** The TIMED-OUT run turned out to have been fixed by commit `bf7a70e` on the same day it last could have occurred. `git log -S "<mechanism>" -- <file>` is the cheapest first move on any stale bug report, and it beat every plan that started with a reproduction. Then verify the fix is *deployed*, not just committed: `GET /v2/acts/<id>/versions` returns the real `sourceFiles` content Apify is building from.
4. **`storePosition` is the traction metric, and it had never been recorded over time.** Rank is what a cycle looks at, but rank inside a match group is decided by `storePosition`, which Apify computes from cumulative users/runs/reviews. Cycle 544's first stored baseline: everything published before ~cycle 510 sits at 50,951-54,829, the two newest Actors at ~67,600-67,800. A new listing therefore starts ~13k behind and must climb — which is a measurable claim only now that `bin/store-rank` appends to `state/store_rank_algolia.json`.
5. **Rank on a thin query drifts on its own.** `trademark-search-scraper` moved p18 -> p1 on `nice classification` and `nih-reporter-scraper` #26 -> p17 on `nih grants`, neither with any copy change. A future cycle that edits listing copy and then sees a rank move must not read it as causation — h74's negative verdict is not weakened by this, it is the reason the drift column exists.

## Cycle 542 — a published PAY_PER_EVENT Actor with no `Actor.charge()` call gives every row away free, and no standing check catches it

`sam-gov-opportunities-scraper` (built cycle 539, published cycle 540) was configured PAY_PER_EVENT at
$0.0015/row in `meta.json` (`events.result`), and the Apify listing itself was correct — but `src/main.js`
only ever called `Actor.pushData(results)` in one bulk call at the end. It never called `Actor.charge()`.
Every other PPE Actor in the fleet (21 of 22, checked via `grep -rl "Actor\.charge(" */src/main.js`) routes
every push through a small `pushResult()` helper that calls `Actor.charge({eventName, count: 1})` first and
only pushes/counts the row if `chargedCount > 0`; this Actor was the sole exception, built without it. The
result: since cycle 540, any real buyer running this Actor would have received every opportunity for free —
a silent, permanent revenue leak on a live, correctly-priced Store listing. (Caught before any real revenue
existed fleet-wide — $0 booked — so no refund/correction owed, but the same class of bug on a future Actor
with real usage would be a genuine loss, not just a missed opportunity.)

**Root cause of why it slipped through**: none of the standing checks (`check-registry-fields`,
`check-code-fields`, `check-store-meta`, `check-pricing`) look at whether `Actor.charge()` is called at all —
they check field-shape and Store-metadata drift, not the charging call itself. `apify call` test runs
"succeeded" and pushed the right rows with the right shape, so the on-platform verification step that has
caught other bugs in this fleet (cycle 540's multi-value-filter bug, cycle 513's proxy issue) didn't surface
this one either, because a missing charge doesn't fail the run or change the output — the only place it's
visible is the run's `chargedEventCounts` in the Apify API, which nobody was checking.

**Fix**: added the same `isPPE` + `pushResult()` pattern used by `federal-register-scraper`/
`grants-gov-scraper` (per-item `Actor.charge()` before `Actor.pushData()`, `isPPE` guards non-PPE/local runs).
Verified the fix actually charges by calling `GET /v2/actor-runs/<id>` after a real `apify call` and reading
`chargedEventCounts` directly (`{"result": 2}` after the fix, vs. presumably `{}` before it — not re-verified
against the old build since re-publishing an unfixed build to check would itself have been dishonest to any
watcher, but the absence of any `Actor.charge` call in the pre-fix source is unambiguous).

**Fleet-wide implication for a future QUALITY slot**: every PPE Actor's `chargedEventCounts` should be spot-
checked this way at least once after publish, not just its dataset output shape — a Store listing that "runs
successfully with correct data" can still be charging nothing. Consider a `bin/check-charges` helper that
runs a cheap `apify call` against each PPE Actor and asserts `chargedEventCounts` is non-empty, the same
category of gap-closing tool as `check-registry-fields`/`check-code-fields` already are for their own class
of silent drift.

## Cycle 517 — CORRECTION to cycle 452's "the blackout is over": it never lifted, the check was authenticated

Cycle 452's `bin/check-store-rank` sends `Authorization: Bearer $APIFY_TOKEN` on Store search calls, so it (and
every rank measurement built on it since, h50-h136) was reading the *owner's own view* of Store search, where
`effectivePlatformFeatures.ACTORS_PUBLIC_DEVELOPER` grants full visibility of your own Actors. Anonymous
requests (`curl` with no token, or `+&includeUnrunnableActors=true` to bypass the filter and confirm) show
**zero** of our 21 Actors for any query, including our own brand name. `GET /v2/users/me` explains why:
`effectivePlatformFeatures.ACTORS_PUBLIC_ALL.isEnabled: false`, `disabledReason: "...upgrade your plan or
contact support@apify.com"`. This is a documented Apify mechanism (`docs.apify.com/api/v2/store-get`): by
default, Store search excludes Actors from developers who haven't passed KYC or lack a large user base.

**Lesson: a "does the public see X" check must never send the account's own auth token** — an authenticated
call answers "can *I* see X," which is a different and much more forgiving question. `bin/store-visibility`
(cycle 116) got this right by design and would have caught the regression immediately if it had been re-run
between cycles 452 and 516 instead of being superseded in practice by the token-authenticated tool. Any future
"is X visible/discoverable/live to a stranger" check should default to anonymous and treat auth as an opt-in
control, not the other way around.

Full evidence and the owner email sent about this are in `state/STATUS.md` cycle 517 and `tasks/queue.md` h137.

## Cycle 444 (2026-09-18, opus-5, QUALITY/reliability) — fault-inject the retry path, and audit *bare* calls as well as retry loops

Closed h68 (network-error `try/catch` port) on the last 2 Actors: `us-federal-awards-scraper` (0.1.23),
`uk-find-a-tender-scraper` (0.1.21). Two durable lessons, both about verification rather than the fix itself.

- **Prove the catch block is reachable, not just that the happy path still works.** Cycles 442/443 verified this
  same fix six times by re-running the stock regression and confirming the row count was unchanged — which proves
  nothing about the new code, since the new code only runs when the network fails. Cheap fix: copy `src/main.js` to
  a throwaway `src/netfail.tmp.mjs` with `sed` replacing only the API host with `http://127.0.0.1:9/` (nothing
  listens on port 9, so connects fail with an *instant* ECONNREFUSED instead of burning the 45-60s request
  timeout), run it, and read the log. Both Actors emitted all four `request failed (connect ECONNREFUSED
  127.0.0.1:9); retrying in 10/20/30/40s (N/4)` warnings, then their existing stop-early + zero-rows guidance, and
  **exited 0** — the whole point of the fix, and previously untested. ~100s per Actor, ~40s of that real sleeping.
  Delete the temp file and `ls src/` before pushing (Apify would ship it; it is dead code but it is still bytes in
  the image and would trip `check-source-bytes`).
- **An audit scoped to one code shape misses the same bug in another shape.** The h68 audit searched for
  hand-rolled retry loops (`for (let attempt = 1; attempt <= 4; …)`) whose `await gotScraping(...)` lacked a
  `try/catch`, and declared the fleet clean after 8 fixes. But `us-federal-awards-scraper` also resolves a
  `startUrl` saved-search hash through a **bare one-shot** `await gotScraping(...)` with no loop at all — same
  crash-on-timeout defect, invisible to a loop-shaped grep. Triage by blast radius, not uniformly: that call runs
  before any row is pushed or charged, so a clear thrown message ("network-level failure, not a bad link -- re-run;
  nothing was charged") is the right fix and a retry would be over-engineering; a bare call *mid-run*, after rows
  are charged, would need a real retry because a crash there silently truncates what the buyer paid to collect.
  Queued as h69: `grep -n "await gotScraping" actors/*/src/main.js` and check each hit for an enclosing
  try/catch-or-loop.
- **Reword an error message when its loop gains a new exit cause.** `uk-find-a-tender-scraper`'s post-exhaustion
  log said "Still rate-limited by X after 4 retries" — true before this change, wrong half the time after it, and
  exactly the line a buyer would paste into a support mail. Adding a retry cause to a loop means re-reading every
  log line that loop can emit.

## Cycle 432 (2026-09-18, opus-5, BUILD/competitor-gap) — third-party enrichment as a gap-closer, and a fabricated-default trap in a free API

**Shipped:** `steam-reviews-scraper` `includeOwnerEstimates` (build 0.1.28 live) — owner range, peak concurrent
players yesterday, and Steam's crowd-voted tags with vote counts on `dataType:"games"` rows.

- **The gap came from outside Steam.** Competitor diff (5 live input schemas: automation-lab 70 users, easyapi 59,
  logiover 52, datawell, shahidirfan) found exactly one thing our 20-input schema lacked: datawell's
  `includeOwnerEstimates`. Its sibling `mode:"reviewSummary"` was a false-positive gap — our `dataType:"games"` row
  already carries the full `query_summary` (reviewScore/totalReviews/totalPositive/Negative/positivePercent) plus
  store data, which is a superset. **Lesson: when a competitor's extra field can't come from the site's own API, ask
  what third-party public API they're calling** — here SteamSpy, which Steam's store API does not duplicate.
- **Verify the third-party data is ALIVE field by field before advertising it.** datawell advertises "owner and
  playtime estimates". Probed SteamSpy across 7 apps (Dota 2, CS:GO, Cyberpunk 2077, Stardew Valley, Monster Hunter
  Wilds, CoD MWII, Schedule I): `owners`, `ccu` and the 20-tag vote map are populated on every one, but
  `average_forever` / `median_forever` / `average_2weeks` / `median_2weeks` are a **flat 0 on all 7** — dead since
  Valve hid profile playtime. So we shipped owners/CCU/tags and put the dead playtime field in the README's FAQ as an
  explicit non-claim. A competitor advertising a field is not evidence the field has data.
- **New trap worth checking on ANY third-party enrichment API: the fabricated default.** SteamSpy answers HTTP 200
  for an appid it has never heard of, echoing the appid back with `name:null` and
  **`owners:"0 .. 20,000"`** (verified live on appid 99999999). An `if (!body || body.appid == null)` guard — the
  obvious one, and the one I wrote first — passes that straight through, so the Actor would have *sold a made-up
  owner estimate* for every app SteamSpy lacks. Two things made it catchable: probing a deliberately bogus id, and
  noticing that `"0 .. 20,000"` is also a **legitimate** bucket for a genuinely tiny game (confirmed on `2943590`
  Before The End and `3600030` Three Sisters Demo, both real Steam apps). The guard therefore keys on `name` being
  non-empty, not on the owners string. **Rule: for any enrichment API, send a known-bad key and diff the response
  against a known-good one before trusting any field as a "has data" signal.**
- **Additive-field convention that keeps an existing row shape byte-identical:** spread the new fields conditionally
  (`...(flag ? {…} : {})`) rather than emitting them as nulls always. Verified: flag off = 33 keys (unchanged), flag
  on = 39 keys. Charging is untouched — the fields ride the game row the buyer already pays for, no new event.
- `apify-admin publish` enforces a **300-char `description`** limit (separate from the 60-char `seoTitle` limit
  cycle 430 hit). Both are caught by the helper's own validation/400, not silently truncated — but budget for them
  when writing meta.json, and note the 140–156 char `seoDescription` guidance in PLAYBOOK is ours, not Apify's.
**Always grep both files:** `grep -n "<pattern>" notes/LEARNINGS.md notes/LEARNINGS_ARCHIVE.md`
Re-trim rule: when this file passes ~150KB, move the oldest cycles into the archive (append-below the pointer header, never overwrite).

## Cycle 407 (2026-09-17) — Google News RSS is a non-deterministic live feed; don't trust a single before/after param diff

Competitor-gap diffing `google-news-scraper` against `easyapi/google-news-scraper` (2559 users) surfaced 4 extra
input params (`lr`, `cr`, `nfpr`, `filter`) that look like real Google search knobs. Live-tested each directly
against `news.google.com/rss/search` (the endpoint we call, not the web-search HTML `easyapi` most likely scrapes).
`lr`/`cr`/`nfpr` were true no-ops (byte-identical output). `filter=0` vs `filter=1` vs unset looked like a real
effect at first glance (103 vs 101 items, different ordering) — but a **same-URL-called-twice control** also
reordered and changed the item count on its own, with no param difference at all. The RSS feed itself is live and
non-deterministic (ranking/inclusion shifts between requests seconds apart), so a single before/after diff on any
param can produce a false-positive "effect." **Standing method addition: when live-testing whether an undocumented
param changes RSS/feed output, always run the unmodified baseline URL twice first to measure the feed's own
noise floor before attributing any diff to the param.** Recorded as a clean negative, no code shipped — see
`state/STATUS.md`/`tasks/queue.md` cycle 407.

## Cycle 405 (2026-09-17) — Steam's server-side date window (h25): holds under paging with `filter=recent`, breaks with `filter=all`, and `start_date=0` silently disables `end_date` too

Closed cycle 404's open question and shipped it: `steam-reviews-scraper` `reviewsAfter`/`reviewsBefore`
now send Steam's own `start_date`/`end_date`/`date_range_type=include` instead of paging back from
today and discarding everything outside the window client-side. Build 0.1.26 live.

**Three things measured live before writing any code, none of them assumable from the one-page probe cycle 404 left:**
1. **Pagination only holds with `filter=recent`.** With `filter=all` + the date-range params, the cursor Steam returns on page 2 is byte-identical to the one sent — every subsequent "page" replays the exact same 100 reviews forever, with no error and no `success:0` to detect it. With `filter=recent` (already forced whenever a date window is set, per cycle-297-era logic), consecutive pages had 0 recommendationid overlap, strictly decreasing timestamps, and clean termination (0 reviews on the page past the window edge) — walked 39 pages / 3900 reviews with zero out-of-window rows.
2. **`start_date=0` is treated as absent, and silently drops `end_date` filtering too** — a window with only `reviewsBefore` set (no lower bound) returning the game's newest reviews unfiltered if you use `0` as the "no lower bound" placeholder. A real nonzero sentinel (tested `1` and a 2007 date, both work identically) filters correctly. Steam review IDs don't predate ~2010, so `1` is a safe sentinel.
3. **`end_date` alone (no `start_date` at all) is also ignored** — same failure mode as (2), reinforcing that `start_date` must always be present (real value or sentinel) whenever `end_date` is used.

**Why this matters beyond speed:** the old client-side implementation had a real correctness cliff, not just a cost one — an old window on a busy game could hit `maxReviewsPerApp` (the scan cap) before paging back far enough to even reach the window, silently returning 0 rows for a window that has real reviews. Server-side filtering removes that failure mode entirely: Steam starts the feed at the window, so the scan cap only limits how much OF the window you see, never whether you reach it.

**Verified:** local runs on all 3 shapes (both bounds, `reviewsBefore`-only via the sentinel, `reviewsAfter`-only) each returned every row correctly inside/before/after the requested boundary; platform build 0.1.26 run on Witcher 3 (292030) June 2026 window returned 100/100 in-window rows in ~8s; stock `test_input.json` regression unchanged (10 rows / 39 fields). No new input fields, no watch-fingerprint change (the two inputs already existed and were already fingerprinted).

## Cycle 404 (2026-09-17) — Steam's `filter_offtopic_activity` is a real, cheap-to-verify feature gap; and Steam's review endpoint DOES accept server-side date windows

**Shipped:** `steam-reviews-scraper` `includeOffTopic` (build 0.1.25 live). Found by the standard
input-schema diff against the niche's top listings — `danek/steam-reviews-ppr`'s
`filter_offtopic_activity` and `memo23/steam-reviews-scraper`'s `includeOffTopic` were the only real
gap. (`automation-lab` 70 users, `easyapi` 59, `logiover` 52, `danek` 52 all diffed; everything else
they expose we already had, or is `proxyConfiguration`, which is a platform feature and not a
product gap for a no-proxy pitch.)

**What the parameter is.** When a game gets review-bombed over something that isn't the game, Valve
flags that time range as "off-topic activity" and `store.steampowered.com/appreviews/<id>` excludes
those reviews *by default* (`filter_offtopic_activity=1`). Passing `0` returns the unfiltered set.
We never sent the parameter at all, so we silently inherited Steam's filtered view — fine as a
default, wrong for a buyer whose whole research question IS the backlash.

**Cheap detector for "does this game have a flagged period at all" (2 requests, no paging):**

    for f in 1 0; do curl -s "https://store.steampowered.com/appreviews/<id>?json=1&num_per_page=0\
      &language=all&purchase_type=all&filter_offtopic_activity=$f" | jq .query_summary.total_reviews; done

A delta = flagged. Verified deltas 2026-09-17: Total War: ROME II (214950) 88,334 -> 94,228,
War Thunder (236390) 784,322 -> 910,013, NARAKA (1203220) 302,783 -> 343,134, Rust/Witcher 3/
Terraria also flagged. **Trap that cost ~10 minutes:** diffing the first page of `filter=recent`
instead is worthless — busy games gain reviews between the two curl calls, so you get a different
`recommendationid` set for a reason that has nothing to do with the flag (Geometry Dash looked like
a hit and was pure churn). The `query_summary` totals are stable and unambiguous; use those.

**The totals endpoint matters too, not just the review list.** The `dataType:"games"` row's
`reviewScore`/`totalReviews` come from the same endpoint, so the flag now follows the run's setting
there as well — otherwise a game row would report a score that contradicts the reviews pulled next
to it in the same run.

**Watch-mode detail, same rule as cycle 400's `includeMacApps`:** the new flag enters the watch
fingerprint only when true (`...(includeOffTopic ? { includeOffTopic: true } : {})`). Writing it as
`false` on the default path would rewrite every existing fingerprint and reset all live baselines
once, for zero behaviour change.

**Separate finding, NOT shipped, worth a future cycle:** `appreviews` also honours
`start_date` + `end_date` (unix seconds) + `date_range_type=include` when `filter=all`. Probed live
on Witcher 3 (292030) for 2026-08-20..2026-09-01: every returned review fell inside the window.
We currently implement `reviewsAfter`/`reviewsBefore` client-side by forcing `sortBy:"recent"` and
paging back from today, which for an old window means scanning tens of thousands of reviews the
buyer never sees. If server-side windowing holds up under paging, it turns our most expensive filter
into a cheap one. Queued as h25.

**Publishing gotcha re-confirmed:** `bin/check-store-meta` compares **`.actor/actor.json`**'s
description against live, while `bin/apify-admin publish` reads **`meta.json`**. Change one and you
get a drift report against the other — update both. Also: `apify-admin publish` hard-caps
description at 300 chars and seoDescription at 200, and `apify-admin publish <slug>` needs the meta
file path as a second argument or it dies with an IndexError.

## Cycle 358 (2026-09-16) — a custom test-input call is only as safe as the field names in it; a typo'd field silently falls back to the Actor's default fanout, not an error

A varied-input smoke test on `apple-podcasts-scraper` sent `{"searchTerms":["science"],"maxResultsPerTerm":5}` — `maxResultsPerTerm` is not a real input property (the actual cap is `searchLimit`, default 10). Apify doesn't reject unknown keys; they're silently ignored, so the call ran with every other field at its schema default: `dataType:"episodes"` (fetch every episode of every matched show), `searchLimit:10` (10 shows per term). Result: 1100 real episodes returned correctly — not a bug — but an uncapped run that charged ~$1.10 against the platform-usage credit for a verification call that was meant to be a handful of items.

**Rule: before constructing a one-off custom-input API call for a smoke test, `cat .actor/input_schema.json` (or grep the property list) and use real field names, not remembered/guessed ones.** This matters most for Actors whose default `dataType`/mode fans out per match (search term → N shows → all episodes of each) — a wrong cap field there doesn't error, it just runs the expensive default. `bin/store-test` (empty input, schema defaults) and `actor-health` (curated `test_input.json`) don't have this risk since they don't hand-construct field names; only ad hoc custom-input verification calls do.

## Cycle 340 (2026-09-16) — watch mode on a multi-record-type Actor: the snapshot record is the thing that keeps charging
`watchLabel` port #12 (`google-play-reviews-scraper`, build 0.1.25) was the first onto an Actor that pushes **two record types**: discrete events (reviews, stable `reviewId`) and a **snapshot** (`recordType:"app"` — score, installs, histogram — no id, no "new"). Three rules came out of it, all reusable for the remaining review Actors (`app-store-reviews`, `steam-reviews`, both multi-record-type):
1. **A snapshot record must be deferred, not skipped and not pushed eagerly.** Pushing it per run breaks the whole promise of watch mode ("nothing new costs nothing") — on a quiet app an hourly schedule would still charge 24 app records/day. Dropping it entirely is worse: when a new review *does* arrive the buyer loses the context row. Fix: fetch it, hold it in `pendingAppRecord`, push it lazily right before the first *new* review of that app. Verified live: quiet rerun pushed 0 rows/charged 0; the run with 2 recovered reviews charged `{result: 3}` = 2 reviews + 1 app record.
2. **A search-resolved target set can drift without the fingerprint changing.** Editing `appIds` changes the fingerprint (safe — fresh baseline, 0 charged), but a `searchTerms` lookup resolving to a *different* app next week does not. Without a guard that app's entire back catalogue is delivered as "new" and charged. Fix: store `seededApps` alongside `seenIds` and baseline any unknown target on the spot (`appSeeding = seeding || !seededApps.has(appId)`), and only record a target as baselined if its walk wasn't cut short by the global SEED_CAP.
3. **Client-side filters MUST be in the fingerprint (cycle 335's rule), and here they're the only filters there are** — Google Play's endpoint takes no rating/keyword/version/date params at all, everything is applied in `passesFilters()` after fetching. Proven live: adding `minScore:5` to an existing label produced a *second* KV record (`...-f3b802522c` vs `...-aec139387b`) rather than reusing the narrow baseline.

**Cap semantics (Trap 5) resolved the us-federal-awards way:** `maxReviewsPerApp` is an honestly-documented *fetch-depth* cap (README already said "counts reviews fetched, before filtering"), `maxResults` is the delivery cap — so incremental runs keep the buyer's value untouched and only the baseline walk gets its own deeper floor (`max(maxReviewsPerApp, 1000)`, ≤5000). Confirmed live in the log: seed fetched 1000, the incremental run right after fetched 5 (the buyer's cap).
**New honest-warning shape worth copying:** when *every* matching review inside the fetch window was new (`newForApp === passCount && data.length === fetchNum`), reviews posted before the window are unreachable forever — the run now warns and says so in the status message ("raise maxReviewsPerApp or run more often"). Any depth-capped, newest-first feed has this failure mode; a page-walking API (TED, federal-register) does not, because it keeps paging until it hits a seen id.

## Cycle 343 (2026-09-16) — "upstream is down" measured from this box alone is not a fact: Apple empties the review RSS per source network
Cycle 342 concluded, from ~20 `curl`s off this Linode box, that Apple's customer-review RSS was **down fleet-wide** (HTTP 200 + `feed.entry: null` for every app id, storefront us/gb/de/jp, page, sort, URL shape and both client classes). Every one of those measurements was real — and the conclusion was still wrong. **The same three app ids (Notion/Instagram/Spotify, `us`, `mostRecent`, page 1), fetched from Apify's network in the same minute, returned full 50-entry feeds** while this box got `entry: null`. So Apple empties that feed **per source network** (rate-limit/blocklist shaped — this box had hammered it across cycles 341-342), and other iTunes RSS feeds (`topfreeapplications`) keep serving from the same IP, which is exactly why the box-only evidence looked so convincing.
- **Rule: never diagnose an upstream as down without a measurement from a second network.** For us the free second network is Apify itself — one `run-sync-get-dataset-items` call with the suspect input costs cents and is the *production* path anyway. `bin/actor-health` already runs there, so when it disagrees with a local `curl`, the platform is right about the product and the box is just telling you about the box.
- **Corollary for the two-cycle rule (Playbook):** a second measurement that varies only *time* while holding *source network* fixed is a retry, not a second axis. Vary the network.
- The 03:30 nightly `actor-health` failure (`app-store-reviews-scraper`, `items:0`) was a genuine, separate, transient emptiness on Apify's side — gone by 05:05 (stock `test_input.json` → 10/10 on build 0.1.37).
**Shipped anyway, because the fix is right under either cause (build 0.1.36/0.1.37):** when a run ends with **zero reviews served across all pairs** (`feedServed === 0`, counted before filters and before watch de-dup), probe two control apps that always have hundreds of thousands of reviews (2 apps x 2 sorts x both client classes, 3 attempts spaced 5s); if those are empty too, nothing reaching this run can produce reviews, so `Actor.fail` with a named Apple-side-fault message instead of telling the buyer "no reviews match your filters" / "nothing new since the last run". Two placement details that matter:
1. **The check runs BEFORE `saveWatchRecord`.** A watch *seeding* run that recorded "pair baselined, 0 ids" during an empty-feed window would treat the app's entire back catalogue as new on the next run **and charge for it**. Failing first leaves the baseline untouched.
2. **`feedServed === 0 &&` short-circuits the probe**, so a healthy run never pays for it; and an app that genuinely has no reviews still gets the old friendly warning, because the control probe answers `false` on its first request (~240ms, measured).

## Cycle 346 — a "new since last run" watch can be widened to "changed since last run" for free if the compared fields are already thin
`grants-gov-scraper`'s first-ever competitor audit (`nexgenwatch`'s 8-Actor family sells deadline-amendment/status-change/forecast-to-posted watches as separate paid products) turned into a general pattern for the other 13 `watchLabel` Actors, not just this one:
- **If a field that can meaningfully change over an opportunity/row's lifetime (deadline, status, a small set of "is this row still what it was" markers) is already a *thin* field — present on every row regardless of `enrich`/detail-lookup cost — tracking it in the watch snapshot is free.** No extra API call, no extra scan cost. The only new cost is storage: swap the watch record's `Set<id>` for a `Map<id, snapshot>` (or an array of small objects), which is a few dozen bytes per id, not a new request shape.
- **This billed at the SAME per-row price as a new delivery, not a new charge event.** A changed-and-redelivered row is exactly as valuable to the buyer as a new one; standing up a second Apify pricing SKU (`apply-actor-charge-event`) for it would have meant a `pricingInfos` migration and a second price point to justify, for a feature validated only by ~2-user competitor Actors. Reuse the existing event name until real demand says otherwise.
- **The backward-compatibility trap this shape creates: every prior `watchLabel` Actor's live watch records predate the richer snapshot.** Loading code must detect the old (bare-id) shape on read and treat those entries as snapshot-unknown (null), never as "no change" or "change from null" — otherwise turning the new flag on either (a) never fires because null !== null reads as unchanged by an unguarded loose check, or (b) fires spuriously for every existing baselined row on the very next run. Verified by force-converting a live-shaped test record to the legacy flat-array format and confirming a clean 0-new/0-changed rerun before shipping.
- **Candidates for the same treatment, not yet done:** `us-federal-awards-scraper` (award status is a thin field), `fda-recall-scraper` (recall classification/status can be upgraded after the initial notice), `federal-register-scraper` (a rule's `effectiveOn` date can be amended). Each needs its own check of which fields are genuinely thin vs. detail-only before assuming the pattern transfers directly.

## Cycle 350 (2026-09-16) — one failing live run against a third-party API is not proof of a bug; rerun with diagnostics before concluding either way
`hacker-news-scraper`'s new `enrichGithubLinks` feature (GitHub repo star/language/push-date lookup) tested clean 4 ways locally, but its first real-platform run silently returned `githubRepo` populated with the star/language/pushed fields all `null` for all 10 matches — and crucially, **no warning was logged**, meaning the code's own error handling never fired. ## Cycle 352 (2026-09-16) — a number you wrote about your own product decays every time you improve the product; make the drift check mechanical

## Cycle 360 (2026-09-16, opus-5, QUALITY) — we published a guide about a trap and then shipped the trap; a multi-value input is only tested when you send two values

The queued audit (cycle 359 item (d)): check every array-typed, API-forwarded input in the fleet for the bug class that hid `uk-find-a-tender-scraper`'s `stages` issue — *the only value ever tested was the single-value default*. One real hit, and it is the most embarrassing kind.

## Cycle 368 (2026-09-16, opus-5) — how to audit "code emits it, docs never declared it" without an AST parser, and what it found
- **The auditor (`bin/check-code-fields`) is a hand-rolled scanner, not a regex over the whole file, and that distinction is why it works.** A naive `grep '\w\+:'` over `src/main.js` picks up ternary branches, nested sub-objects and option bags. What works: walk the source char by char skipping strings/comments, push a frame per `{`, let each frame accumulate only its OWN text (nested `{}`/`[]`/`()` bodies dropped, so a nested literal's keys are never attributed to its parent), then match keys with a comma-or-start anchor `(?:\A|,)\s*(key)\s*:` so `cond ? a : b` can't produce a phantom key. Treat a literal as a record shape only if it shares >=2 keys with `dataset_schema.json`.
- **Always build a negative control before trusting a new auditor.** Ran the extractor against `git show 0d77a0c^:.../dataset_schema.json` (the pre-fix schema) and it reported exactly the two fields cycle 367 found by hand. Without that, a scanner that reports "0 drift" is indistinguishable from a scanner that silently parses nothing — which is exactly `scholarship-scraper`'s state (0 literals extracted, because its rows are assigned field-by-field; it prints as `ok` and is really a blind spot).
- **Three false-positive classes, each needing a different suppression, all found by reading the code rather than tuning thresholds:** (a) internal fields `delete`d before push (`ats-jobs-scraper`'s `_rawId`/`_externalPath`); (b) a nested element shape whose literal is bound to a name that is itself a declared field (`const variants = (p.variants ?? []).map((v) => ({sku, price, ...}))` — needs a STATEMENT-scoped binding lookup, since the text next to the `{` is just `.map((v) => (`); (c) watch-mode fingerprint objects (`watchCriteria`), which are named after the input filters and therefore overlap the record schema by construction while never being pushed. Raising MIN_OVERLAP would have hidden real findings instead of these.
- **What it found — a new recurring drift class worth checking on every new multi-record-type Actor: `dataset_schema.json` declares ONE record shape, so a second record type's fields silently get no Console columns and often no product-page credit either.** 3 Actors affected: `steam-reviews-scraper` (`gameRow`, 24 fields, 10 also unadvertised), `apple-podcasts-scraper` (12, 3 unadvertised), `us-federal-awards-scraper` (14 subaward fields, all already advertised). Fix pattern: add the second shape's fields as OPTIONAL properties so the primary record type still validates.
- **Practical split when a finding spans both halves:** `registry.json` is read by the site at request time, so advertising verified fields is a no-build, immediately-live change; `.actor/dataset_schema.json` needs an `apify push` per Actor. Ship the registry half in the same cycle you find it, queue the pushes one-per-cycle with the exact field lists and types. Verify the fields are real first — for `steam` that meant curling `store.steampowered.com/api/appdetails?appids=570` and confirming every claimed field is populated (and that the Actor passes `l=english`, so we aren't advertising fields that arrive as localized text).

## Cycle 376 (2026-09-16) — reverse-engineering a site's own search-URL params, and the schema-default trap in "paste a URL" inputs

## Cycle 408 (2026-09-17) — a per-item detail call is a *filter dependency*, not a "descriptions on/off" toggle
`ats-jobs-scraper` gated its SmartRecruiters/Workday per-job detail call on `includeDescriptions`. But on Workday that call is the ONLY source of `employmentType`, `department` and an exact `publishedAt` — the list payload has none of them. Two bugs fell out of that, both silent (no error, just zero rows):

1. **Pre-filtering on a not-yet-populated field.** Those two fetchers run `passesFilters()` on the list-mapped job *before* the detail call, to bound how many detail requests they make. Any filter on a deferred field therefore compared against `null` and dropped every posting: `{"ats":"workday", "employmentTypeKeyword":"full"}` returned **0 rows on every Workday board**, forever, while the same filter worked fine on the five ATSes that carry the field in their list payload. Fix: the in-fetcher pre-filter now takes an explicit list of deferred field names to skip (`WORKDAY_DEFERRED`, `SMARTRECRUITERS_DEFERRED`) and the main loop's unrestricted `passesFilters()` applies them after enrichment.
2. **Gating enrichment on the wrong input.** With `includeDescriptions:false` the detail call was skipped entirely, so even after fix 1 the deferred fields stayed null. The gate has to be "does any *filter* need a detail-only field", not "does the buyer want descriptions" (`workdayNeedsDetail`).

**Generalizable rule for the fleet:** whenever an Actor enriches rows with a second request, write down which output fields exist only *after* that request, and check every filter against that list. A filter on a post-enrichment field must either (a) run only after enrichment, or (b) force enrichment on. Grep for other two-phase Actors before assuming this is Workday-specific.

Related: a filter can also need data the buyer didn't ask to *keep*. `descriptionKeyword` fetches the description even when `includeDescriptions:false`, matches on it, then nulls the two description fields at push time — filter inputs and output-shape inputs are independent knobs and should not be collapsed into one flag.

## Cycle 412 (2026-09-17) — Federal Register Public Inspection: an "ignored" filter that replaces the query, and a shared primary key across two endpoints
Three reusable things, all verified live against `federalregister.gov/api/v1` before any code shipped.

## Cycle 416 (2026-09-17) — "computed but unfilterable" is now the highest-yield gap pattern in the fleet; and filter placement is a billing question
- **Third consecutive competitor-gap cycle where the real gap was a field we already emit but can't filter on** (fda `countries` c411, uk-tenders `regions` c415, shopify `priceMin`/`priceMax`/`isOnSale` this cycle). This is a checkable pattern, not a coincidence: when scanning an Actor, diff `registry.json output_fields` against `.actor/input_schema.json properties` and look at what's in the first list and absent from the second. Those filters are always zero-extra-request (the data is already in hand) and are exactly what a competitor's input schema advertises. **Do this diff first on any competitor-gap cycle — it's faster than reading competitor schemas and it finds the shippable gaps.**
- **On a per-result-charged Actor, a missing filter is a billing defect, not a missing convenience.** Without `maxPrice`, a buyer who wants sub-$50 products pays for the entire catalog and discards most of it client-side. That's the argument to put in the listing copy ("filter ... before you pay"), and it's why these ship even when the competitor exposing them is small (`clearpath`, 69 users).
- **Where you put a new filter is determined by what charges below it.** `shopify-products-scraper` has two filter sites: raw-payload filters before `shape()`, and shaped-row filters after it. New price/sale filters had to go in the second (the fields don't exist on raw Shopify JSON) — but strictly *above* `enrichWithDetail()` (charges `productDetail`) and `pushResult()` (charges `result`). Before placing a filter after an enrichment step, **read the enrichment and confirm it doesn't write the fields the filter reads** (here it only writes SEO/rating/subscription fields and can fill a null `available`) — that's the cycle 408/409 bug class, and it's cheap to check rather than assume.
- **A product is a price range, not a price.** `minPrice`/`maxPrice` on a multi-variant catalog must be range-OVERLAP (`priceMax >= minPrice && priceMin <= maxPrice`), not a test against a single number — a $40-$120 hoodie genuinely satisfies both "under $50" and "over $100" because a buyable variant exists at each end. Also decided: rows whose price can't be read at all get **dropped** when a bound is set, so a price-filtered run never returns a row the filter couldn't be evaluated against. Same shape will apply to any future range field.
- **Apify's input schema has no decimal/float type** — only `integer`. Fleet convention is `"type":"integer"` + `"editor":"number"` (established on `fec-campaign-finance-scraper`'s `minAmount`). The Actor code parses with `Number()`, so API/JSON callers CAN pass decimals and they work exactly (verified live with `maxPrice: 2.98`); only the Console editor is restricted. For money fields, say this in the description instead of silently shipping an integer-looking price filter.
- **When adding a filter, grep the zero-results diagnostics for hardcoded filter names.** This Actor's empty-run message listed only `"onlyAvailable"/"searchQuery"` and would have confidently blamed the wrong input for a price-filtered empty run. Built the message from the set of filters actually set instead, with their values. Any Actor with a "filters removed everything" message has this rot risk every time a filter is added.
- **`hacker-news-scraper`'s `excludeKeywords` (cycle 418): a full-text search API's relevance-ranked `query` param is not the same as boolean search — it has no negative-term operator, and there's no server-side workaround.** The only fix is client-side: fetch the normal match set, drop rows whose already-mapped text fields contain an excluded term, before the GitHub-enrichment call and before charging. Worth checking on any other Actor whose backend is a relevance-search API (Algolia, Elasticsearch, etc., as opposed to a structured filter API like openFDA/grants.gov) — those tend to support AND/OR-ish syntax but rarely NOT.
- **A zero-rows diagnostic needs to know about every way a query can end up with zero *charged* rows, not just zero *matched* rows.** Adding `excludeKeywords` to `hacker-news-scraper` created a new failure shape the existing diagnostic didn't cover: Algolia returns real hits (`fetched > 0`, so `emptyQueries` never fires), but every hit gets dropped client-side before `pushResult`. The generic fallback message ("no queries or usernames provided") would have been actively misleading. Same lesson as the shopify-products-scraper note above, generalized: **any new client-side pre-charge filter needs its own named branch in the diagnostic, not just a new possible cause folded silently into an existing one.**

## Cycle 420 — units are a filter dimension, and "impossible range" checks must be unit-aware (`clinicaltrials-scraper`)
- **A numeric filter whose unit is implicit is a half-built filter.** Our eligibility-age bounds were `ageRangeFromYears`/`ageRangeToYears` — whole years only — which makes every neonatal/infant query inexpressible (18 **Months** on a cancer search = 108 studies; 18 **Years** = 2,229; same number, completely different product). The fix was two enum inputs, not a rename: keeping the `...Years` input names meant zero breakage for saved tasks and API callers, at the cost of a slightly odd name when the unit isn't years. Worth it. When auditing other Actors for gaps, **grep the input schema for unit-bearing names (`...Years`, `...Days`, `...Km`, `...Usd`) — each one is a candidate for the same treatment.**
- **A "this combination is impossible, fail fast" guard can stop being true when you add a dimension.** Ours threw on from > to, correct and live-verified for same-unit bounds. Add units and it's wrong: `min ≥ 1 Years AND max ≤ 12 Months` returns **13 real studies** (studies enrolling exactly one-year-olds, where the two bounds meet). Throwing would have blocked a legitimate query with a confident, wrong error message. Rule: **when you widen an input's domain, re-derive every fail-fast guard that reads it — and settle satisfiability with an API call, not with arithmetic.** Narrowed the throw to same-unit, warned on mixed.
- **A permissive URL parser hides its own gaps as warnings.** The `startUrl` parser had been *dropping* any UI `ageRange` bound with a non-`y` unit letter for ~290 cycles, with a log warning nobody reads — so a pasted `...&ageRange=_18m` returned unfiltered results that looked plausible. The feature work only touched it because the new units made the drop fixable. **When a parser logs "ignoring that bound", that line is a TODO with a timestamp, not a handled case** — worth a grep across the fleet for `ignoring`/`skipping` warnings in URL/param parsers.
- Unknown units are a hard upstream 400 (`No enum constant ...TimeParts.Unit`), so the whitelist-with-fallback pattern is mandatory here, same as the `documentTypes` codes — except unknown *doc* codes silently return 0 rows. Same Actor, two different failure modes for the same class of mistake; both need the whitelist, for opposite reasons.

## Cycle 428 (2026-09-17) — FEC schedule endpoints are KEYSET-paginated; `page` is accepted and silently ignored (real live bug, shipped since ~cycle 130)

`api.open.fec.gov/v1/schedules/schedule_a|b|e` accept a `page` query param, return a `pagination.pages` count, and then **ignore `page` entirely** — requesting page 1, 2 and 3 of the same query returns byte-identical `sub_id` sets (verified live this cycle on all three schedules). The real cursor is `pagination.last_indexes`, an object whose keys (`last_index` plus a per-schedule sort key such as `last_contribution_receipt_date` / `last_disbursement_date` / `last_expenditure_date`) must be echoed back as query params on the next request. Echo them and paging works perfectly (6/6 unique across 3 requests on each schedule).

**What it cost us:** `fec-campaign-finance-scraper`'s contributions mode had used `page` since it shipped. A run with `maxResults: 45` returned 45 rows of which only **20 were unique** — the first page repeated, **charged per duplicate row**. Fixed this cycle (45 rows → 44 unique, the 1 repeat being two genuinely identical $50 contributions). Platform-verified on build 0.1.14.

**Generalisable rules:**
1. **A pagination param that is accepted without error is not a pagination param that works.** Whenever an API is paged, the first test must be "does page 2 differ from page 1?", compared on a row identity field — not "did page 2 return 200 with rows?".
2. Keyset/cursor APIs often keep the offset params in their schema for compatibility. `pagination.pages` being a large number tells you nothing about whether `page` is honoured.
3. This is a **charging** bug class, not just a data bug: any per-result Actor that loops pages and pushes without a row-identity check will bill a customer for the same row N times. Worth a fleet sweep (queued as h54).
4. Drop `sort_null_only` before echoing `last_indexes` back — it is a flag the API returns inside that object, not a cursor value.

**Also found (FEC Schedules B/E, new modes this cycle):** `committee_id` is fast and indexed on Schedule B and E (sub-second), even though it reliably 504s on Schedule A (cycle 410) — a per-endpoint property, not an API-wide one, so re-probe a filter per endpoint instead of inheriting a previous verdict. And Schedule E `expenditure_date` carries filer typos through unmodified (a real 2024 row reads `3024-07-18`); `dissemination_date` is the sortable/reliable date.

## Cycle 441 (2026-09-18, sonnet-5) — webhookUrl payload shape isn't one-size-fits-all; read the Actor's own log line first

## Cycle 442 (2026-09-18, sonnet-5) — `actor-health` caught a live FAILED run; the fix generalizes to a whole retry-loop class
- **Re-running `actor-health` after a burst of BUILD cycles is itself a QUALITY task, not a formality.** It hadn't run since cycle 434 (8 cycles / 7 builds earlier); this run turned up `court-records-scraper` FAILED (`status: FAILED`, run `gUXbfnafB1CmKLbzA`) — a genuine crash, not a stale artifact.
- **Root cause: the hand-rolled HTTP retry loop (`for (let attempt = 1; attempt <= 4; ...)` around `gotScraping`, used across most of the fleet's non-Crawlee API-fetch Actors) only retries on HTTP status codes (429/5xx). A network-level failure — `TimeoutError`/`ECONNRESET`/DNS — throws instead of resolving with a status, and with no `try/catch` around the `await gotScraping(...)` call, that exception is unhandled and crashes the whole Actor process.** Confirmed transient (the identical input succeeded on immediate retry, both locally and on the platform after the fix) but the underlying defect is real and will recur under any ordinary network blip.
- **The fix already exists in the fleet — `grants-gov-scraper` and `nih-reporter-scraper` (both built post-cycle-421) already wrap the same call in `try { resp = await gotScraping(...) } catch (err) { log.warning(...); await sleep(...); continue; }`.** Applied the identical pattern to `court-records-scraper` (build 0.1.6, live, verified: 12-row local regression unchanged, 10-row platform regression unchanged on the exact query that failed).
- **Audited the rest of the fleet for the same shape** (`grep -l "for (let attempt" actors/*/src/main.js`, then read each hit): still vulnerable (hand-rolled retry loop, no try/catch) — `clinicaltrials-scraper`, `fda-recall-scraper`, `federal-register-scraper`, `us-federal-awards-scraper`, `uk-find-a-tender-scraper`. Already safe — `app-store-reviews-scraper` (`fetchPage`'s inner `fetchEntries` call is already try/catch-wrapped per-client-class), `steam-reviews-scraper` (`getJson` uses got's own native `retry:{limit:2}` instead of a hand-rolled loop, which does retry network-level errors). ## Cycle 456 (2026-09-18) — a search API that IGNORES an unsupported filter is a billing hazard, not just a no-op
`court-records-scraper` gained `partyName`/`attorneyName`/`docketNumber`/`judge`. ## Cycle 483 (2026-09-19) — a 200 with an empty payload is not proof of "no data"; `shopify-products-scraper` was calling a live 250-product store empty
- **The bug**: the nightly health check flagged `shopify-products-scraper` as failing (0 items, `[]`) on `https://www.allbirds.com` — a store with 250+ live products that had returned a clean 10 rows on its three previous runs (01:01Z, 02:01Z, 2026-09-18 14:03Z) and that returned 250 products from this box both directly *and* through three separate Apify Proxy sessions minutes later. The workable shape is a **resumable** harvester (`state/harvest/harvest_courts.py`) that records completed pages and re-runs across cycle boundaries, not one long-running process with a bigger backoff.
- **Gotcha that cost a shell:** `pkill -f harvest_courts.py` matched the very bash invocation that contained the string (the heredoc writing the script), killing the command mid-flight (exit 144) so the intended restart never ran. When killing a background job by pattern from a shell whose own command line mentions the script, resolve the PID first (`ps -eo pid,args | grep '[h]c.py' | awk '{print $1}' | xargs -r kill`) instead of `pkill -f`.

## Cycle 500 (2026-09-19) — CourtListener throttle tells you exactly when it clears; and enum labels are not "the stale fixture"
- **A 429 from CourtListener carries the unblock time in its body**: `{"detail":"Request was throttled. Expected available in 7258 seconds."}`. Cycles 496-499 each guessed a retry threshold ("2+ hours since the last 429") and burned part of a cycle deciding whether to retry. **One cheap probe request returns the exact number of seconds remaining** — always probe once and read the body instead of guessing from log timestamps. 7258s at 11:30Z ⇒ clear at ~13:31Z. The window is also clearly multi-hour and *shared* across the whole anonymous budget (harvest + OPTIONS), which is why cycle 497 saw it get worse, not better, while hammering.
- **Distinguish stale *data* from stable *code constants* when deciding "live API only".** Cycle 496 correctly rejected `freelawproject/courtlistener`'s `cl/search/fixtures/court_data.json` (the court *rows*) as stale — 422 vs 472 courts, wrong military classifications. That rejection does NOT extend to `cl/search/models.py`'s `Court.JURISDICTIONS` tuple, which is the enum the `OPTIONS` endpoint itself renders its choices from. Fetching it from GitHub raw is unthrottled, authoritative, and pinnable to a commit SHA. **Validate it anyway against the live rows you already have**: all 8 codes present across our 260 live-harvested courts appear in the 23-code table, so the table is not missing anything our data actually uses.
- Practical shape: when an API budget is exhausted, look for the piece of the task whose source of truth is *code* rather than *data* and do that piece offline — it takes the blocked item off the next cycle's critical path.

## Cycle 504 (2026-09-19) — read the 429 body; a fixed backoff can fake a permanent blocker
**The bug that cost 9 cycles.** `state/harvest/harvest_courts.py` retried rate-limited pages on a *fixed* 15s backoff and never looked at the response body. CourtListener's 429 states the exact wait: `{"detail":"Request was throttled. Expected available in N seconds."}`. With 8 attempts x 15s the harvester could only ever wait 120s, so any throttle longer than that produced `GIVEUP` no matter how close the budget was to refilling — and cycles 496-499 each read that as "the API is too throttled today" and deferred. Patched `fetch_page` to parse N and sleep it (cap `MAX_WAIT=240`; above that, abandon the run rather than sleep a cycle away). The "multi-hour, progressively tightening budget" cycles 496/497 inferred from log timestamps **did not exist** — the harvest finished in ~4 minutes once the waits were read instead of guessed.
- **Generalize:** when an API tells you how long to wait, honour it — never infer a rate limiter's shape from your own log timestamps. Cycle 500 got this half-right (it probed once and read the body to schedule the *next cycle*), but the fix belonged in the retry loop, not the cycle scheduler.
- **Corollary:** a "blocked, retry later" item that recurs 3+ cycles deserves one cycle spent reading the retry code itself, not another deferral. The cheap probe that reveals this is one manual request with the body printed.
- **Competing budgets are real, though:** `OPTIONS /courts/` shares the anonymous budget with the harvest and 429'd twice in earlier cycles; it returned 200 first try once the harvest wasn't running. Sequence calls against one budget, don't interleave them.
- **Live-API-only vindicated again:** the map's `acca` -> `Military Appellate` is exactly where the stale GitHub fixture (rejected cycle 496) said `Federal Special`. Baking that into a paid Actor would have shipped a wrong value to buyers.

## Cycle 508 (2026-09-19) — `bin/check-store-rank` was under-reporting: "NOT IN TOP 1200" mostly meant "stopped after page 1"

`GET /v2/store?search=<q>&limit=100&offset=N` does **not** return `limit` items per page.
Measured across many queries: with `limit=100` a page comes back with **73-93 items**. The
API appears to apply the limit first and then drop items from the page it already cut
(deprecated/private/filtered listings). Pages ARE genuinely disjoint and offset IS honoured
(verified: page@0 ∩ page@100 = 0 items for 'clinical trials'), so paging works — the pages
are just short.

Two bugs in `bin/check-store-rank` fell out of that:

1. `if len(data["items"]) < PAGE: break` — intended as "last page", but a short page is the
   NORMAL case, so the loop broke after page 1 for essentially every query. Every
   "NOT IN TOP 300 / NOT IN TOP 1200" line this tool has ever printed meant only
   "not in the first ~80 results".
2. Rank was `offset + i`, which assumes full pages and over-states position by the
   accumulated shortfall. Correct rank = count of items actually iterated.

Impact on the business picture: the corrected full run went from **24/40 queries returning
us** to **39/40**. Actors previously believed invisible are merely deep —
`substack-scraper` #88 on 'substack', `google-play-reviews-scraper` #109 on
'android app reviews', `shopify-products-scraper` #91 on 'shopify products',
`app-store-reviews-scraper` #93 on 'app store reviews'. Only ONE query in the fleet is a
true absence: `substack-scraper` <- 'newsletter scraper' (scanned all 1022 returned).
Page-1 count (11) is unchanged — the fix changes the diagnosis, not the standing.

Also worth knowing: the `total` field in the response is the API's own match count and runs
well above what search will actually hand out (claims 1225 for 'substack', hands out 981;
claims 548 for 'android app reviews', hands out 483). Never quote `total` as a rank
denominator. Duplicate items across pages do occur (`fda-recall-scraper` appeared at both
802 and 911 for 'substack'), so ranks deep in a result set are approximate.

**Durable lesson, same class as cycle 504's retry-code bug**: when a measurement tool keeps
returning the same discouraging answer ("we're invisible"), read the tool before believing
the answer. Two cycles of BUILD scans were also reading `total=` from this same endpoint to
size niches — that number is inflated, though the user counts used for the demand bar come
from a different field and are unaffected.

## Cycle 511: a 200 on the first curl is not "scrapeable" — Goodreads AWS WAF challenge, goodreads-book-scraper ruled out

Cycle 510 scoped `goodreads-book-scraper` as fully de-risked after **2** plain `curl` requests

## Cycle 520 (2026-09-19) — Apify Store rank: a TITLE match outranks a description-only match, before `storePosition` ever applies
- **Corrects cycle 168's conclusion** ("textual criteria tie for everyone matching the query; rewriting titles/descriptions cannot move us"). That is true only *within* one match group. Algolia's default ranking runs `typo → geo → words → filters → proximity → attribute → exact → custom`, and `attribute` (which attribute the match landed in) is evaluated **before** the custom `storePosition` tiebreaker. So a record matching in `title` beats a record matching only in `description` no matter how much better the loser's `storePosition` is.
- **Measured on one record, two queries, same `storePosition` (52702) — this controls for usage/age entirely.** `court-records-scraper` on `courtlistener` (only in our description): **p67**, while ranks 1..47 were exactly the 47 records carrying "courtlistener" in their title, sorted among themselves by `storePosition`. Same Actor on `docket scraper` (both words in our title): **p6**, ahead of competitors with `storePosition` as low as 15715/32147/50062. Rank moved 61 places on text placement alone.
- **The lever is bounded, so size it before spending a publish slot.** Joining a title-match block lands you *after* every title-matcher with a better `storePosition`, not at the top: `bin/store-rank --attr "courtlistener" court-records-scraper` predicts p67 → ~p32 (31 title-matchers already beat our `storePosition`). p32 is still off page 1, which is why no title was edited this cycle — the diagnostic is what makes that a decision instead of a guess. Title edits are worth it where the title-match block is *small* (the `docket scraper` block is 20 records; `super pac`, `tmview`, `fec api` are similar).
- **Caveat on `--attr`'s prediction:** it is approximate for multi-word queries. Algolia matches per word with a prefix match on the last, so "docket scraper" title-matches a title reading "…Dockets + Opinions…Scraper" (the matcher in `attr()` handles this), but `words`/`exact` criteria still interleave a few non-title records into the block — the `docket scraper` block sits at ranks 1..44, not 1..20 contiguous. Treat the predicted rank as ±a few, not exact.
- **`storePosition` 999999 on a brand-new Actor is a "not yet scored" sentinel, not a penalty.** `trademark-search-scraper` (published same day) carried 999999 on both `storePosition` and `experimentalStorePosition` while all 20 older Actors — including `court-records-scraper`, published 2 days earlier — had real values (51067–54480). Apify scores new listings in a batch job; re-measure after ~48h before drawing conclusions. It still ranked **p5 on `tmview`** while sentinel-scored, which is further evidence the attribute criterion outweighs `storePosition`.
- **Process lesson (3rd instance of this exact class).** `bin/store-rank`'s `TERMS` map is the keying mechanism for all buyer-facing rank tracking, and the last 3 Actors published were never added to it — so "fleet-wide" scans silently covered 18/21 and those 3 had *never once* been measured. Same shape as cycle 519's icon gap and cycle 515's index gap: a standalone tool that a publish never wires itself into. Both are now explicit steps in PLAYBOOK step 8. **When adding a per-Actor tool, add its registration to the publish checklist in the same cycle, or it will drift.**

## Cycle 522 (2026-09-19) — a real `--attr` title-edit win (recruitee p91→p13), and a tokenizer bug that nearly caused a wasted one

**Real win:** brainstormed new candidate buyer-intent queries beyond the `TERMS` map's tracked set (per h141's open follow-up) and re-ran `--attr` on `ats-jobs-scraper`'s existing-but-not-title-matching terms. `recruitee` (7433 nbHits, already p91 via description match) had a title-match block of 10 records ahead of our storePosition — predicted ~p11. Added "Recruitee" to the title (`ATS Jobs Scraper – Greenhouse, Ashby, Lever, Recruitee`, 54/63 chars), published, force-rebuilt for reindex (per cycle 515 rule — confirmed the index lagged ~45s this time, not instant), re-measured: **p13**, other 3 tracked queries on the Actor unaffected beyond normal `storePosition` drift noise.

**Near-miss:** the same brainstorming pass flagged `clinicaltrials.gov` on `clinicaltrials-scraper` as an apparent slam dunk — `--attr` reported a **0-record title-match block** (predicted ~p1 from p61), the same shape as cycles 520/521's two confirmed #1 wins. But the Actor's title already literally reads "ClinicalTrials.gov Scraper...", so if the block were really empty and we were really outside it, that would be a contradiction (the phrase is already there) — worth checking before publishing anything.

**Root cause:** `bin/store-rank --attr` splits the QUERY only on whitespace (`query.lower().split()`) but splits TITLES on every non-alphanumeric character before matching words. A query with a character glued to letters — `"clinicaltrials.gov"` stays one token — can never prefix-match a title word like `"clinicaltrials"` (title-side splitting turned the dot into a space, producing two words: `"clinicaltrials"` and `"gov"`). So the function reported "not in our title" for a query that, read literally, plainly is.

**But the fix is not simply "split the query the same way."** Tried that hypothesis and checked it against ground truth: pulled the raw Algolia hit for `clinicaltrials-scraper` on query `"clinicaltrials.gov"` and read `_highlightResult.title.matchLevel` / `.description.matchLevel` directly — both **"none"**, with empty `matchedWords`. So Apify's real Algolia index does NOT consider this a title (or description) match either, despite the literal substring being present. Real Algolia's tokenizer disagrees with both the naive "keep as one token" AND the naive "split like titles" heuristic for this specific dotted query — the true behavior is opaque without more probing than was worth doing this cycle. No title edit was made; predicted rank was never trustworthy.

**Reusable rule: before spending a publish slot on any `--attr` prediction for a query containing punctuation glued to letters (dots, slashes — domain-like or versioned terms), pull the raw hit's `_highlightResult` and check `matchLevel`/`matchedWords` directly instead of trusting the word-split heuristic.** Plain multi-word alphanumeric queries (the common case, e.g. "super pac", "recruitee", "nice classification") are unaffected — this is specifically about queries containing a non-alnum character with no surrounding whitespace. Documented as a caveat in `bin/store-rank`'s `attr()` docstring rather than "fixed" in code, since no tested tokenization rule was found to actually match Algolia's real behavior for this class of query.

## Cycle 523 (2026-09-19) — corrected cycle 522's `_highlightResult` verification method (it has a hidden position-6 cutoff), then used the corrected version for a real win: `hn api` on `hacker-news-scraper` p227→p2

**What started this:** brainstormed fresh candidate buyer-intent queries for the 5 Actors flagged in h142 as never probed beyond their single tracked `TERMS` entry (`google-news-scraper`, `steam-reviews-scraper`, `substack-scraper`, `app-store-reviews-scraper`, `hacker-news-scraper`). `--attr` reported several apparent small-block opportunities: `hn api`/`who's hiring` (hacker-news-scraper), `steam api`/`steamspy` (steam-reviews-scraper), `substack api` (substack-scraper).

**Tried to apply cycle 522's "verify with raw `_highlightResult` before publishing" rule — and it backfired.** Checked our own hit's `matchLevel` for all 5 candidates: all came back `"none"` on both title and description, which looked like 5 confirmed false positives (matching cycle 522's clinicaltrials.gov shape). Before writing that off, sanity-checked the method against two ALREADY-CONFIRMED real wins from cycles 520/522 (`recruitee` on `ats-jobs-scraper`, `tmview` on `trademark-search-scraper`) — both also came back `matchLevel: "none"` on our own hit, despite being proven-real by an actual pre/post rank measurement. **Root cause, confirmed by direct experiment:** Algolia only computes real `_highlightResult` data for the first 6 hits of a query response — verified by re-requesting the identical query at `hitsPerPage` 3, 20, and 100 and finding positions 1-6 always carry genuine per-record highlighting (full/partial/none matching actual content) while position 7+ is hard-coded `"none"` regardless of content, including a case where a position-7 hit's title was byte-identical to a position-3 hit that showed `"full"`. **Checking our own hit's `matchLevel` is therefore useless whenever we rank below p6 for a query — which is always true pre-edit**, since ranking below p6 is exactly the situation `--attr` exists to evaluate. Cycle 522's clinicaltrials.gov "confirmed fake" verdict was reached this same broken way and should be treated as **unresolved, not settled** — re-checked this cycle: other developers DO get real `matchLevel: "full"` at p1 for that query (a genuine title-match block exists), yet our own record (title also literally containing "ClinicalTrials.gov") sits at p61 instead of in that cluster, for reasons still unexplained. Worth a dedicated look someday, not urgent.

If Algolia agrees that record is a genuine title match, the block is real; if even the block's nominal #1 shows `matchLevel: "none"`, the block is a naive-tokenizer artifact and no edit should follow. Applied to all 5 candidates: **all 5 verified genuine** (block #1 showed real `matchLevel: "full"` in every case) — cycle 523's first instinct to discard them all was wrong.

## Cycle 524 (2026-09-19) — Algolia PROXIMITY beats everything `--attr` models; it decided every Store-rank win we have
**The finding, from a real two-publish controlled experiment on one Actor** (`google-news-scraper`, same index, same storePosition 53755, only the word order of the title changed):

| live title | `google news api` | `google news rss` |
|---|---|---|
| `Google News Scraper – RSS & API, Real URLs, Any Language` | **p255** | **p4** |
| `Google News API Scraper – RSS, Real URLs, Any Language`   | **p6**   | **p128** |

Both queries word-match the title in BOTH titles. The only variable is how many words
separate the query's tokens. Moving `API` from 3 words after `News` to directly after it
is worth ~250 ranks — an order of magnitude more than the entire storePosition spread
that `bin/store-rank --attr` models. Algolia's `proximity` criterion runs before the
custom `storePosition` tiebreaker, so joining the title-match block is **necessary but
not sufficient**.

**Why this hid for 5 cycles:** every win the `--attr` method has produced (`recruitee`,
`tmview`, `super pac`, `nice classification`, `hn api` p2, `steam api` p2) happened to be
written as an exact contiguous phrase, so the naive model's predictions kept landing.
The first non-contiguous edit (this cycle's interim `RSS & API` wording) missed its ~p16
prediction by 240 ranks — that miss is what exposed the mechanism.

**Rules now encoded in `bin/store-rank`:**
1. A title can realistically win **one** multi-word query. Choose it deliberately; a
   second multi-word query in the same title pays the proximity penalty.
2. Write the target query as a literal adjacent, in-query-order phrase in the title.
3. `--attr` now prints the measured **token span** (0 = contiguous) for any query already
   in our title, and flags "LIKELY PROXIMITY DEMOTION" when span > 0 and rank > 20. The
   span helper scores the *tightest* occurrence, because a token can appear twice
   (`Steam Reviews Scraper – Steam API…` scores span 0 via the second "Steam", which is
   exactly why it sits at p2).
4. Prediction lines now carry an explicit "VALID ONLY IF the new title spells this query
   contiguously" caveat. Do not publish off a prediction without a phrasing that satisfies it.

**Shipped this cycle off the corrected understanding:** `steam api` p213→**p2**, `google
news api` p623→**p6**. Existing tracked queries (`steam reviews` p44→p43, `google news`
p157→p160) unchanged beyond ordinary storePosition drift.

## Cycle 533 (2026-09-20) — distinguish an IP-reputation block from a JS-challenge block BEFORE deciding a source is dead (or alive)

`scholarship-scraper` had been failing nightly health since cycle 457 with the one-line verdict
"bold.org is behind Vercel bot-protection, not fixable from this box". That verdict was reached by
curling bold.org **from this box only** — which cannot distinguish the two block types, and left the
Actor sitting at the top of the queue as an untriaged `[hard]` item for ~76 cycles.

- **The test that settles it**: re-request through 2–3 *fresh Apify datacenter proxy sessions*
  (`curl -x http://session-<id>:$PROXY_PASSWORD@proxy.apify.com:8000 ...`; the password is at
  `GET /v2/users/me` → `data.proxy.password`), and **read the response body, not just the status code**.
  - Different IPs → 200: it was IP reputation. The fleet-standard
    `Actor.createProxyConfiguration({useApifyProxy:true})` one-liner fixes it (this is exactly what
    rescued `trademark-search-scraper`, cycle 512 — same 3-minute fix).
  - Different IPs → identical challenge page: it is a **JS proof-of-work** and no amount of proxying,
    header spoofing or retrying will ever work. Here: 3/3 sessions returned the same 32,182-byte
    `<title>Vercel Security Checkpoint</title>` page, i.e. Vercel **Attack Challenge Mode**, which
    challenges *every* visitor lacking a solved-challenge cookie regardless of origin IP. Decisive.
- **Do not reach for residential proxy on a JS challenge.** It costs credits and cannot help — the
  challenge is not about where you come from.
- **A 429 on `robots.txt` is the tell.** No real rate limiter blocks `robots.txt`; a site-wide
  challenge does. That single request classifies the outage in 10 seconds.
- **The product lesson, which is the bigger one: a blocked scraper must FAIL, not succeed-with-zero.**
  This Actor exited SUCCESSFUL with `[]` and the generic "No pages to crawl — pick at least one
  category type" hint. To a buyer that reads as *"nothing matched my filters"*, so they burn runs
  tuning inputs against an unwinnable problem, and the Store success-rate metric flatters a product
  that cannot deliver. Throw a typed error (`class SiteBlockedError extends Error`) from **every**
  fetch entry point — ours had two, and fixing only the sitemap path would have left `startUrls`
  users still seeing the silent-empty behaviour — and `Actor.fail(msg)` so the reason lands in the
  run's status message. Guard it so a block that arrives *mid-crawl*, after rows were already pushed
  and charged, stops gracefully and keeps them instead of failing the whole run.
- **Where the "degraded" warning has to live.** fetchsmith.com already had a `notice` for this Actor
  (`registry.json` → `tool.html` renders `.notice.warn` + a `degraded` pill on `/tools`), but the
  **Apify Store README had nothing** — and the Store is where essentially all of our traffic is. When
  marking a product degraded, do both, and date the banner.

## Cycle 535: `bin/store-rank --attr`'s apostrophe tokenizer bug, and the real Algolia highlight cutoff is position 5, not 6

- **Bug**: `attr()`'s naive `title_match()`/`token_span()` splits the QUERY on whitespace only (keeping punctuation like `'s`) but strips all non-alnum characters from TITLE words before matching. So a query token `"who's"` can never `startswith`-match a title word `"who"` (apostrophe stripped) — any query containing `'s` (or other internal punctuation) falsely reports a "0 title-matchers" block, even when a large genuine block exists. Confirmed on `"who's hiring"` (`hacker-news-scraper`, cycle 535): real Algolia shows a 5-member `matchLevel: "full"` block at positions 1-5, treating the apostrophe-s as droppable (titles spelled both "Who's Hiring" and "Who Is Hiring" score identically). **Do not trust `--attr`'s empty-block verdict for any query with internal punctuation** — verify manually with raw `hitsPerPage` requests and `_highlightResult` first, same method as this cycle.
- **Cutoff correction**: the `attr()` docstring (written cycle 522-524) claims real Algolia highlighting is only computed for "the first 6 hits" of a response. Re-tested directly this cycle with `hitsPerPage` 5/6/7 on the same query: position 6 was hard-coded `matchLevel: "none"` even though its title was pattern-identical to position 2's genuine `"full"` match. **The real cutoff is positions 1-5, not 1-6.** The docstring itself was not corrected this cycle (out of scope for the slot) — anyone editing that logic next should re-verify and fix the stated number.
- **Practical workaround used**: when a query contains an apostrophe or is otherwise suspect, also probe the punctuation-free/split variant (e.g. `"who is hiring"` instead of `"who's hiring"`) — `attr()`'s naive matcher works fine on plain-word queries, and Algolia's real ranking usually treats the two forms equivalently enough to use the clean variant's numbers as a reliable stand-in.

## Cycle 540 (2026-09-20) — repeated query params can fail OPEN: SAM.gov multi-value filters must be comma-joined
- **The trap**: SAM.gov's internal search backend accepts a repeated query key (`naics=541511&naics=541512`) with a clean 200 and a plausible result set — but honours only the FIRST value and silently drops the rest. Measured: `naics=541511` → 607, `naics=541512` → 312, repeated-key form → **607** (i.e. exactly the first value alone, an invisible under-count). The **comma-joined** form `naics=541511,541512` → **919** = 607+312, a true OR. Re-confirmed on two more params: `pop_state` (TX 592 + CA 767 = `TX,CA` 1359) and `notice_type` (p 4016 + o 8281 = `p,o` 12297). URL-encoding the comma (`%2C`) works identically.
- **Why it matters beyond SAM.gov**: cycle 539's `pop_state` trap failed CLOSED (wrong param name → 0 rows, immediately obvious). This one fails OPEN — a buyer filtering on 4 NAICS codes gets a believable pipeline that is missing 3 of them, with no error anywhere. `URLSearchParams.append()` in a loop is the natural way to write this and is exactly what produces the bug. **Standing rule going forward: whenever an Actor exposes an array input that maps to a query param, verify the OR arithmetic with result counts (a+b == a,b) before shipping — do not infer the encoding from the site's own UI or from a single-value count delta.** Cycle 539 shipped the repeated-key form on a reasonable-looking assumption and it was wrong.
- **Cheap test recipe** (no Actor run needed): hit the endpoint with `size=1` for value A, value B, and A+B, and compare `page.totalElements`. Three curls, ~10s, catches this class of bug outright.

## Cycle 556 — a source API can return HTML entities in fields that contain no HTML tags
`grants-gov-scraper` had a `stripHtml` helper that removed tags and collapsed whitespace but never
decoded entities. That looked complete for years because the obvious test ("are there tags in the
output?") passes — Grants.gov returns **entities without tags**: a 10-row enriched sample carried
131 entities (`&nbsp;` x120, `&amp;`/`&rsquo;`/`&ldquo;`/`&rdquo;`) and zero tags. Generalizable:

1. **"Strip HTML" and "decode entities" are two different jobs.** A field can need the second
   without ever needing the first. Check for each separately — counting tags tells you nothing
   about entities. The order matters too: strip tags -> decode -> collapse whitespace, so a decoded
   `&nbsp;` folds into normal spacing instead of leaving a double space behind.
2. **Check every field the helper should cover, not just the one it was written for.** Here only
   `synopsisText` was wired up; `title`/`applicantEligibilityDesc`/`modComments` shipped raw. The
   helper existing is not evidence it is applied.
3. **Decode unknown entities to themselves, not to nothing.** `&foobar;` must survive verbatim;
   silently dropping an unrecognized entity corrupts text worse than leaving it encoded.
4. **Cheap fleet-wide probe** (this is how it was found): run `bin/varied-test <slug> '{...}' <text
   fields>` and pipe through a `&[a-zA-Z]+;|&#\d+;` regex count. Any Actor reading free text from a
   government/CMS API is a candidate. Size the defect with a count BEFORE editing code — the
   tags-vs-entities split is what decides whether the fix is a strip or a decode.
5. **Watch out for fingerprints computed over the field you just normalized.** `eligHash` hashes the
   now-decoded eligibility text, so the first `watchChanges` run after the fix reports a one-off
   false "changed". Accepted deliberately here (no watch users); the point is to *notice and record*
   it, so a later cycle doesn't re-diagnose it as a bug.

**Separate, recurring:** adding an output field is not done when `dataset_schema.json`/`registry.json`/
README are updated. Cycle 551 added `opportunityScore` (53 -> 54 fields) and left FOUR live surfaces
stale — `meta.json` description + seoDescription, `.actor/actor.json` description, and the blog post
that quotes a field count. `check-blog-claims` and `check-meta-fields` are the only checks that see
these; a field addition is done when both exit 0, and `meta.json` edits need an `apify-admin publish`
plus `apify push --force` to reindex.

## Cycle 560 — source-API markup is a distinct defect class from entities, and the fix is field-shape-specific
- `bin/check-entities <slug> '<input>'` walks every string in every output row (nested included) and counts both `&entity;` and raw `<tag>` markup per field. It needs no key list, which is why it caught `federal-register-scraper`'s `abstract` — a field no hand-written probe list had named. Prefer it over hand-rolled regex on QUALITY cycles.
- **Size the defect against the SOURCE API before writing a fix.** A 10-row Actor sample showed 2 tags; a 1000-doc/5-agency sweep of the Federal Register API showed 88 tags, 100% in `abstract`, and exactly two kinds (`<INF>` 86, `<bullet>` 2) with zero entities. That inventory is what made the fix narrow and testable instead of a guess.
- **A shared `cleanText` would have introduced a second defect.** grants-gov (cycle 556) replaces every tag with a SPACE — correct for block markup, wrong for `<INF>`, which is *intra-word* subscript: `NO<INF>X</INF>` must become `NOX`, not `NO X`. Rule: classify tags as inline (-> empty string) vs. block (-> space) per source, then decode entities, then collapse whitespace. Resist "promote it to a shared helper" when the sources' markup conventions differ.
- **Markup in output is only a defect if the README doesn't sell it.** `sam-gov-opportunities-scraper` ships `<p>/<strong>` in `description` and that is correct — the README states the markup is preserved and the sample row shows it. Check the docs before "fixing" a field. Answer to cycle 556's open question: this class is real but not fleet-wide (1 genuine hit in 4 Actors probed).

## Cycle 572 — when NOT to drop "Scraper" from a Store title (refines cycles 554/557/571)
