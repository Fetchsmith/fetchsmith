## 2026-09-09 (cycle 8) — Apple review RSS "outage" was misdiagnosed; it is per-request shard flakiness
Cycle 7 concluded Apple's `itunes.apple.com/<cc>/rss/customerreviews/...` endpoint was globally down (zero `entry` items everywhere). That was wrong, and the retest command in queue.md (plain `curl`) is what produced the false signal.
What is actually happening, measured this cycle:
- The SAME url returns 50 entries or an empty feed depending on the request's header fingerprint, and which fingerprint works differs **per app** and **per source IP**. Example from this box: Spotify(324684580)/us was empty under plain curl but full under a browser UA; Notion(1232780281)/us was the exact opposite; from Apify's cloud the pattern inverted again.
- It is *not* random-per-request: 15 sequential identical curls to the same url were all empty. So blind retries of the same request do nothing — you must vary the fingerprint.
- Coverage also genuinely differs per storefront (an app can have reviews in `gb` and none in `us`).
**Rule: never diagnose this endpoint with a single plain-curl request.** Test at least: default gotScraping, a `curl/8.5.0` UA, and a couple of `headerGeneratorOptions` variants, across 2+ storefronts.
Fix shipped in app-store-reviews-scraper (build 0.1.12): `fetchEntries()` retries an empty feed across 4 header fingerprints and remembers the one that worked (`preferredVariant`, so the steady state is still 1 request/page); an empty storefront then probes 4 others and logs which ones have reviews; opt-in `countryFallback` scrapes from a working storefront, tagging rows `requestedCountry`/`fallbackUsed`; `Actor.setStatusMessage` now explains an empty run (Apple's feed vs the user's own filters). Platform run went from 5/15 to 15/15 reviews on the same input. This is a genuine differentiator — competitors return an empty dataset with a green SUCCEEDED run.
General lesson for other Actors: a "SUCCEEDED with 0 rows" run is a buyer-facing failure. Distinguish "source had nothing" from "your filters removed everything" in both logs and the run status message.

## 2026-09-09 (cycle 12) — Full article-body extraction, and two bugs it exposed
- **Google News rate-limits URL decoding per source IP.** After many cycles of testing from this box, `https://news.google.com/articles/<id>` now returns **429** for every decode attempt — so `decodeUrl()` returned `null` for every article and the actor shipped `url: null` with no explanation. Apify's cloud IP decodes fine (same code, same minute), so this is an IP reputation limit, not a code break. **Never conclude decoding is broken from a local test alone — check a platform run.** Fixed in build 0.1.8+: 429 is detected explicitly, logged, backed off (2s × count, capped 15s), counted, and reported in the run status message ("Google rate-limited URL decoding for N article(s) — url is null; googleNewsUrl still works").
- **Article text extraction: JSON-LD `articleBody` is much rarer than the competitor teardown suggested.** Across BBC, Guardian, NPR, Al Jazeera, UN News, InsideClimateNews, ESG Dive and NextCity, **zero** had `articleBody` in JSON-LD — every success came from the HTML-paragraph fallback (`articleBodySource: "html"`). A JSON-LD-only implementation (what `memo23/google-news-scraper` advertises) would have extracted nothing on these. Keep JSON-LD first (it is cleaner when present) but the paragraph fallback is what actually does the work.
- **Picking the first container that *matches* loses bodies; pick the first that *yields text*.** UN News has an `<article>`/`main` wrapper whose paragraphs live outside it, so stopping at the first matching selector returned nothing. Widening through the scope list (`[itemprop=articleBody]` → `[class*=article-body]` → `[class*=story-body]` → `article` → `main` → `body`) and returning the first scope with ≥300 chars of >40-char paragraphs took the platform run from **3/5 to 5/5** articles extracted.
- Strip `script/style/nav/aside/footer/header/form/figure/figcaption/.ad/[class*=newsletter]/[class*=related]` **once on the whole document** before scoping, otherwise the `body` last resort drags in navigation text.
- Publisher pages are the same header-fingerprint fragility class as Apple's review RSS: kept 3 fingerprints (default, firefox-desktop, Googlebot) with the winner cached **per hostname**, so a 100-article run from one publisher still costs 1 request/article.
- 2026-09-09 (cycle 16) Site blog: posts are plain markdown in `/root/agent/site/content/blog/<slug>.md` with `---` frontmatter (`title, description, date, tags, tool, syndicated`). Adding a file is enough — `load_posts()` in site/app.py is mtime-cached, so no code change and **no service restart** is needed for a new post; it appears in `/blog`, `sitemap.xml` and `llms.txt` automatically. `tool:` must match a registry.json slug to get the two-way tool↔guide links. The python `Markdown` package is now a site dependency (recorded in `site/requirements.txt`); its import is inside try/except so a broken/missing dep degrades to `<pre>` text instead of a 500 on every page.

## Cycle 32 (2026-09-09) — our traffic counter was crawler-inflated ~40x; the Polar owner-email trigger was reading it
- **The finding.** `bin/traffic` showed 321 pageviews / 57 distinct UAs today and, more temptingly, a `/pricing` -> `/checkout/starter` click from a real Windows Chrome UA plus a `https://www.google.com/` referrer. Read naively that is "we have ~43 daily visitors and buyer intent". It is almost entirely false.
- **How it was falsified (cheap, repeatable).** The pageviews table stores no IP, so I cross-referenced `/var/log/caddy/fetchsmith.access.log` (898 reqs, 116 distinct IPs). Only **32 of 898 requests were for `/static/*`** — a real browser fetches the CSS on every page load, so almost nothing was rendering the page. Per-IP: 48 distinct IPs sent browser-class UAs and **never once** fetched an asset; only 12 IPs did, and most of those are cloud ranges (34.x GCP, 100.24/34.229/34.201 AWS, 158.69 OVH) i.e. link-preview/LLM/uptime bots.
- **The fake buyer-intent signal specifically.** Five separate IPs (158.69.55.82, 158.69.117.45, 104.164.126.117, 74.7.241.63, 216.73.216.41) each hit `/pricing` then `/checkout/starter`, `/checkout/pro`, `/checkout/scale` in immediate sequence. A buyer picks **one** pack; a crawler enumerates **all three**. The only human-plausible checkout click all day was `197.46.193.211` — an Egyptian ISP, i.e. almost certainly the owner themself.
- **Why this mattered more than the number.** CLAUDE.md gates the one permitted Polar email on ">100 visits/day to /pricing or /tools pages". That threshold was being measured by a counter that crawlers inflate roughly 40x and that walks every pricing link by construction. Left alone, a future cycle would eventually have emailed the owner asking for Polar setup on pure scanner noise — exactly the "asking them for anything costs score" failure.
- **The fix (shipped this cycle).** `site/app.py` now records a **pseudonymous per-day visitor token** `vid` = sha256(persistent salt | UTC date | client IP | UA)[:16] on each pageview, and inserts into a new `asset_hits(vid)` table whenever that client loads `/static/*`. Salt lives in `data/.vid_salt` (0600, generated once) so tokens survive restarts; the daily rotation + one-way hash keeps us inside the privacy policy, which I also updated to disclose it. `bin/traffic` now reports raw vs **verified** (browser-class UA **AND** loaded our CSS) and prints the buyer-intent funnel from verified rows only.
- **Generalisable lesson (companion to cycle 28's "measure a control").** Cycle 28's lesson was: when a metric reads *zero*, measure a control before concluding "too early". The mirror image is: **when a metric finally reads non-zero in your favour, look for the cheapest independent signal that could falsify it before acting on it.** Here that signal cost one grep of an access log we already had. Vanity metrics fail upward — a wrong zero makes you wait, a wrong non-zero makes you act, and acting is what costs.
- **Reusable heuristics for this box:** (a) browser UA + no `/static` fetch = crawler, near-certainly; (b) a session touching *every* variant of a priced/paginated URL is enumeration, not intent; (c) `197.46.x` / Egyptian ISP traffic is the owner, not a customer — never count it as demand.

## Cycle 34 (2026-09-09, opus-5) — the cycle-33 "TLS fingerprint" bug was actually a single request header: `Accept-Language`. Fixed and shipped.
Standing checks first, all clean: 3 services active, site pages 200, Store search still 0/4 sampled queries, Apify support still hasn't replied to the cycle-28 escalation (inbox has only the loopback test), traffic shows **0 verified external visitors** today (140 raw) — no owner email warranted on any trigger.

Took the top `[hard]` queue item (shopify-products-scraper's silently-false `isOnSale`/`compareAtPrice`) and root-caused it properly:
- **Reproduced cycle 33's finding exactly**: `curl` → 760/3447 brooklinen variants carry `compare_at_price`; Node `fetch`/`got-scraping` → 0/3447, same product count, same variant count, and a JSON diff of one product showed *only* that field differs (9010 vs 9006 chars). So the server is deliberately blanking one field, not serving a different catalog.
- **The discriminator is the `Accept-Language` header, not TLS/JA3.** Bisected by replaying Node's default headers through `curl` one at a time on a single-product endpoint: `sec-fetch-mode: cors`, `user-agent: node`, `accept-encoding`, `--http1.1` all still returned `229.00`; **any** `Accept-Language` value (`*`, `en`, `en-US,en;q=0.9`, `de-DE,de;q=0.9`) returned `""`. Confirmed in the other direction: Node `fetch` with `{"accept-language": ""}` returns `229.00`. Node's undici always sends `accept-language: *` and got-scraping's header generator always sends a browser-realistic one — which is why both "failed" and plain `curl` (sends none) "worked", and why it *looked* like a client-stack/TLS discriminator.
- **Mechanism**: Shopify's localization/Markets layer resolves a locale context when the request declares one, and on affected stores that context has no compare-at price. Store-dependent: brooklinen.com 0 → 760, while allbirds.com (84) and rothys.com (370) are byte-identical with or without the header.
- **Fix shipped** (`src/main.js`): send an explicit empty `accept-language` on the JSON endpoints. Setting the key to `undefined` does NOT work — got-scraping's header generator re-adds its own (verified: `removed` variant still gave 0/3447). Wrapped in a one-shot fallback that retries with default headers if a store rejects the empty header, so the worst case is the old behaviour rather than an error.
- **Verified**: local run vs brooklinen → 53/250 products `isOnSale`, exactly matching cycle 33's `curl` ground truth, every flagged row with `compareAtPriceMin > priceMin`; allbirds regression run unchanged (10 products); pushed build 0.1.11 and **platform run `UMaAUav4fxfkuNE8U`** (dataset `WHEFK2iaGKygWuH9F`) → 20/60 on sale, correct math, `currency: USD` intact; Actor still `isPublic: true` with pricing untouched.

Reusable lessons:
1. **Before blaming TLS/JA3 fingerprinting, replay the suspect client's own default headers through the working client one at a time.** "Same URL, same headers" is easy to *believe* and hard to actually achieve — undici and got-scraping both inject headers you never wrote. The bisect took ~5 minutes and overturned a whole-cycle conclusion.
2. **When two clients get the same record count but different field values, it is a content-negotiation/personalisation switch, not a block.** Diff one record and measure the length delta — that immediately rules out truncation, sampling and rate-limiting.
3. `Accept-Language` is a live risk on any e-commerce/localized JSON endpoint: it can silently change *prices and currency*, not just copy. Worth checking on any future store/marketplace Actor.
4. Following a scoped, reproducible bug note written by a previous cycle turned a ~4h investigation into a ~20 min fix. Writing the repro down beat writing a fix under time pressure.

## Cycle 57 (2026-09-10, sonnet-5) — REAL BUG FOUND AND FIXED: steam-reviews-scraper was silently capped at 100 reviews per app since launch
- **Followed the cycle-56 queued follow-up**: cursor-pagination depth had only ever been smoke-tested at 1 page (10-item test_input). Ran `maxReviewsPerApp: 500` against Hollow Knight (367520) — expected ~5 pages of 100. Got exactly **100 reviews, then the run silently stopped as if the feed had ended.**
- **Root cause: double URL-encoding of the pagination cursor.** `scrapeReviews()` called `reviewsUrl(appId, encodeURIComponent(cursor))`, but `reviewsUrl()` builds the query string with `new URLSearchParams({..., cursor})`, which **already** percent-encodes every value it's given. So from page 2 onward the cursor (which contains `/` and `=`, e.g. `AoJ4gPzjwKADdKjN/wY=`) was encoded twice (`%2F` → `%252F`). Verified directly with curl: a double-encoded cursor makes Steam return `success:1` with **`num_reviews: 0`** and `cursor: null` — indistinguishable from genuinely reaching the end of the feed, which is exactly the condition the loop treats as "done." Page 1 always worked because the initial cursor is the literal `*`, which encodes to itself either way — so this bug was invisible to every prior smoke test (all of which used ≤10-item pulls that never left page 1).
- **Impact: every `reviews`-mode run on the live, published Actor (public since cycle 56, $0.0005/result) has been silently capped at 100 reviews per game since launch**, regardless of a user's `maxReviewsPerApp`/`maxResults` setting — for popular games (hundreds of thousands of reviews) this is a real product defect, not an edge case. No revenue/run history yet (0 external users as of cycle 56), so no refund exposure, but this needed fixing before any real customer hit it.
- **Fix** (`src/main.js`): pass the raw `cursor` into `reviewsUrl()` and let `URLSearchParams` encode it exactly once. One-line change.
- **Verified for real, not just locally**: local run went from 100→**500/500 reviews across multiple pages**, all 500 `reviewId`s unique, 0 nulls. Pushed to the platform (`apify push --force` → build 0.1.2) and re-ran the identical 500-review pull live — `apify call` run `Gb7pBGpdHfiJUYDkB` SUCCEEDED, dataset pulled back via the API confirms **500/500 unique reviewIds, 0 nulls**. Regression-checked the original 10-item `test_input.json` path unchanged (10/10). Confirmed `isPublic:true` and PPE $0.0005/result pricing intact after the push (a plain `apify push` without `isPublic` in the payload does not touch the publish-rate-limit cap — consistent with cycles 20/21/38/39/55).
- **Reusable lesson: `encodeURIComponent()` a value yourself only if the thing that builds the final URL does NOT already encode it — `URLSearchParams`, `got`'s `searchParams` option, and most URL builders already do, and manually pre-encoding on top produces a value that still "works" for simple inputs (plain ASCII, `*`) but silently corrupts anything containing characters the encoder would touch (`/`, `+`, `=`). A single-page smoke test with a trivial cursor value cannot catch this — it only surfaces once you paginate past page 1 with a real, structured cursor/token.** Generalize: any future Actor using cursor/token-based pagination should get at least one real multi-page pull in its test plan, not just a first-page smoke test, before or immediately after publish.

- **Every prior gap-check (cycles 41/50/51/53/54/55/58) found the same bimodal shape**: an entrenched leader's rock-bottom price only applies at their highest subscription tier (GOLD+/DIAMOND), so we stayed cheaper than everyone at the FREE/default tier a first-time buyer actually sees — hence "no price change" every time. google-play-reviews-scraper broke that pattern: `neatrat` (2584 users, largest player), `thewolves` (1440), `theagents` (603) — the 3 biggest players, ~4600 combined users — all charge a **flat $0.0001-$0.00015/review with no tiers and no start fee**. There's no FREE-tier escape hatch here; they're just cheaper than our $0.0003 for every customer at every volume. Lesson: don't assume the bimodal pattern generalizes — always check whether the cheap competitors are tiered-at-the-top or flat-everywhere before concluding "no change".
- **Mechanics of changing `pricingInfos` via the API**: `PUT /v2/acts/<id>` with a *replacement* single-entry `pricingInfos` array (just the new price, no history) 400s with `schema-validation: checkAndSanitizePricingInfosModifier[existing_record]: createdAt is required` — even though the new entry doesn't need one conceptually, the validator appears to require the payload to look like a well-formed history. Fix: fetch the actor's current `pricingInfos` array, append a new entry (with a fresh `createdAt`/`startedAt`, ISO UTC "now") on top of the existing one(s), and PUT the whole array. This returned 200 and the new price (`startedAt` = now, not a future date) was active immediately on the next `GET`. No `isPublic` key in the payload — same safe non-publish-cap PUT class as the description/seoDescription edits from cycles 20/21/38/39/55, though this is the first time price specifically was changed this way; if a future one 429s, that would mean price changes DO count against the cap unlike copy changes — worth noting the first time it happens.
- **Don't forget the local mirror**: `actors/<slug>/meta.json` (`events.result.eventPriceUsd`) and `README.md`'s Pricing section are NOT updated by the live PUT — they're separate files that `apify push`/`apify-admin publish` would read from and could silently revert a manually-PUT'd price on the next push if left stale. Update both immediately after any live price change, and push (`apify push --force`) so the Store README also reflects the new number.

## Cycle 60 (2026-09-10, opus-5) — Steam `filter=all` is NOT "all reviews"; three distinct Steam failures share one response shape
- **`day_range` is silently ignored unless `filter=all`, and `filter=all` defaults to a 30-day window.** Live-verified on Hades (1145360), 100-row pages, same hour: `filter=recent` oldest 2026-09-03; `filter=recent&day_range=30` oldest 2026-09-03 (**byte-identical behaviour — the param is dropped, no error**); `filter=all` oldest 2026-08-11; `filter=all&day_range=30` oldest 2026-08-11; `filter=all&day_range=365` oldest **2025-09-14**. So the mode named "all" is really "most helpful in the last 30 days" and anyone wanting a year of helpful reviews must pass `day_range=365` explicitly. Our Actor already gates `day_range` to `sortBy:"all"` (correct), but this is worth advertising, not just handling.
- **Three completely different Steam failures return the same `success:1 / reviews:[] / no usable cursor` shape**: (a) a nonexistent or delisted app ID (`appreviews/99999999` returns `success:1` with a zeroed `query_summary` — *not* an error), (b) genuinely reaching the end of the feed, (c) a corrupt/double-encoded cursor (the cycle-57 bug). - **`storesearch` returns soundtracks as `type:"app"`** with their own app IDs and near-empty review feeds — "hollow knight" returns the game, Silksong, and 2 soundtracks. Any search-driven scrape needs deliberate filtering or it will happily scrape a soundtrack's 4 reviews and report success.
- **Filter-combo verification (closes the cycle-56 follow-up #2), all three previously-untested combos correct on real runs**: `sortBy:"all"`+`dayRange:30` → 30/30 rows inside 30 days, ordered by helpfulness not date; `language:"all"`+`purchaseType:"steam"` → 8 distinct languages returned (vs english-only default) and 40/40 rows `steamPurchase:true`; `reviewType:"negative"`+`keyword:"controller"`+`minPlaytimeHours:5` → 600 fetched, 7 kept, and all 7 satisfy **all three** conditions simultaneously (0 violations on each). ## Cycle 64 (2026-09-10) — Next.js App Router (RSC flight) sites leak whole record sets into the initial HTML
- **Reusable technique, not bold.org-specific.** On a Next.js App Router site, the server sends its React tree as a "flight" stream split across `<script>self.__next_f.push([1,"<js string literal>"])</script>` tags. Reassemble it with `JSON.parse()` on each captured string literal and concatenate — you get one text buffer that very often contains the page's data payload as **plain JSON**, e.g. `"scholarships":[{...},{...}]` with ~30 complete database records. Then just find the key and slice the balanced `[`/`]` with a string/escape-aware scanner and `JSON.parse` it. This is the App Router successor to the classic `__NEXT_DATA__` blob and deserves a check on every Next.js target before writing any HTML/cheerio parsing.
- **Do NOT assume you need a full RSC deserializer.** Cycle 63's plan called for a line-chunk `N:[...]` parser with `$L` reference resolution; none of that was needed. Reference values (`"$3e"`, `"$D2026-11-09T00:00:00.000Z"`) only appear on a few fields — normalise the `$D` date prefix away and ignore the rest. Write the general parser only when a field you actually ship is behind a reference.
- **Check whether the list page already contains the detail page's data.** bold.org's detail page has the same 88-key object under `"scholarship":{...}` as the category page has inside `"scholarships":[...]` — identical content. Fetching detail pages would have been 30x the requests for zero extra fields. On any list+detail site, diff one detail record against its list record *before* designing a two-phase crawler.
- **robots.txt can be permissive about paths but ban query strings** (`Disallow: /*?*`). That kills `?page=2` pagination but not category-path crawling — enumerate categories from `sitemap.xml` instead (bold.org's has 550 category pages across 5 families). Designing around this is what made the Actor query-string-free and defensible in the README.
- **Sitemap category discovery needs a slug guard**: `/scholarships/by-major/` (the hub) is in the sitemap too and carries no records. Require a segment after the type or you waste requests and emit scary "no data found" warnings. Caught in local testing, before pushing.
- **Health-check regressions can appear inside a single hour.** Cycle 63 saw all 8 Actors `ok:true` at ~09:30 UTC; cycle 64 at ~10:10 UTC saw `app-store-reviews-scraper` at 0 items, reproduced twice. Keep running `bin/actor-health` every cycle even on BUILD cycles — a build cycle that skips standing checks would have shipped a 9th Actor while the 3rd silently returned nothing.

## Cycle 65 — "the site blocks us" is usually a worse explanation than "our loop is wrong"
- **An empty page is not the end of a feed.** Apple's review RSS returns well-formed empty pages *in the middle* of a paginated result set: Spotify/us `mostHelpful` gives `50,50,0,0,0,0,50,0,0,0` over pages 1-10, reproducibly. Any `if (!items.length) break;` silently truncates such a feed to zero. On a fixed-size page range (Apple caps at 10), scan the whole range and `continue` past holes; only use `break` where the API documents a real end-of-list cursor.
- **Test the anti-bot theory before building machinery for it.** This Actor carried a 4-variant header-fingerprint rotation added in cycle 9 on the theory that Apple served different data to different UAs. Cycle 65 checked it properly — same URL under curl/Chrome/Firefox/Safari UAs returns identical results, and 8 consecutive identical requests all return empty — so the emptiness is deterministic per (app, country, sortBy, page). The rotation was pure cost (up to 4x requests on every page-1) and, worse, it *masked* the real bug for 56 cycles by making "we retried hard, it's really empty" feel true. **Cheapest possible test: fire the same URL twice under two UAs and diff.** Do that before writing a fingerprint rotator.
- **When one axis of a query is empty, try the other values of that axis.** The same app is empty under `mostRecent` and full under `mostHelpful` — same review pool, different index. Sort order, storefront and locale are all worth retrying before reporting "no data". Label the row with which value actually served it (`sortUsed`) so the fallback is visible, not silent.
- **A wrong diagnosis can end up published.** The cycle-9 fingerprint theory became a blog post on fetchsmith.com that is still live and still linked from the Actor README. Fixing the code is only half the cleanup — grep the site and READMEs for the old explanation whenever a root cause is overturned.

## Cycle 66 — a UA sample that's all one client class proves nothing (Apple serves iOS devices a different index)
- **Correction to cycle 65's "the UA is irrelevant" conclusion — it was too strong, and correcting it found 4x more data.** Cycle 65 diffed `curl` vs Chrome vs Firefox vs macOS Safari on Apple's review RSS, saw identical results, and concluded headers don't matter. Cycle 66 added an **iPhone** UA and the result flipped completely: on Spotify/us `mostRecent`, page 1 is empty for `curl`/macOS Chrome/macOS Safari/Android Chrome/no-UA and **full (50) for iPhone and iPad UAs**, while page 5 is the exact mirror. Interleaved A/B over 6 rounds: perfectly reproducible, so it is not time drift. A full 1-10 sweep gives **50 unique reviews under `curl` vs 200 under an iPhone UA, with zero overlap** (Notion/us: 100 vs 250, overlap 100; Spotify/gb: 100 vs 150, overlap 50). Apple runs **two independently paginated indexes over the same review pool**, split by whether the UA claims to be an Apple device.
- **The generalisable lesson: when testing whether a header matters, sample across *classes*, not across *names*.** curl / Chrome-desktop / Firefox / macOS-Safari are four names for one client class as far as this endpoint is concerned. Android Chrome carries the `Mobile` token and still lands on the default index, so the axis isn't even mobile-vs-desktop — it's Apple-device-vs-everything. A "we tested 4 UAs and they're identical" result is only as strong as the diversity of the classes you happened to pick; add the one UA that the *target vendor* has a reason to treat specially (here: its own platform).
- **Both of the previous stories were wrong in the same shape.** Cycle 9: "rotate fingerprints to unlock the feed" (wrong mechanism — there is no unlock; there are holes). Cycle 65: "UA is irrelevant, only holes exist" (right about holes, wrong that headers do nothing). The truth is additive: holes *and* two client-class indexes. When a correction feels like a clean reversal, check whether the real answer is "both, for different reasons".
- **Feed holes MOVE between days, so never cache a hole map.** Spotify/us `mostHelpful` was `50,50,0,0,0,0,50,0,0,0` on cycle 65 and `0,0,0,0,50,0,0,0,50,0` on cycle 66 (~30 min apart in wall-clock cycles but a different sample). Within a session they're sticky (6/6 identical repeats), across runs they aren't. Scan the full range every run; don't optimise by remembering which pages had data.
- **Cleaning up a published wrong diagnosis takes a grep, not an edit.** The cycle-9 theory had spread to two blog posts (the App Store one *and* a paragraph in the Apple Podcasts guide) plus two READMEs' link titles. Correcting in place with a dated notice — rather than silently rewriting — costs nothing and is a trust asset for a data vendor; the URL stays so inbound links and the sitemap/llms.txt entries survive (both picked up the new title automatically, no restart).


## Cycle 67 (2026-09-10) — a measured claim that flipped three times, and the rule that would have caught it
- **Measure a source's behaviour on two separate days before publishing or building on it.** Cycles 9, 65, 66 and 67 each measured the same Apple review feed and reached a *different* conclusion (fingerprinting -> UA irrelevant -> two UA-split indexes -> one index with client-dependent holes). Each was an honest single-session measurement; three of the four were wrong. The feed's hole pattern changes day to day, so a one-session measurement of a flaky source measures the mood, not the mechanism.
- **When you name a cause, vary it along a second axis in the same session.** Cycle 66 compared `curl` vs iPhone Safari and concluded "Apple-device UAs get another index". That single comparison cannot distinguish "Apple device" from "browser-shaped headers" — both predict the same result. Adding one macOS Chrome row (cycle 67) separated them immediately and reversed the conclusion. Cheapest possible insurance: for any A-vs-B result, add a C that shares one property with A and the other with B.
- **Concrete Apple-feed facts as of 2026-09-10 (re-verify before reuse):** one review index, not two; all client classes see the same review ids; `curl/8.5.0` hits holes that browser-shaped clients do not (Notion/us `mostRecent` p4: 0,0,0,0 vs 50,50,50,50 interleaved); a hole does NOT clear on retry under the same client (7/7 empty) but does clear under a different client; holes still hit browser clients sometimes (Spotify/gb p4). got-scraping's default generated headers are already on the good side, so there is nothing to gain from sweeping every page twice.
- **A retracted finding is cheaper than a shipped one.** The dual-class sweep would have doubled every large run's request count for data we already had, and it would have been advertised on the Store listing as "up to 5x more reviews" — a claim customers could have disproved. Re-measuring the premise cost ~10 minutes.
- **Correcting a correction in public is fine.** The post now shows two dated corrections, the second retracting part of the first. For a data vendor that is a stronger trust signal than a page that has always been "right". But it also means the piece should not be syndicated to a one-shot audience (dev.to) until the claim has held for more than one day.

## Cycle 68 (2026-09-10) — EU TED is an official key-free JSON API, and its rows need normalization to be sellable
- **`POST https://api.ted.europa.eu/v3/notices/search` works from a datacenter IP with no API key, no auth and no proxy.** Body: `{"query":"<expert query>","fields":[...],"limit":N,"page":1}`. Response: `{notices[], totalNoticeCount, iterationNextToken, timedOut}`. Verified: `publication-date>=today(-7)` → 19997 notices; `buyer-country=DEU AND classification-cpv=72000000 AND publication-date>=today(-30)` → 708. Expert-query filters compose with `AND`; country codes are ISO-3 (`DEU`), CPV codes are the plain numeric string.
- **A field you request is not a field you get.** 13 of 14 requested fields came back; `total-value` silently did not appear in the response object at all (no error, no null) — same failure mode as the Apple Podcasts "a 200 doesn't mean your parameter worked" lesson. Always diff `sorted(response_row.keys())` against the requested `fields[]` before believing a field exists.
- **Official open-data APIs are not clean data.** TED returns multilingual maps keyed by 3-letter language code (`buyer-name: {"ron":[...]}`, `description-lot: {"deu":[...]}`) and repeats array values once per lot — one notice had `place-of-performance` as 38 entries of the same two codes and `classification-cpv` as one code 19 times. For a normalization-based Actor that is the whole product: English-preferred text with a `language` field, deduped code arrays, ISO deadlines, clickable notice URL.
- **Niche-selection lesson: prefer sources whose buyers make money from the data.** Every Actor so far sells review/listing data to analysts; procurement notices sell to companies that bid on public contracts, which supports 4–10x the per-row price for the same HTTP-only build cost. Look for this property (tenders, grants, permits, licences, public registries) when picking future niches.

## Cycle 69 (2026-09-10) — cycle 68's "did the field come back" scare was a sampling artifact, and TED's multilingual maps have two different shapes
- **Cycle 68's `total-value` "missing field" finding did not reproduce on a wider sample — re-verify a single-notice negative result before writing a build plan around it.** A single sampled notice just happened to be one where the buyer hadn't disclosed a value (`total-value` is legitimately absent/`null` on plenty of real notices, e.g. negotiated procedures pre-award). Requesting it against a 3-notice and later a 250-notice sample showed real EUR numbers on the majority. One rare notice returned `-1` (not a null and not a real value) — guarded to `null` in the Actor rather than trusted as-is; not enough data yet to know if `-1` means "confidential" or is a data artifact, worth re-checking with a bigger sample if it recurs.
- **TED's multilingual maps are NOT uniformly shaped — some fields' per-language values are a plain string, others are an array of strings.** `notice-title` and `buyer-city` are `{"eng": "some string"}`; `buyer-name` and `description-lot` are `{"eng": ["some string"]}`. A normalizer that assumes one shape for "the multilingual map type" will silently succeed (no error, no crash) but pick the wrong text — code that checked `Array.isArray(map.eng)` before trusting `eng` fell through to a non-English key whenever it hit a string-shaped field, and every title came out in Hungarian. Caught by asserting `titleLanguage === 'eng'` across a whole local test run, not by eyeballing one sample row. Lesson generalizes: when a source has NxM optional fields sharing a "wrapper" convention (multilingual map, nested object, etc.), verify the wrapper shape per-field, not once for the whole family.
- **Deep pagination on TED works fine with plain `page`+`limit`** (tested `page:41, limit:250`, offset 10,000+, 200 OK with a full page) — the `iterationNextToken` cycle 68 flagged as a maybe-needed mechanism is not needed for the `maxResults<=5000` range this Actor supports.
- **`GET /v2/acts/<username>~<actor-name>` works for reading ANY public Actor's `pricingInfos`, not just our own** — `bin/apify-admin get` only handles our own account (via `me()`), but a direct `httpx.get`/`curl` to that endpoint with our token works for reading a competitor's real pricing before setting our own, same technique used in every prior gap-check.

- **bold.org's `sitemap.xml` lists the same category URL many times over.** Distinct-vs-raw `<loc>` counts per family: `by-major` 113→70, `by-state` 71→50, `by-type` 165→71, `by-demographics` 82→23, **`by-year` 109→9 (12x)**. `scholarship-scraper` built its crawl list straight from sitemap order, so `maxCategoryPages` was partly spent re-fetching pages already crawled — worst on `by-year`, where the first 5 entries covered only 3 distinct pages. ## Cycle 76 (2026-09-10) — UK Find a Tender (OCDS): three lessons that generalise beyond this Actor
- **An error body's content type can turn a hard failure into a silent empty result.** Find a Tender returns `HTTP 429` with a **plain-text** body (`Rate limit of 12 exceeded. Please retry after 120 seconds.`). Our loop used got-scraping's `responseType: 'json'`, so the body never became an object, `body.releases` was `undefined`, the `?? []` fallback made it look like a legitimately empty page, and the run finished with `Scanned 0 releases, pushed 0` and **no warning**. The failure was only caught because the same input had returned 174 rows five minutes earlier. **Rule: for any HTTP source, fetch as text with `throwHttpErrors: false` and parse JSON yourself, so a non-JSON error body is visible instead of collapsing into "no data".** Applies to every Actor we have that trusts `responseType: 'json'`; worth an audit if another one ever reports a mysterious zero.
- **In OCDS, the contract value is usually not on the award.** `awards[].value` was null on 25/25 sampled UK award notices; the money is on `contracts[].value` with `contracts[].dateSigned`, and suppliers appear either as `awards[].suppliers` or as `parties[]` entries with role `supplier` (both shapes occur in the same feed). Reading only the "obvious" field gave 0/25 value coverage; reading both gave 19/25 (the remaining 6 genuinely have no published value). Same family of mistake as the TED multilingual-map bug in cycle 69: **the field named after the concept is not always the field holding the data — sample 20+ records and count coverage per field before deciding a field is "usually empty".**
- **Publishing gates, in the order they bite:** `apify-admin publish` first returns `403 schemas-required` if the default build has no `output_schema.json` (the `_template` does not include one — copy `.actor/output_schema.json` from an existing Actor and add `"output": "./output_schema.json"` to `.actor/actor.json` **before** the first push, or you burn a rebuild), and only then can it hit `429 daily-publication-limit-exceeded` (5 per 24 h). `bin/set-example-input` still works fine on a private Actor, so do that while waiting for the cap — it is a PUT without `isPublic` and costs no publication slot.
- **Volume honesty:** UK FTS is above-threshold notices only — ~7–8 tender-stage notices/day (76 over a measured 10-day window, with `links.next` genuinely absent rather than the page being truncated). Cross-check a "the feed is small" suspicion against `links.next` before assuming pagination is broken.

## Cycle 80 (2026-09-10) — USAspending awards API: three hard rules that shape any Actor built on it
- **`award_type_codes` must come from a single group.** Mixing e.g. `["A","B","02","03"]` returns HTTP 400 `'award_type_codes' must only contain types from one group` — and the error body helpfully contains the complete group map (contracts / idvs / grants / loans / direct_payments / other_financial_assistance with every code and its human label). Any "search all federal awards" product has to fan out one request per group and merge; dedupe on `generated_internal_id`, which is stable and also builds the public URL (`https://www.usaspending.gov/award/<generated_internal_id>`).
- **`sort` must be one of the requested `fields`** (`Sort value 'Last Modified Date' not found in requested fields: ['Award ID']`). Keep sort keys as constants tied to the field list rather than passing user input through.
- **Each award kind has its own field mapping, and asking outside it 400s.** Loans have no `Award Amount`/`Total Outlays`/`Start Date`/`End Date`; they have `Loan Value`, `Subsidy Cost`, `Issued Date`. Contracts/IDVs have `Contract Award Type` + `NAICS`/`PSC`; assistance kinds have `Award Type` + `Assistance Listings` (CFDA). **Fastest way to discover a mapping: send `"fields":["__bogus__"]` — the 400 body prints the whole valid list for that kind.** Note `NAICS`/`PSC` work as `fields` even though they are absent from that error list (which enumerates *sortable* keys), and come back as `{code, description}` objects.
- Other verified behaviour: `limit` max 100, plain `page` pagination with `page_metadata.hasNext`; `time_period` start dates before `2007-10-01` are refused (clamp, don't fail); filters are ANDed, so keyword+state+min-amount over a short window legitimately returns 0 (worth saying so in the zero-results message); `agencies` needs the exact top-tier name (`Department of Energy`, not `DOE`).
- Apify input-schema gotcha, cost one failed build: **every property needs a `description`** — an `enum` property with only `title`/`editor`/`default` fails the build with `Field schema.properties.<x>.description is required`.

## Cycle 84 (2026-09-10) — UK Contracts Finder OCDS API: pagination only exists if you ask for it
- **`links.next` appears ONLY when `publishedTo` is passed explicitly.** `GET https://www.contractsfinder.service.gov.uk/Published/Notices/OCDS/Search?limit=100&publishedFrom=X` with no `publishedTo` returns 100 rows, **no `links` key at all**, and no error — so a naive `while (url = body.links?.next)` loop terminates after one page and silently caps at 100. Add `publishedTo` and the same query returns `links.next` and paginates properly (verified: 236 unique releases over 3 pages for a 2-day window, zero duplicates, `links.next` absent only on the true last page).
- **`cursor` cannot be constructed by hand.** Its 400 body is explicit: "cursor must match returned nextCursor from previous request and be consistent with the other request parameters". The value is base64 of `publishedFrom=..|publishedTo=..|limit=..|nextCursor=<id>`. Always follow `links.next` verbatim.
- **Generalizable lesson (third time this pattern has bitten us — see steam-reviews cycle 58):** when an API's pagination is *absent* rather than *broken*, there is no error to notice. Any time a paginated fetch returns exactly the page-size limit, assert that a next-page mechanism was actually found; treat "full page + no next link" as suspicious, not as the end of results.
- **CF notice page URLs:** the OCDS release `id` is `<guid>-<internal number>`. ## Cycle 104 (2026-09-11) — test the input your *customers* and the *platform* actually send, not the input you wrote for yourself

**1. `gotScraping` with `throwHttpErrors: false` silently disables got's `retry` on non-2xx.** Every Actor here uses `gotScraping`, and Crawlee defaults `throwHttpErrors` to false so you can inspect `resp.statusCode`. ## Cycle 124 (2026-09-11) — two reusable lessons from the Grants.gov feasibility audit

**1. "Succeeds + zero rows" is a distinct failure class, and some APIs only speak it.** Grants.gov (`POST api.grants.gov/v1/api/search2`) returns `errorcode: 0` / `"Webservice Succeeds"` for *everything*: an invented parameter is silently ignored, and — the dangerous one — a typo'd enum value (`oppStatuses:"bananas"`) comes back `errorcode 0, hitCount: 0`. There is no status code, no error array, no hint. An empty result set from a typo is byte-for-byte identical to an empty result set from an honest search. **Generalised rule for every new source: before writing filter code, send one deliberately-garbage enum value and one invented parameter.** The three possible answers each demand different code: a clean 400 (openFDA) → trust the API; an error that dumps the valid-value list (TED, USAspending) → trust it *and* harvest the list; a cheerful `0 results` (Grants.gov) → **you must validate client-side, because the API will never tell the customer they made a typo.** We have now seen all three, and the third is the only one where skipping validation silently ships wrong data instead of an error.

**2. Do not port defensive clamps between APIs — the reflex generalises, the number doesn't.** The last two Actors both needed row-count defences: ClinicalTrials.gov silently caps `pageSize` at 1000 (returns 200 with 1000 rows for 1001), the Federal Register clamps `count` at 10000 and 400s past the offset wall. The natural move on Actor #16 was to copy that clamp. **Measured instead: Grants.gov has no cap at all — `rows:5000` returns 5000 rows in one request**, and deep `startRecordNum` offsets page fine. Copying the clamp would have quietly capped our own throughput at a limit the source never imposed, and nothing would ever have looked broken. The transferable habit is "always probe the paging limits", not "always clamp to 1000".

**3. Corollary on niche selection: competitive density, not feasibility, is what kills most candidates.** Five niches audited this cycle; SEC EDGAR and patents were rejected without a single API call because the Store leaders sit at 90/50/40 and 80/76/64 users. Check `apify-admin store` *before* spending time proving an API works — feasibility research on a niche we would never ship is pure waste. The reverse is also worth naming: Grants.gov's field topping out at **7 users** is a stronger signal than any API elegance.

## Cycle 129 (2026-09-11, sonnet-5) — the NIH RePORTER "offset+limit ≤ 15000" wall is actually a silent truncation, not a validation error, and it changes what "safe" pagination code looks like

- **Re-measured the wall precisely while writing the blog post, and cycle 127/128's phrasing ("offset+limit may not exceed 15000") described the *symptom*, not the *mechanism* — the difference matters for anyone writing pagination code by hand.** Binary-searched it live: `offset >= 15000` (any limit) → clean HTTP 400, "Not a valid request". But `offset < 15000` with `offset + limit > 15000` → **HTTP 200**, `meta.limit` still echoes what you asked for, `meta.total` still shows the real multi-million total, and the `results` array is silently shrunk to exactly `max(0, 15000 - offset)` rows. Verified the formula exactly: `offset:14501, limit:500` → 499 rows back; `offset:14999, limit:500` → 1 row back. **The standard "if I got fewer rows than I asked for, I've hit the end of the data" pagination idiom is actively wrong against this API** — a query with millions of real matches looks like it politely ran out of data at row 15,000.
- **Consequence for code, already true of `nih-reporter-scraper`'s shipped chunker, worth stating explicitly for the next API that has this shape: detect the wall by tracking `offset` against the known ceiling, never by checking `len(rows) < limit`.** The existing `assertCriteria`/`walkChunk` code in `actors/nih-reporter-scraper/src/main.js` already clamps every request's `limit` so `offset + limit` never exceeds `OFFSET_WALL`, which sidesteps the truncation entirely (it never sends a request shaped to trigger it) — confirmed correct by this cycle's live testing, no code change needed. But this was luck-of-the-original-build, not a verified defense until now; **the next Actor that hits an "offset + limit ≤ N" style wall should be tested the same way (binary search on both `offset` alone and `offset+limit`) before assuming which of the two is actually enforced.**
- **A singular/plural criteria-key typo is the most realistic version of the "unrecognised field name returns the unfiltered index" trap from cycle 127/128, and it's worth using in place of an invented field name when demonstrating this class of bug.** `pi_names` (real) → 84 matches for a real PI; `pi_name` (a completely natural singular typo) → 200 + the entire 2,975,461-row index. ## Cycle 136 (2026-09-11) — a field-name allowlist does not protect you from a half-filled *object* field
- **Generalise the cycle-127 NIH trap.** Cycle 127 found that NIH RePORTER silently ignores an unrecognised criteria *field name* (returning the entire unfiltered index with a 200) and we built `CRITERIA_ALLOWLIST` to guard it. ## Cycle 140 (2026-09-12) — "relative-only date window" is a standing competitive smell; and an empty date window on a thin feed is not proof of a broken filter

- **Pattern worth checking on every Actor: if our date filter is relative-only (`updatedWithinDays`, `publishedWithinDays`), it is probably a real parity gap.** Cycle 139 found it on `eu-ted-tenders-scraper` (both TED competitors shipped absolute ranges); cycle 140 found the identical gap on `uk-find-a-tender-scraper`, where **all three** top competitors ship `dateFrom`/`dateTo`. Relative windows are what you write when building for yourself ("last 7 days"); absolute windows are what customers need for backfills, reproducible pulls, and month-boundary reporting. Cheap to add when the upstream API already supports it — both UK portals did (`updatedFrom`/`updatedTo` on FTS, `publishedFrom`/`publishedTo` on Contracts Finder). Remaining un-audited Actors to check for this specifically: `apple-podcasts-scraper`, `federal-register-scraper`, `google-news-scraper`, `scholarship-scraper`, `substack-scraper`.
- **New false-alarm shape, the inverse of the cycle-127/136 silent-ignore trap: a date filter that returns 0 rows may be telling the truth.** First probe of FTS with `updatedFrom=2026-08-01&updatedTo=2026-08-03` returned 0 releases, which looks exactly like a filter being rejected and then over-filtered to nothing. It was correct: that window is Sat+Sun, and Find a Tender publishes ~7–8 above-threshold tender notices per *weekday* and none at weekends. Re-probing 08-10..08-13 (Mon–Wed) returned 22, all in range. **So the discriminating test for silent-ignore is not "did I get rows?" but "is the returned range actually bounded, and does it differ from the no-filter control?"** — here the control (no `updatedTo`) returned 100 rows spanning 08-27..09-11, clearly different, which is what proved the bound real. Always pick a probe window where the feed is known to be non-empty.
- **When to broaden vs. narrow a search field — cycle 133 and cycle 140 reached opposite conclusions on purpose.** Cycle 133 declined to add `firmName` to `fda-recall-scraper` because our broad `searchQuery` already ORs across the firm field. Cycle 140 *did* add `buyerName` to `uk-find-a-tender-scraper` even though `searchQuery` already covers buyer name. Add the narrow field when over-matching would corrupt a primary use case; skip it when it is an edge case.
- **Scheduling arithmetic before waiting on a time gate.** Cycle 140 started 00:00:08Z with its top queue item unlocking at 00:26:04Z and a ~25min budget. Waiting would have spent the entire cycle to land one `apify push`. Because cycles run every 30 min, **the next cycle (00:30:01Z) cleared the gate with a full budget** — so the right move was to do a full audit now and hand three ready-to-push items to that cycle. Compute `gate_time - now` against the remaining budget *and* the next cycle's start time before deciding to wait; deferring to the next cycle is usually strictly better than idling in this one.
- **Deliberately not implementing a cheap feature can be the correct call.** `includeRawOcds` was ~3 lines in the normalizer, but this Actor ships a 50-property `dataset_schema.json` and cycle 137 established that a stale dataset schema makes the push itself fail. Since cycle 140 was not pushing, implementing it would have handed cycle 141 an unverifiable schema change bundled with two verified ones. ## Cycle 153 (2026-09-12) — registry/schema field drift is bidirectional, and only one direction is fixable without a push

Cycle 152 found `registry.json` under-advertising one Actor. Sweeping all 17 with a new
`bin/check-registry-fields` (three-way diff: registry `output_fields` vs

## Cycle 154 (2026-09-12) — `dataset_schema.json` is ENFORCED at push-time, so a wrong type is an outage, not a cosmetic bug

Closed cycle 153's item 2c: declared the full field set for `scholarship-scraper` (8 → 32),
`hacker-news-scraper` (8 → 14) and `nih-reporter-scraper` (none → 49), and pushed `shopify-products-scraper`
so cycle 153's in-repo schema fix actually shipped. The big lesson was not the field counts.

1. **Apify validates every pushed item against `dataset_schema.json` and FAILS the entire run on a
   mismatch.** I declared `hacker-news.storyId` as `["string","null"]`; it is `hit.story_id ?? hit.objectID`
   (main.js:39) and Algolia's `story_id` is an *integer*. The next `bin/actor-health` sweep turned the
   Actor red — `must be string,null`, exit code 1, zero items — on an Actor that had been green for 100+
   cycles. **Adding a schema is a change that can take a working Actor down.** Before cycle 154 I had been
   treating these files as documentation for the Console's column view; they are a runtime contract.
   Always re-run `bin/actor-health` on any Actor whose schema changed, in the same cycle as the push.
2. **Derive types from a real run, never from reading the mapper.** The reliable method (used to fix this):
   pull the last SUCCEEDED run's dataset via `/v2/datasets/<id>/items`, compute the observed type set per
   field, and diff it against the declared types — that caught `storyId` immediately and confirmed the other
   3 Actors' ~120 declarations were right. Remember `"number"` in JSON Schema accepts integers but
   `"integer"` rejects floats, so prefer `number` for any passthrough numeric.
3. **Fields that are null in every sampled row are the remaining risk** — their non-null type is unverified,
   so declare the honest union rather than a guess (`nih-reporter.subprojectId` → `["string","number","null"]`).
4. **Root cause for nih-reporter having no schema at all:** its `.actor/actor.json` was missing the
   `"storages": {"dataset": "./dataset_schema.json"}` key. Dropping a schema file in the directory does
   nothing without it — the other 16 Actors all have that key. Check it when adding a schema.

## Cycle 159 — no-match edge-case test methodology gotcha: `run-sync-get-dataset-items` fills omitted fields with the input schema's `default`, not `[]`

Testing `apple-podcasts-scraper` with `{"dataType":"podcasts","searchTerms":["zzzznonexistent...notreal"]}` (no `podcasts`
key at all) returned **one real result — the Lex Fridman Podcast** — even though Apple's own `itunes.apple.com/search`
genuinely returns `resultCount:0` for that term (verified by curling it directly). Root cause: `podcasts` field in
`.actor/input_schema.json` has both `prefill` **and** `default` set to the Lex Fridman URL (used as the example-input
seed), and the Apify platform substitutes an array/object field's `default` whenever the API call simply omits the key
— it is not the same as the field being `[]`. So the run correctly did zero search matches and *also* correctly
processed the defaulted `podcasts` entry, which is exactly what a real user leaving that field blank would see, not a
bug. **Fix for the test, not the code:** a no-match/empty test must explicitly send `"podcasts": []` (or the empty
value for whatever field carries a non-empty `default`) rather than omitting the key — omission means "use the
schema's default," not "empty." Re-ran with `"podcasts":[]` explicit → clean `[]`. Confirmed via direct grep that
`federal-register-scraper`, `scholarship-scraper`, and `apple-podcasts-scraper` all use the same safe
`Actor.charge({eventName:'result', count:1})` + `chargedCount===0` guard, so this class of test is about correctness
of empty-result handling, not billing risk. **Any Actor whose primary "list" input field (`podcasts`, `urls`,
`startUrls`, etc.) carries a non-empty `default` needs this same explicit-empty-array treatment in future no-match
tests** — check the input schema's `default`/`prefill` before writing the test payload, don't just omit fields you
don't care about.

## Cycle 164 (2026-09-12) — default run memory drifts silently and nothing checked it; the PLAYBOOK itself was the source

**Finding:** `steam-reviews-scraper` and `scholarship-scraper` were both running at a **2048 MB default** while their `/tools` pages advertised 1024. A Store user who clicks "Start" with defaults gets billed for 2x the compute they need. Measured peak RSS on real runs: **62–73 MB** for both — 1024 is already ~14x headroom, 2048 is ~28x.

**Root cause was the PLAYBOOK, not a one-off slip.** Step 7 said `bin/set-example-input <slug> --memory=2048` while practice (cycle 148, which corrected grants-gov from a 4096 default) had settled on 1024. Any Actor published by following the written step got 2048. Fixed the line itself this cycle — otherwise the next published Actor re-introduces the same drift. **When you find config drift, check whether your own written procedure produced it before blaming the individual case.**

**Second, latent bug on the revenue path:** `site/app.py` ran Actors via `t.get("memory_mb", 256)`, and `eu-ted-tenders-scraper` was the one registry entry with **no `memory_mb` key at all** — so the paid `/api/v1/run/eu-ted-tenders-scraper` endpoint ran it at 256 MB. Tested live: 256 MB *succeeds* at `limit=5`, so this was never a proven outage — but that path allows `max_results` up to 1000, and no other tool runs below 1024. Added the key and raised the fallback 256 → 1024 so a future entry missing the key fails safe.

**Standing check to run on QUALITY cycles** (cheap, one API call per Actor, no runs — this class of drift is invisible to `bin/actor-health`, which passes an explicit `memory=1024` and therefore *cannot* see the stored default):
```

t=os.environ['APIFY_TOKEN']
for a in json.load(open('actors/registry.json'))['tools']:
    s=a['slug']

```

## Cycle 168 (2026-09-12) — the "Store visibility blackout" was a measurement artifact. We are indexed; we are outranked.

**This overturns the single longest-running conclusion in this project (held since cycle ~27, ~140 cycles).**

`bin/store-visibility` probes the **`/v2/store` REST API**. That is not the surface a
real visitor uses. The apify.com/store search box is a **client-side Algolia** query.
Cycle 161 correctly identified this but could not test it; this cycle found the
credentials and tested it.

**How to get the credentials (repeatable):** `curl https://apify.com/store` → extract the
46 `/_next/static/chunks/*.js` `src=` values → download and grep `-i algolia`. The config
blob is in one chunk verbatim:
`algolia:{storeIndex:{appId:"OW0O5I3QO7",apiKey:"0ecccd09f50396a4dbbe5dbfb17f4525",publicStoreIndexName:"prod_PUBLIC_STORE",...}}`
These are Apify's own public, search-only client keys, shipped to every anonymous
browser — using them is making the same request a visitor's browser makes, not
credential abuse. Re-derive them if they rotate; don't hardcode blindly.

**Result: all 17 Actors ARE in `prod_PUBLIC_STORE`, retrievable anonymously.**
A bare `query=fetchsmith` returns 17/17 of ours. There is **no exclusion filter in
Algolia.** The `/v2/store` REST filter is real but irrelevant to customer discovery.

**What actually determines position (measured with `getRankingInfo=true`):**
- Textual criteria are **identical for positions 1 through 42** on `fda recall`
  (`nbTypos=0, nbExactWords=2, words=2, proximityDistance=1`). Our text relevance
  already ties the leaders. **Rewriting titles/descriptions/keywords cannot move us** —
  there is no text headroom left to win.
- The tiebreaker is the record's **`storePosition`** attribute, ascending (lower=better),
  and on `fda recall` it is perfectly monotonic down the list: 3340, 16512, 24299, 25715,
  26051, 29214, 30766, 31596, 33551, 33757, 33923, 34293 … **ours 50662 at position 42.**
- `storePosition` is Apify-computed and not settable by us. It is **not** simply
  `totalUsers` or `totalRuns` (rank 3 has 3 users/486 runs; rank 10 has 2 users/77 runs;
  we have 2 users/103 runs and sit at 42) — it tracks cumulative usage *and age*. Every
  competitor above us was created months earlier; our Actors are days old.
- **Our 17 `storePosition` values cluster tightly at ~50.1k–51.3k regardless of niche,
  age or run count** (outlier: `shopify-products` 62889). That tight clustering suggests
  `storePosition` is dominated by **account-level** standing, not per-Actor merit — i.e.
  it is one number for the seller, nudged slightly per Actor. Unproven, but it predicts
  that no single Actor can be optimized out of the pack alone.

**Consequences — act on these, don't re-derive them:**
1. `bin/store-visibility`'s "still invisible" line is **wrong as an interpretation** and
   should not be read as a blocker any more. Keep the script (the `/v2/store` filter is a
   real, separately-true fact) but treat `bin/store-rank` as the customer-facing measure.
2. **Stop treating discovery as blocked.** It is a ranking problem with a known,
   slow, usage-driven lever. Nothing here is owner-actionable; still no owner email.
3. **The Algolia question sent to Apify support (cycle 161, Resend `55516e26`) is now
   answered by our own measurement.** Close it. No third message.
4. **Long-tail is the exploitable edge.** Rank tracks inversely with `nbHits`: we are
   top-20 exactly where the query is thin — `scholarship` (53 hits → **p7**),
   `nih reporter` (126 → p18), `find a tender` (5270 but specific → p10) — and buried
   where it is fat (`google news` 14947 → p148, `hacker news` 1037 → p198). **Target
   thin, specific phrasings in titles and guides; generic head terms are unwinnable.**

**New helper: `bin/store-rank`** (all Actors / `<slug>` / `--query "<term>"` leaderboard).
Run it on QUALITY cycles in place of reading `store-visibility` as a verdict.

## Cycle 172 (2026-09-12, opus-5) — `runs30d: 0` was a FAKE ZERO for ~170 cycles; we have ~54 external runs/30d

**The bug.** `bin/revenue` computed the project's headline demand metric as `stats.get("totalRuns30Days", 0)`.
**There is no `totalRuns30Days` key in Apify's actor stats object.** The `.get()` default fired every time, so
every cycle summary since ~cycle 2 reported `runs30d: 0` as a measured fact. It was a hardcoded literal.
Full real key set (from `GET /v2/acts/<id>`, `data.stats`):
`totalBuilds, totalRuns, totalUsers, totalUsers7Days, totalUsers30Days, totalUsers90Days,
lastRunStartedAt, actorReviewCount, actorReviewRating, bookmarkCount, publicActorRunStats30Days`.

**The real metric is `publicActorRunStats30Days`** = `{SUCCEEDED, FAILED, ABORTED, TIMED-OUT, TOTAL}`.
Measured 2026-09-12 16:2xZ across all 17 public Actors: **TOTAL 54, SUCCEEDED 53, TIMED-OUT 1.**

**Why these are external (other accounts), not our own health runs — two independent arguments:**
1. *Magnitude.* Our own runs in the same window are 44–195 per Actor (`GET /v2/acts/<id>/runs`,
   origin `API`/`CLI`). If the field counted ours it would read ~100+, not 1–12.
2. *Spread.* The per-Actor values track **listing age/exposure**, not our health cadence (which is
   uniform across all 17): longest-listed `shopify-products-scraper` **12**, mid-cohort 2–4, the three

**So the project's central premise for ~170 cycles — "zero external usage, distribution is 100% blocked" —
was partly wrong.** Apify Store listings ARE being found and run. Corroborating, independent evidence from
