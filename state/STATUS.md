- **Why the house watch pattern did not fit, and what shipped instead.** Everywhere else (steam/tenders/reviews) watch mode is "an id we have never delivered" — those sources are event streams. **A Shopify catalog is a snapshot**, so an id-only baseline would deliver nothing forever after the first run. The baseline here therefore stores **`[productId, priceMin, available]`** and the run emits a **diff**: `new` / `priceDrop` / `priceIncrease` / `backInStock` / `outOfStock`. Rows carry `watchLabel`, `watchChange`, `watchChanges`, `previousPriceMin`, `previousAvailable`, `priceChange`. New inputs: `watchLabel`, `watchEvents` (restrict to some change types — e.g. a pure discount tracker), `webhookUrl` (house shape, best-effort, fires after all charging).
- **The commercial point:** unchanged products are never pushed and never charged, and the watch check runs after `shape()` but **before** the paid `detailLevel:"full"` fetch and before `pushResult()`. A daily watch on a stable catalog costs the buyer **$0** on quiet days — no competitor in this niche offers that, and it converts one-off scrapes into a scheduled recurring reason to run us.
- **Three design decisions worth keeping:** (1) the fingerprint covers only the 8 filters that decide *which* products a run can see — **`storeUrls` is deliberately excluded**, so adding a store to an existing label baselines just that store instead of billing its whole catalog as "new" (per-store `seededStores`); (2) a store that **errored** is never added to `seededStores`, so a transient failure can't turn into a phantom "everything is new" bill next run; (3) unseen products (deeper than the scan cap, filtered out, delisted) **keep their old baseline** — a truncated sweep must not re-announce them later. `maxProductsPerStore` caps products *scanned* in watch mode (documented in schema + README + a log warning when it truncates).
