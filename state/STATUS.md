  1. **`appNames`** — free-text app name input, resolved via `itunes.apple.com/search?entity=software&term=<name>` to a `trackId`, merged into the existing `apps` pipeline. **Verified live before shipping that Apple's search API is a real trap for "resolve by name" features**: it essentially never returns zero results — random keyboard-mash strings (`xqzzptmwvbnjklasdfghqwerty999888777`), pure gibberish, and emoji-only queries all matched real, completely unrelated apps (an Arabic math quiz, an emoji trivia game, a security-camera app), and even a single ASCII character ("a") returned 3 popular apps. Only a literal empty string returned 0 results. A naive "take the top hit" implementation would have silently resolved a typo to a random app. Fixed with a relevance gate: a match is only accepted if it shares a real word (>=3 chars) with the app's name/bundle id/developer; otherwise the name is treated as **no match found** (named warning, not a guess).

If the fallback-to-other-sort path (empty-feed recovery) ever lands on `mostHelpful`, the cutoff still filters but doesn't try to early-stop an unordered feed.

Fixed: when `appNames` is non-empty and `apps` exactly equals the known default array, the default is discarded rather than mixed in (documented tradeoff: a user who explicitly types the *exact* default URL alongside `appNames` would also have it dropped — accepted as a rare, low-cost edge case vs. the alternative of an uninvited, billable app in every `appNames`-only run).
